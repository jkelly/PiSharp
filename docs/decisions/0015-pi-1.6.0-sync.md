# Pi v1.6.0 sync

Status: candidate implementation authorized by the project owner on 2026-11-21: "Update PiSharp to Pi and Pi Durable both released version 1.6.0". This authorization covers every applicable change in v1.5.2..v1.6.0 for Pi and Pi Durable, which share one upstream repository. It does not authorize publication or deployment.

## Target and scope

The candidate moves from Pi v1.5.2 (`b4afdddf44e059c67ccf5097e5317d913521b470`) to v1.6.0 (`faac585884ae2c013a6b1400f3e9e77f10b34bac`, tree `7b395e942aa81ffe0dba09ae2939184c200e4d3b`). All packages and root changes are inventoried from the complete local Git diff in `compatibility/sync-1.6.0-files.json`: 1,311 changed files, with both endpoints and their hashes and no API file-count limit. `compatibility/sync-1.6.0-applicability.json` gives every one of them a work package and a status. Native runtime changes require implementation and regression evidence. The upstream applications under `apps/`, upstream build tooling, upstream documentation and TypeScript-only files are recorded as explicit no-ops with a category and a reason. No inventory or version update establishes parity by itself.

The candidate package version is 1.6.0. The extension Node runtime installs exact 1.6.0 Pi dependencies into a version-isolated cache and pins `undici` to 8.12.4, the version in the 1.6.0 coding-agent manifest. Existing caches remain available. The detailed provider identity follows the candidate version; default attribution and account-selection policies do not change. The Durable and Chord source constants name the v1.6.0 commit and packages.

## Evidence and preservation

`compatibility/target.lock.json` records the candidate Git source and its canonical SHA-256 hashes. The prior target is preserved byte-for-byte as `compatibility/target.v1.5.2.lock.json`; the v1.5.2 inventory, applicability table, acceptance record and their tests continue to refer to it. Earlier target locks, the v0.99.1 evidence baseline, historical fixtures, captures and published release evidence, including the 1.5.2 release record and model catalog, remain pinned to their original sources. Authored regressions are distinct from upstream captures.

The new lock carries the previous source paths that still exist, all surviving paths changed in the range, and every upstream package manifest. The row-level Durable map stays historical v1.5.0 evidence. `compatibility/durable-sync-1.6.0-overlay.json` carries the changed Durable files, and the map's candidate pointer names it and keeps the v1.5.2 overlay as a previous candidate. A source citation moves to the v1.6.0 commit with the verified implementation of the file it names. Existing acceptance gaps carry forward until supported by new evidence.

The Node bridge's compatibility modules are regenerated from the exact v1.6.0 source. `tools/NodeBridge/runtime-fixture-160` holds the manifest and npm lock of the 1.6.0 test runtime beside the preserved `runtime-fixture-150` and `runtime-fixture-152`. It is test-only and admits no production cache.

## Validation and release

Offline source checks verify tag and tree identities, the complete file inventory, archive hashes, per-file hashes and preserved locks. Area tests and integrated .NET validation are recorded separately. The sync work plan is `AI_DOCS/sync-1.6.0.md`, and the work-package reports are under `AI_DOCS/agent-reports/`.

This decision records a candidate source target. It does not update the public release ledger, advertise complete parity, publish packages or deploy a site. Those actions require their own authorization and release evidence.

## Release authorization

On 2026-11-22, after PR #63 merged with all CI checks passing, the project owner asked for the 1.6.0 package release to be prepared. Release preparation targets all 28 admitted libraries and the CLI at version 1.6.0 through the existing tag-triggered, gated NuGet trusted-publishing workflow. The tag and publication wait for the owner's separate go-ahead. The owner gave it the same day, and chose to ship the MCP HTTP close fix of PR #66 in 1.6.0: the release branch merges `main` after #66, so the tag includes it. Publication flags and the dated changelog are promoted only after the uploaded packages and GitHub release are verified. The earlier source receipts retain their original scope and bytes.
