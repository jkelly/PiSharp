# Pi v1.2.0 sync

Status: approved by the project owner on 2026-10-14 ("update everything to latest"). The standing rule applies: PiSharp follows what current Pi does.

## Target

PiSharp retargets from Pi `v1.1.0` (`abe508e1b89912adde45528136c3221eb69acdd7`) to Pi **`v1.2.0`**: commit `06a466935536f8c9bcacb2d5efc0fc021be1bdff`, tree `e8872645392bc4d214e3153104864e4b69d99ed0`, released 2026-10-12.

The range is `v1.1.0..v1.2.0`: 81 commits and 606 changed files (146 added, 177 deleted, 281 modified, 2 renamed). There is no intermediate release. Most of the churn is in packages PiSharp does not port: `pi-durable`, `pi-env`, Chord, the removed client, server and protocol packages, and the deleted `coding-agent/src/experimental` tree.

The source comparison found these unchanged:
- `pi-agent-core` (only its package version changed);
- the RPC mode and types;
- the session manager, `messages.ts` and the compaction algorithm (only `compaction/utils.ts` changed, see the applicability table);
- the `read`, `write`, `edit`, `bash`, `grep`, `find`, `ls` and `powershell` tools.

Do not invent migrations for them. The re-freeze re-verifies their hashes.

## Timing

The sync starts now on the `sync/pi-1.2.0` branch. A foundation stage lands first: this decision, the applicability table, the re-freeze, the citation re-pin and the work list. Area work then ports the behaviour changes in parallel.

Every gap and open gate recorded against v1.1.0 carries forward unchanged. None is closed or dropped by retargeting.

## Releases

PiSharp **1.2.0** is released when the sync changes are complete. No tag, release or package is published without the owner's explicit go-ahead.

## Excluded scope

The following stay outside the port, under [architecture.md](../architecture.md) "Scope for native version 1" and decision 0002:
- `pi-env`, the remote execution daemon, including its new pseudo-terminal (`pty`, `ptyForeground`) and `listFiles` operations.
- `pi-evals`, a private package.
- The removed `pi-client`, `pi-server` and `pi-protocol` packages and the experimental server, client and plugin stack (`coding-agent/src/experimental`, `src/cli/experimental`, the `./client` and `./experimental/plugin` exports). PiSharp never ported them, so there is nothing to remove.
- Chord, including its new host runtime that replaces the facet and service runtime. The coding agent no longer depends on Chord.
- Codemode's new sandbox hosts:
  - `RemoteCodemodeSandbox` and the `@earendil-works/pi-codemode/cloudflare` entry (a Cloudflare Durable Object);
  - `InlineCodemodeSandbox`;
  - the `portable` entry with `CodemodeSandboxBase`;
  - deterministic `sandbox.start()` runs.

  The coding agent's codemode extension still uses only `CodemodeSandbox`. PiSharp runs scripts on Jint ([decision 0003](0003-codemode-javascript-engine.md)). This exclusion lapses if the coding agent starts using one of them.
- `pi-durable`, its harness, tools and storage adapters. It stays on the separate `feature/pi-durable` branch and is re-pinned there separately. Upstream deleted `coding-agent/src/experimental/durable` in v1.2.0. That matters only to the durable branch: the owner chose to keep `pisharp durable` there as a PiSharp-only mode.
- The Nix flake, packaging, and npm or managed-installer distribution policy, as in decision 0002.

Each exclusion is recorded in [sync-1.2.0-applicability.json](../../compatibility/sync-1.2.0-applicability.json).

## Notes: coding-agent core and CLI

Native C# extension contracts follow the TypeScript API changes of `before_agent_start` (see [native before_agent_start](../contracts/native-before-agent-start.md)) and of tool reach. Source-compatible additions:
- `ExtensionBeforeAgentStartEvent.MessageType` (`ExtensionBeforeAgentStartMessageType.User` or `Custom`) and `Message` (the starting custom message), with `ExtensionBeforeAgentStartEvent.ForCustomMessage`;
- `AgentPromptPreparation.LeadingMessages`: custom messages a prompt preparation records before the run's inputs;
- `ExtensionToolDescriptor.ReachesTools` (`Func<JsonData, ToolReach>`, pure and synchronous) with the new `PiSharp.Contracts.ToolReach` (`All` or the input's words), as `ToolDefinition.reachesTools`;
- `ToolNamespace.Aliases`, as `ToolNamespace.aliases` (MCP servers alias their namespace with the server name);
- `McpOfferedTool.OutputSchema` and `McpPlannedTool.OutputSchema`, which codemode declarations relocate under `structuredContent`, and `McpOAuthIssuerMismatchException`;
- `PiSharp.Agent.TypeBoxJsonSchema`, a public port of the TypeBox 1.3.27 validation engine. The published `models`, `settings`, `keybindings` and `theme` schemas are checked with it, so validation messages are TypeBox's.

Behaviour changes for native extensions, as upstream's breaking changes:
- `before_agent_start` handlers also run for runs started by a custom message with `triggerTurn` (`MessageType` `Custom`, empty `Prompt`).
- While a run starts the session is busy: input without a delivery mode fails with Pi's "Agent is already processing" message.
- The native `sendUserMessage` action without `DeliverAs` now fails with that message while the session is busy (also while a run starts). It used to steer. While idle it still starts a run, as `prompt({ streamingBehavior: deliverAs })` does.
- `before_agent_start` handlers receive a cancellation token that only closing the session cancels; an abort requested meanwhile aborts the run as it starts. With `AgentCancellationBehavior.SettleAborted`, an `Agent` whose run was cancelled during its prompt preparation records the inputs and settles an aborted run instead of failing before them.

## Notes: Node bridge

TypeScript extensions run against the Pi 1.2.0 npm packages (`PiNodeRuntime.PiVersion` 1.2.0, without the `@earendil-works/chord` override). The offline compatibility modules are regenerated with `port-upstream.mjs` from v1.2.0, and the theme JSON validator is installed before themes load in both modes, as `main.ts` does.

TypeScript tools that declare `reachesTools` are registered with `ExtensionToolDescriptor.ReachesTools` reaching every tool (`ToolReach.All`), as `tool_search` does. The contract is pure and synchronous and runs on the tool-call path, so PiSharp does not ask the tool's own function in Node there: a call waits for every MCP server, which is never wrong but can be slower. Exact per-input reach for TypeScript tools would need an asynchronous variant of the contract; that is deferred. `pi.getAllTools()` still hands extensions `ToolInfo.reachesTools` as the tool's own function, and for C# tools (`codemode`, `tool_search`, native tools) a function that asks the host.

## Notes: deferred

- **Per-input reach of TypeScript tools.** TypeScript tools that declare `reachesTools` reach every tool (see the Node bridge notes). Exact reach needs an asynchronous variant of `ExtensionToolDescriptor.ReachesTools`.
- **Live clock in the unthemed codemode renderer.** The themed interactive renderer shows `Elapsed` while a script runs and `Took` once it finished, like bash rows, and `executeCodemode` publishes an update before the first nested call. The unthemed native renderer (`PiSharp.Codemode.CodemodeRenderer`) shows only the recorded `Took` time of a final result, because the native renderer contract carries no row state.

Both are recorded as `ported-with-deferral` in the applicability table (`tools.reaches-tools`, `codemode.row-timer`).

## Notes: implementation differences and close-out fixes

- **MCP wait by reach.** Pi's MCP extension waits in its `tool_call` handler for the servers a call may reach. PiSharp's MCP host is not an extension of the session's registry, so the profile composes `McpToolCallHooks` over the session's tool hooks: the extensions' `tool_call` handlers run first (the built-in MCP extension loads after the others), then the wait. The observable order is Pi's. Another extension's `codemode` or `tool_search` that declares `reachesTools` stands in for a disabled built-in one, as in `ensureDiscoveryActive`.
- **A command's triggered run when print mode exits.** A TypeScript command that calls `pi.sendMessage(..., { triggerTurn: true })` and returns without `ctx.waitForIdle()` leaves its run starting when print mode reads the last message and closes. Pi 1.2.0's dispose aborts that run and drops its events: exit 0, no output, the session header alone in JSON mode, no model request (observed with the 1.2.0 npm packages). PiSharp 1.1.0.7 failed that run and exited 1 (`RpcHostFailed` or `CleanupFailed`). That was not a regression from the busy-start change. The close-out fixed it to match: a closing RPC dispatcher lets a run it did not adopt settle under the shutdown abort without writing its events; an adopted run that the abort ends as a cancelled task settles instead of failing the host; and print mode writes no JSON event after the last prompt resolves, since `print-mode.ts` unsubscribes before it disposes the session.
