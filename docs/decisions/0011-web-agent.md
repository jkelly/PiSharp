## Context

PiSharp Web Agent is a local chat app and model playground for one power user on one computer: chats with any of PiSharp's providers, side-by-side comparison, a playground with every request option, and (later) spend caps and personal model tests. Until now it existed only as a plan and mockups.

Three things decided its shape:
- **The durable engine already exists.** `feature/durable-network` (decision 0008) has a multi-session host (`PiSharp.Durable.Hosting`), the device API's frame building (`PiSharp.Durable.Server`), the client reducers (`PiSharp.Durable.Client`) and a web hub on the same design system (`PiSharp.Durable.Web`). None of them is packable, so the Web Agent must live in this repository.
- **The provider catalog lives in the CLI.** The model registry, the built-in catalog, `models.json`, provider auth and live routes are internal to `PiSharp.Cli`, which a web app cannot reference.
- **The flagship is a chat that never loses a run.** Closing the tab, sleeping the computer or killing the server mid-answer must still give exactly one answer, never re-run a tool that ran, and never switch the account a chat was started with.

`docs/architecture.md` deferred browser and web interfaces. Decision 0008 started that expansion for durable sessions only; this decision is the second one: a web product on top of it.

## Decision

1. **Location.** `src/PiSharp.WebAgent`, an ASP.NET Core MVC app (`Microsoft.NET.Sdk.Web`, not packable) in this repository, on `feature/web-agent`. It references `PiSharp.Web.Common`, `PiSharp.Durable.Hosting`, `PiSharp.Durable.Server` and `PiSharp.Durable.Client`. Decision 0008's hub may later become its `Durable` area.
2. **Model runtime.** The registry, catalog, `models.json` config, `ConfigValueResolver`, remote catalog, provider auth catalog and live provider routes move out of the CLI into a new unpacked library, `src/PiSharp.ModelRuntime` (`git mv`, namespaces kept, `InternalsVisibleTo` for the CLI, the Web Agent and their tests). One new seam, `IProviderCredentialSource`, replaces the concrete `auth.json` store; an `IRegistryProviderLayer` hook keeps Llama in the CLI. `AuthJsonCredentialStore`, `ProviderLoginHost`, Llama, the CLI's `DurableModels` and the TUI stay in the CLI. If the extraction stalls, a thin router over the public `NativeProviderFactory` (openai, google, anthropic by key, codex, copilot) replaces it.
3. **Streaming.** Server-Sent Events, one stream per browser tab, with the hub's `hello` / `{sub, frame}` / `view` protocol (`GET /api/stream`, `PUT /api/stream/{id}` subscriptions), and server-rendered Razor fragments. Commands are idempotent JSON POSTs under `/api/...`. No SignalR.
4. **Storage.** One data folder, `%LOCALAPPDATA%\PiSharpWebAgent\` by default:

   | What | Where |
   | --- | --- |
   | Chats | durable sessions under `device\` (one `agent.sqlite` per chat) |
   | Web data: account metadata, active accounts, chat bindings, settings, the spend ledger, evals | `webagent.db` (SQLite, WAL), with migrations in one id range per area |
   | Every provider call (W4): Playground, Compare, Tool Bench, agent compare and chats | `runs.db`: kept 30 days, pinned runs exempt, raw payloads opt-in with a 7-day cap |
   | Secrets | `credentials.json`, each value encrypted with ASP.NET Core Data Protection (key ring in `keys\`, protected with DPAPI on Windows) |

   `PISHARP_WEBAGENT_DATA` moves the folder, and `--data <folder>` overrides both.
5. **Sessions.** Each chat is a durable session hosted in process, not PiSharp's JSONL session store. `DurableDeviceHost` runs inside an `IHostedService` (running `pisharp durable serve` instead would read the CLI's `auth.json` and could not use web accounts). Markdown export comes from the Client's `Transcript`. The tool working directory is a setting of its own (Settings › Tools), passed as `StartDirectories`.
6. **Tool approval.** A `web-approval` durable extension, built on the command guard's `BeforeTool` pattern (`src/PiSharp.Durable.Hosting/Apps/Extras.cs`). It decides before the tool's intent is recorded, so a crash while waiting asks again and a crash after deciding never re-runs the tool. The decision is memoised (`MemoAsync`); the first tab to decide wins. Read-only tools never ask. Questions and plan reviews use the existing `user-interaction` extension.
7. **Accounts.** A chat is bound to its provider account when it is created, and keeps it. Each request carries `metadata.pisharp {account, tier, op}` through the new `DurableDeviceOptions.SessionStream` hook; the harness saves it with the prepared request and reuses it on recovery, and the host route strips it before anything reaches a provider. An unknown, removed or revoked account fails with the `expired` state; nothing falls back to another account. Anthropic is API key or Amazon Bedrock only (no subscription OAuth); ChatGPT/Codex sign-in is opt-in.
8. **One user, this computer.** The app binds `http://127.0.0.1:5180` and refuses any `--urls` that is not loopback. There are no login pages. `PiSharp.Web.Common`'s HostGuard answers 421 to a foreign `Host` (DNS rebinding), 403 to a cross-origin write and 415 to a non-JSON API write, and sends a strict Content-Security-Policy (no inline script). Secrets never reach the browser, a log or a command line; pages show masked hints only.
9. **Offline mode.** `--faux` runs on `FauxDurableModels` and a faux catalog, with no provider code path registered at all. Every automated test uses it, or recorded and scripted transports.

## App skeleton (W2, WU4)

**Start.** `Program.cs` reads `--faux` and `--data` itself (ASP.NET Core's command-line provider would read `--faux --data x` as `faux=--data`), passes the rest (`--urls`, configuration) to the host, and stops with exit code 2 and a one-line reason for a bad `--data` or a non-loopback `--urls`. The content root is the output folder, as in the hub. `WebAgentHost` holds the core: `AddWebAgentCore`, `AddWebAgentFallbacks`, `UseWebAgentCore`, `MapWebAgentCore`. Each area plugs in through its module (`Credentials/CredentialsModule.cs`, `Chat/ChatModule.cs`, `Routing/RoutingModule.cs`, `Settings/SettingsModule.cs`: `AddXxxArea(services, options)` and `MapXxxArea(app)`), called from `Program.cs` before the fallbacks. The fallbacks register only what no area did: the faux models as `IDurableModels`, `FauxModelCatalog` as `IModelCatalog`, an empty `IRecentChats`. With `--faux` the faux models and catalog replace whatever an area registered. `GET /api/health` answers `{status, faux}` for scripts and tests.

**Data folder.** `WebAgentOptions` resolves the folder (`--data`, then `PISHARP_WEBAGENT_DATA`, then `%LOCALAPPDATA%\PiSharpWebAgent`) and names `device\`, `keys\`, `webagent.db` and `credentials.json`. At start the app creates the folders, migrates `webagent.db` and protects a probe value, so the Data Protection key ring exists (or a broken one fails the start) before the first secret is saved.

**`webagent.db`.** `WebAgentDb` uses the hub's exact SQLite pins (`Microsoft.Data.Sqlite` 10.0.12, `SQLitePCLRaw` 2.1.12), WAL, unpooled connections, a 5-second busy timeout and foreign keys on. Migrations are registered in DI (`AddWebAgentMigration`), each with an id inside its area's range:

| Area | Ids | Taken |
| --- | --- | --- |
| core | 1–99 | 1 `app_info` |
| accounts | 100–199 | 100 `accounts`, `active_accounts` |
| chats | 200–299 | 200 `chats` |
| settings | 300–399 | 300 `settings` |
| presets (W4) | 400–499 | 400 `presets` |
| compare (W4) | 500–599 | 500 `compare_groups`, 540 `bench_sessions`, 580 `agent_compare_runs`, `agent_compare_turns`, 585 `agent_compare_patches` |
| spend (W3) | 1000–1999: 1000–1099 ledger, 1100–1199 guard, 1200–1299 pages, 1300–1399 estimation, 1400–1499 chat | 1000 `spend_caps`, 1001 `spend_reservations`, 1100 `spend_approvals`, 1101 `spend_stops`, 1102 `spend_approval_uses`, 1103 `spend_approvals.submission`, 1400 `spend_chat_sends` |
| evals (W5) | 2000–2999: 2000–2099 contracts, 2100–2199 rater, 2200–2299 checks, 2300–2399 drift, 2400–2499 suites, 2500–2599 arena, 2600–2699 pages, 2700–2799 pins, 2800–2899 tests | 2000 `eval_battles`, `eval_votes`, 2001 `eval_suites`, `eval_cases`, 2002 `eval_runs`, `eval_results`, `eval_schedule_slots`, 2003 `eval_baselines`, `eval_drift_signals`, 2004 `eval_price_snapshots`, `eval_price_changes`, 2500 `eval_arena_rounds` |

`schema_migrations` records every applied id, so a lower id added in a later release still runs; each migration and its record commit in one `BEGIN IMMEDIATE` transaction, so a failed migration leaves nothing and concurrent starts apply it once. `PRAGMA user_version` holds the highest applied id for diagnostics only. An id outside every range, or used twice, fails the start.

**Contracts** (`Contracts/`), which the areas implement:
- `IModelCatalog`: providers (id, display name, logo key, auth kinds, billing kind) and their chat models (id, name, reasoning and thinking levels, context window, max tokens, input kinds, cost per million tokens). `FauxModelCatalog` lists `faux/echo`, `faux/echo-small` and `faux/echo-thinking`; WU6's catalog replaces it. Every listed model must resolve through `IDurableModels.GetModel`.
- `IRecentChats`: the sidebar's chats (id, title, updated, running).
- `ISettingsStore`: typed sections, each one JSON document in `webagent.db` (camelCase, enums by name), read as its defaults when missing or unreadable, validated on save, with a `Changed` event so running services follow the pages. The M0 sections are `defaults` (provider, model, thinking level), `tools` (working directory, default the user's home; approval mode `ask`, `allowList` or `auto`, default `ask`; allow-list rules) and `models` (hidden `provider/model` keys). **Shell.** `_Layout` (sidebar with New chat · Playground · Compare · Tool Bench · History · Evals · Presets · recent chats · Settings, the top bar with the theme toggle and shortcuts button, banners, the shared confirm and shortcuts modals, the toast area), `_SettingsLayout` with `_SettingsNav`, and `_ProviderModelSelect`, the two linked dropdowns every model choice uses (only the chosen provider's list is enabled, so a form posts the right pair without script). The theme comes from `PiSharp.Web.Common` (`_WebCommonHead`), not a copy. Static files are always revalidated (`Cache-Control: no-cache`), because modules import each other by plain URL.

**Tests.** `tests/PiSharp.WebAgent.Tests` runs the app as a child process with `--faux`, a temporary data folder and a free port, with provider keys and URL settings removed from its environment, and covers the start, the loopback-only binding, the guard and CSP, the data folder and its overrides, migrations, the key ring, every shell page and asset, the settings store, the faux catalog and the shell partials.

## Hosting seams (W2, WU1)

**Stream metadata.** `DurableDeviceOptions.SessionStream` is a per-session hook, `Func<string sessionId, JsonObjectValue?>`. When a host sets it, every model request of the session carries `metadata.pisharp = {<host fields>, op}` in its `DurableStreamOptions` (`SessionHarnessSettings.Stream`). Generation's prepare phase and compaction's summary request already save the stream options in the task checkpoint, so a recovered request keeps its `op` and account, and every new request (a retry prepared again, a summary request) gets a new `op` (a GUID) and the current binding. `op` is reserved: the host's value replaces one the hook returns. A hook that throws goes to `OnReport`, and the request carries `op` alone. `SessionStreamMetadata` builds, reads (`Field`, `Operation`) and strips the object. `NativeDurableModels`' own routes map only `metadata.user_id`, so the object never reaches a provider. The hook runs on every settings resolution, so it must be cheap and non-blocking (the Web Agent answers it from an in-memory map of the chat bindings). A deferred response's poll carries no stream options; no provider supports deferred responses today.

**In-process frames.** `AgentFrames.ReadAsync(session, agentId, options, ct)` (public in `PiSharp.Durable.Server`) yields one agent's frames (a snapshot with the inbox, requested docs, batches, inbox changes) for a `HostedSession` with no HTTP; `DeviceStreams.AgentAsync` now calls it after `hello`. `AgentFrames.ActiveEntriesAsync`, `AgentFrames.InboxAsync` and `HostedSession.SubscribeChanges` are public too. The device server and the Web Agent's `AgentViewHub` both read agent frames through it.

## Model runtime (W2, WU2)

`src/PiSharp.ModelRuntime` (not packed) holds the model registry, the built-in catalog, `models.json` config, `ConfigValueResolver`, the remote catalogs, `ProviderAuthCatalog`, `ProviderLiveAuthentication` (with Anthropic's), `LiveProviderRoutes`, `LiveModelCatalog`, `LiveSessionSelection` and their helpers: 21 files moved with `git mv`, keeping their `PiSharp.Cli.*` namespaces. The catalog's JSON shards stay in `src/PiSharp.Cli/Models` and are embedded by link under their old logical names. Its seams:

It references `PiSharp.CodingAgent`, `PiSharp.Tools`, `PiSharp.Rpc`, `PiSharp.Extensions.Runtime` and `PiSharp.Extensions.Agent` (the last two because `PiPayloadBudget` moved whole), and never `PiSharp.Cli`, which `tests/PiSharp.ModelRuntime.Tests` checks by reflection.

## Credentials, accounts and sign-in (W2, WU5)

**Accounts.** An account is one credential of one provider. There are four kinds:
- `apiKey`: a key stored in the app.
- `oauth`: a subscription sign-in (ChatGPT for `openai-codex`, GitHub Copilot).
- `environment`: a variable from `ProviderEnvironmentKeys` that the host was started with. Read-only.
- `ambient`: credentials the provider's SDK finds itself, such as the AWS credential chain or Google application-default credentials. Read-only.

Account metadata lives in `webagent.db` (migration 100). The `accounts` table holds:
- id, provider, label, kind, status (`connected`, `expired` or `unavailable`, with a reason);
- a masked hint;
- the sign-in's identity (the ChatGPT account id);
- non-secret settings and details;
- expiry, created, updated and last-used times, and the last connection test.

The `active_accounts` table holds each provider's chosen account.

The active account of a provider is the one the user chose. When there is none, or the chosen one is unavailable, it is the first usable account in this order: sign-in, stored key, environment variable, ambient credentials, oldest first. As a result:
- A first stored key or sign-in becomes active ahead of a variable.
- Removing the active account passes the choice to the next stored account. When no stored account is left, the variable serves again.
- Nothing else moves the choice.

A chat binds to an account id and keeps it (WU7). Nothing falls back from one account to another. An expired or unavailable account fails its chats clearly.

Environment and ambient accounts are synced into rows once per process (ids `env-<provider>-<variable>` and `ambient-<provider>`). A variable that goes away leaves its row `unavailable` instead of deleting it. `ANTHROPIC_OAUTH_TOKEN` never becomes an account: Anthropic is API key or Amazon Bedrock only.

**Secrets.** `credentials.json` is the only place a secret is kept.
- Each value is encrypted with Data Protection, using the key ring in `keys\` (DPAPI on Windows).
- Each kind of secret has its own purpose, `PiSharp.WebAgent.Credentials.ApiKey.v1` or `PiSharp.WebAgent.Credentials.OAuth.v1`, narrowed by the account id. A value copied to another account, or read as another kind, does not decrypt.
- A write goes to a temporary file in the same folder, is flushed to disk, and then replaces the file in one move.
- An unreadable file is left untouched, and every secret read and write then fails with that reason.

The two stores are written in an order a crash cannot turn into a visible broken account:
- A new secret is written before its row. An orphan secret is pruned at the next start.
- A row is deleted before its secret.

Pages see a masked hint at most: a known key prefix, an ellipsis and the last four characters, or nothing for a value under 12 characters. There is no "reveal". Provider and auth-server messages are scrubbed of keys, tokens and JSON bodies before a page or a log sees them.

**Services.** `CredentialVault` is registered once under two interfaces:
- `IAccountStore` gives pages metadata and writes: list, get, active, add a key, replace a key, rename, set active, remove, mark expired, and a `Changed` event.
- `ICredentialVault` gives routing secrets, server-side only. `ReadAsync(accountId)` returns the key, settings or stored sign-in. `OAuthSource(accountId)` is the `IAdmittedOAuthCredentialSource` for `StoredOAuthLifecycle`. Its modifications are serialized per account, refreshes are stored before they are returned, and a removed account is never written back.

**Sign-in.** `SignInFlows` runs PiSharp.AI's own flows on the server and answers their prompts for the page:
- `OpenAICodexOAuth`: ChatGPT with PKCE through the loopback callback on port 1455, or OpenAI's device code.
- `GitHubCopilotOAuth`: GitHub's device code, the Copilot token exchange and model enabling.

Starting a sign-in returns either the authorize URL or the user code and verification URL. The verifier, the codes and every token stay on the server. When port 1455 is taken (for example by the Codex CLI), the page asks the user to paste the redirect URL, and a wrong `state` fails the flow.

A completed sign-in is stored:
- into the account being signed in again, which keeps its id and chats; a different identity is refused and nothing changes;
- otherwise into the account with the same identity;
- otherwise as a new account.

Other rules:
- One flow runs per provider. Starting another cancels the first.
- A flow is given up after 15 minutes.
- Only `openai-codex` and `github-copilot` sign in. Anthropic is refused.
- With `--faux` nothing starts and no connection test runs: the app is offline.

**Connection test.** It runs only on the user's click, as one GET of the provider's models list, never a completion:
- OpenAI-compatible: `{base}/models` with a Bearer token.
- Anthropic: `/v1/models` with `x-api-key`.
- Google: `/v1beta/models` with `x-goog-api-key`.
- Copilot: its own models list.
- A stored ChatGPT sign-in is checked by resolving it, which needs a request only when a refresh is due. A failed refresh marks the account expired.

**API** (`/api/credentials`, JSON, `Cache-Control: no-store`, writes as JSON POSTs under HostGuard):
- `GET accounts[?provider=]`, `GET accounts/{id}`.
- `POST accounts`, `accounts/{id}/key`, `accounts/{id}/rename`, `accounts/{id}/activate`, `accounts/{id}/remove`, `accounts/{id}/test`.
- `POST test` tests a key before it is saved.
- `GET signin`, `POST signin`, `GET signin/{flowId}`, `POST signin/{flowId}/code`, `POST signin/{flowId}/cancel`.
- Errors are `{error}` with 400, 404 or 409.

**Tests.** `Credential*Cases.cs` cover:
- the vault in process, with a fake environment and fake OAuth endpoints (an in-memory HTTP handler) and a real loopback callback on a free port;
- the API end to end against the `--faux` app.

They include a Data Protection round trip, including another key ring, account and purpose. They scan for planted secrets in `credentials.json`, `webagent.db` and its WAL, the key ring, the log, every API answer and every shell page. They also cover masked hints, the active account per provider, environment accounts, validation, the per-account OAuth source, orphan pruning, both sign-in flows (callback, paste, device code), re-sign-in, cancel, replace and time-out, and the connection tests.

## Durable chats (W2, WU7 and WU8)

**Device.** `DeviceHostService` opens one `DurableDeviceHost` on `device\` with the registered `IDurableModels`, and no jobs or schedules. Its `SessionStream` answers `{account, tier}` from the chat binding, and the host adds `op`. Migration 200 (`chats`) binds each chat to its session, provider, model, account id, thinking level, tier, current agent, title and archived flag. A chat binds its provider's active account at creation (`IChatAccounts`, which routing implements over the account store) and keeps it.

**`ChatService`.** Create and send (a browser `requestId` de-duplicates retries), steer and follow-up while busy, abort, withdraw, rename, archive, fork from any entry, edit-and-resend, retry, compact, change the model, thinking level or tier (409 while busy), answer questions, review plans and export Markdown. It is also the sidebar's `IRecentChats`.

**`web-approval`.** It checks the call's memo first, then asks in `ask` mode, or in `allowList` mode when no rule matches. Read-only tools never ask. `ApprovalBroker` is keyed by session, agent and task; the first decision wins, and a later one gets 409 `already_decided`. Only human decisions are memoised. "Allow in this chat" lasts until a restart; "Allow always" adds allow-list rules.

**Streaming.** `AgentViewHub` keeps one reference-counted `AgentFrames.ReadAsync` feed per agent, reduces it with `AgentModel`, and renders changed items with `_ChatItem` through `FragmentRenderer` at most every 150 ms. A new subscriber gets the whole view first. A feed also renders again when the device's running flag changes. `ChatStreamMux` serves `GET /api/stream` and `PUT /api/stream/{id}`.

**Pages.** `/`, `/chat/new` and `/chat/{id}` map `chat-new.html` and `chat.html`: streaming, reconnecting, background, interrupted, dropped and stopped answers, provider errors with details, the expired state with Retry (it forks and sends again with the same account), the approval card and modal (back after a reload), notices, message info, the session details pane, the session tree, the kept-running toast and the composer's slash menu. `ChatFailures` classifies a failed answer; routing's `Account expired (<reason>): ...` errors show as the expired state. Spend Guard states wait for W3.

## Routing (W2, WU6)

`RuntimeModelCatalog` lists every non-virtual chat model that has a live route, from `PiSharp.ModelRuntime`'s built-in catalog (no `models.json`). `WebDurableModels` wraps `NativeDurableModels` with `HostTransport = AccountRouter.RouteAsync` and no environment or key resolver, so nothing falls back. `AccountRouter` reads `metadata.pisharp.account`, strips `metadata.pisharp`, and routes through that account's own generation: a `LiveRouteRuntime` over `WebCredentialSource`, one `StoredOAuthLifecycle` per account, the account's environment allowlist and its `baseUrl`. An unbound, unknown, removed, mismatched, expired or unavailable account stops the request before anything is sent (`AccountRouteErrors`). A provider 401 or a rejected refresh marks the account expired. `--faux` registers no provider code path.

## Settings (W2, WU9)

`/settings` maps the Providers, Provider detail (one view for every provider), Accounts, Models, Defaults and Tools mockups, and the API key, ChatGPT sign-in and Copilot device-code modals (no Anthropic sign-in). A key is POSTed once to `/api/credentials` and never echoed; pages show the masked hint. `/api/settings` saves Defaults, Tools and model visibility. Making an account active is always an explicit choice.

## Recovery, browser tests and CI (W2, WU10)

`Recovery*Cases.cs` kill the app's process tree mid-stream, mid-bash, while an approval waits and during an account switch, then restart it on the same data folder. `tests/PiSharp.WebAgent.BrowserTests` (Microsoft.Playwright 1.63.0, `--faux`) fails on any page or console error. It covers streaming, catching up after a reload, approvals across tabs and reloads, forking from the tree, a planted API key that never reaches the page, and the main pages at 375 px in both themes. `.github/workflows/durable.yml` runs `PiSharp.ModelRuntime.Tests` and `PiSharp.WebAgent.Tests` in its test matrix, and the browser suite in a `webagent-browser` job.

## Spend Guard (W3, S0–S5)

**Contracts and money (S0).** `Spend/Contracts` holds the area's types: sources with fixed wire names (`chat`, `playground`, `compare`, `agent-compare`, `bench`, `arena`, `drift`, `cache-warm`), caps over everything, a provider, an account or a source for a request, a run, a UTC day or a UTC month, each Block or Ask, and the Allow, Ask and Block decisions (Block wins). Amounts are micro-USD integers, times UTC. Refusals carry stable `spend_*` codes (`SpendErrors`) with a parseable `[spend op=..; cap=..]` tail, and the `spend` settings section holds the warning threshold (80%), the reservation output cap (8,192 tokens), the unknown-price behaviour, entered prices and billing overrides. `SpendModule` is a `static partial class`: `AddSpendArea` and `MapSpendArea` call one partial hook per unit (`Spend/<Area>/SpendModule.<Area>.cs`). `--faux-metered` (implies `--faux`) keeps the faux models offline but Metered at $3, $15, $0.30 and $3.75 per million tokens (input, output, cache read, cache write), with usage counted from text length, so tests see real numbers; plain `--faux` stays free.

**Estimation (S1).** `CostEstimator` works out a request's worst case before it is sent: input tokens as UTF-8 bytes / 3 × 1.1 at the higher of the input and cache-write rates, plus the output cap (the request's `maxTokens`, else the reservation cap, else the model's maximum) at the output rate. Price tiers come from the model JSON; within 10% below a tier's threshold the worst case already uses that tier. "Typical" is the median of the model's last 20 actual costs in the ledger. `BillingModes` marks API and environment keys Metered, sign-ins Subscription, faux and loopback providers Free, and a provider without a price Unknown; a user override wins and the detected mode stays visible. Cheaper models are only ever suggestions.

**Ledger (S2).** `SpendLedger` reserves, checks and settles under one lock plus `BEGIN IMMEDIATE`, so 20 parallel $0.10 reservations against a $1 cap let exactly 10 through. A reservation is keyed by its op and idempotent; a group (Compare) reserves all or nothing. States: reserved → settled (actual, or the estimate), released, or uncertain. Uncertain spend keeps counting toward the caps until the user resolves it. Subscription rows are kept at list price and never count toward money caps. `SpendRecovery` runs before the ledger's first other call after a start and marks every row left reserved as uncertain ("stream dropped, no usage reported"). That is right only when the process that reserved them is gone, so the app holds one lock per data folder (`WebAgentDataLock`: `<data>/webagent.lock` kept open with `FileShare.None`, which the operating system lets go when the process ends, even on a crash): `WebAgentHost.CreateBuilder` checks it first, so a second app on a folder in use prints one line and exits with code 2 before it opens anything, `UseWebAgentCore` takes it before the folder is prepared, and the ledger is not made without it. A monthly prompt-cache meter records what cache reads saved and what misses and warm-ups cost.

**Guard (S3).** `GuardedDurableModels` decorates the app's final `IDurableModels` (registered last) and fails closed when a call cannot be checked. `SpendGuard` estimates, reserves under the call's op, and on an Ask or Block takes the run's one-time approval (proceed once, or cap the output so it fits) if there is one (an approval lapses after 10 minutes, is used up by the first stopped call of its run that it matches, and is picked by op first, then by the chat message it answers, then run-wide; every column of an approved Compare group records it, so a recovered column keeps the chosen output cap); otherwise nothing is sent, the decision is recorded as a stop, and the call ends with a non-retryable `Spend Guard billing check: spend_*` error. A request the durable engine sends again after a restart reuses its row (ledger keys op, op~2, …) and is never settled automatically; the usage its resend reports is kept on the row (`ISpendLedger.ReportUsageAsync`), so Resolve can offer that cost. A reserved call's final message carries its ledger key (`pisharp.spendOp`, stored with the answer by the durable engine), and the guard strips that field from every request it forwards, so no provider sees it. How the stream ends settles the row: a finished answer with usage at its actual cost; an error or cancel before any output releases it; a cancel after output at the estimate (raised to what any partial usage reported costs); an error after output, a dropped stream or a metered answer without usage makes it uncertain; a deferred answer keeps its reservation (the handle is remembered in memory only, so after a restart the row stays uncertain). Classification and image generation pass through unguarded (W3 prices chat requests only). The guard never changes the model, the account or the messages; it lowers `maxTokens` only for "cap the output". `GuardedRunExecutor` applies the same reserve and settle rules to non-durable calls (W4's Playground, Compare and Bench; no caller yet).

**Pages (S4).** Settings › Spend: caps (the spend-cap modal adds, edits and removes them), each connected account's billing mode and override, unknown prices, the reservation output cap, the warning threshold and the uncertain rows still counted. History › Spend: the totals against the daily and monthly caps, filters and the mockup's Saved filters (the `spend-filters` settings section and `/api/spend/filters`: named query strings, cleaned to the filters alone, which Save current filters… adds and Manage saved filters renames or removes; a new data folder starts with Uncertain only, Settled at an estimate and Chats only), the paged ledger, CSV export (`/api/spend/ledger.csv`) and the Resolve modal (settle at the reported cost when the recovered request's resend reported usage, at the estimate or an amount, or release). `/api/spend` serves caps, the ledger, resolve and the spend-confirm modal (`POST /api/spend/confirm`). The ledger shows what it holds; an empty ledger shows the empty state. Until W4 builds History's Runs view, its later-milestone page at `/history` shows the same History tabs (Runs · Spend), so the sidebar's History reaches History › Spend.

**Chat (S5).** The composer shows the estimate by Send and, when the guard would ask or block, a chip named after the cause ("Over request cap"). The server works out the request's size from the branch's entries plus the draft; the browser never says how big a request is. A send with `spend: {check: true}` is checked first: an Ask or Block answers 200 `{posted: false, code, message, spend}` with the cause's confirm modal and posts nothing (not an error status, so the browser logs nothing); the user's choice (proceed once, or cap the output) comes back on the same request id and becomes the run's one-time approval, and a Block still refuses. The admitted request ids and the approvals they stored are kept in `webagent.db` (`spend_chat_sends`, migration 1400, pruned after the guard's 30 days), so a retried send of an admitted id is not checked again after a restart either. A call stopped inside a run shows a stop card and the spend banner, and Review… continues it with a "Continue." message after the user's choice. Footers show the ledger's numbers: metered, "≈ list" for a subscription, settled at an estimate, uncertain with Resolve… (a link to History › Spend), price unknown, and the running answer's live estimate. An answer links to the row its `pisharp.spendOp` names; an answer stored without one falls back to usage and time. Every change of a row raises `SpendLedger.Changed`, and an open chat renders that run's footers again, so a Resolve on History › Spend shows at once.

## Custom providers (W3, CP)

Settings › Custom providers edits `<data>/models.json` in Pi's format: list, add, edit (General, Models, Advanced and a server-built Preview), duplicate, delete, import, export and model overrides. Every save is validated with `PiSharp.ModelRuntime`'s `ModelsJsonConfig` and `ModelRegistry` and written atomically, keeping `models.json.bak`; an edit made in another editor is picked up within a second, and an invalid file lists nothing and refuses writes. A key is none (the placeholder key is sent), stored in the credential vault (only its masked hint leaves the server; it is never in the file, the export or the browser after the save), or a `$VAR` reference; `!command` keys are not offered, and a literal key written into the file by hand is not used. The catalog and the routes read a sanitized copy (`routing/models.json`), so custom models route through `AccountRouter` with the provider's own key; loopback base URLs are Free, others Unknown unless priced. Test connection lists the free `/models` endpoint, on a click only. With `--faux` the page still edits the list, but nothing is routed or tested. An entry for a built-in provider id (for example `anthropic`) only overrides models: its `baseUrl`, `headers`, `compat`, `api`, `authHeader`, models and key are not routed (the page lists them as not used, and Import drops them with a warning), so models.json never changes where a built-in account's key is sent. A stored key stays with the servers (scheme and authority) it was entered for: a save that keeps it while pointing at another server is refused, Test connection sends nothing there, and an import that moves the provider to another server without a key of its own removes the stored key and says so. Settings › Providers lists every custom provider after the built-in ones with its key source (no key, a stored key, or `env · VARIABLE`, set or not) and links it to Settings › Custom providers instead of the generic key modal; it counts as connected (for the first-run redirect too) only when it is routed, never with `--faux`, and its key source is usable: a keyless one only when its base URL is loopback (LM Studio, Ollama or vLLM on this machine). A keyless one elsewhere is listed as not configured, with the "no key" chip in the outline tone and a sentence saying why; it stays routed with the placeholder key and is still in the model picker. Accounts & sign-ins notes the vault accounts that hold custom providers' keys (`<name> key`).

## Appearance and About (W3, AP)

Settings › Appearance keeps its preferences per browser in `localStorage` (`pisharp-theme`: dark, light or system; the rest in `pisharp.appearance`); they never reach the server. `appearance.js` runs in `<head>` and sets them on `<html>` before the first paint, so there is no flash of the wrong theme; System follows the browser's colour scheme as it changes. The top bar's toggle and Ctrl+Shift+L change the same choice through `window.PiSharpAppearance`. "Render markdown in user messages" (`userMarkdown`, off by default) is honoured on the server's side: `_ChatItem` renders a user message as typed and, next to it, through the sanitizing `MarkdownRenderer`, and `appearance.css` shows one by `<html data-user-markdown>`; Copy and Edit read the text as typed. Settings › About shows the running build's versions, host facts, catalog numbers, a diagnostics report with no key, token, key hint, account name or message content (copy and download), a provider connectivity check that runs only on a click through the credentials area's connection tester (free endpoints; with `--faux` it says nothing was sent), and links.

## Runs, Playground, Compare, History, Presets and agent compare (W4, R0–R9 and L3)

**Run engine and `runs.db` (R0).** `runs.db` (its own `schema_migrations` in the core id range, WAL; tables `runs`, `run_events` and `run_raw`) records one row per provider call: Playground, Compare, Tool Bench and agent compare runs from `RunEngine`, and every durable session call (chats and agent compare models) through `RecordingDurableModels`, a decorator registered after the Spend Guard and keyed by op, so a recovered call stays one row. `RunEngine` plans a `RunSpec` against the model's API (an option the model cannot take is refused with a 400, never dropped), reserves through `GuardedRunExecutor` (a Compare group all or none), streams, and publishes normalized events to `RunLive`. `/api/runs` serves start, group, plan, options, list, storage, a run, its raw payloads, SSE events with Last-Event-ID catch-up, cancel, pin and delete. A run belongs to the app, so it keeps going when its tab closes; a restart marks a running run interrupted and never retries it. Runs are kept 30 days (settings section `history`); a pinned run keeps its parents and everything under it, at any depth (an agent compare run is three levels: the run, its models, their calls), deleting a run deletes everything under it, and the cleanup runs at start and every hour (`RunRetention`). Raw payloads (the request as sent, the response headers, the raw SSE lines and timing marks, which the routing hook `RunCaptureHandler` captures) are kept only when Settings › Data & storage turns them on, are redacted before they are stored (Authorization and every key-bearing header or query parameter), and are kept 7 days at most.

**Playground (R1).** `/playground` builds a request (`_RequestConfig` with `_RequestConfigModel` and `_RequestConfigAdvanced`, and `_MessageListEditor`), runs it through `POST /api/runs` and streams its events into `_RunOutput`, which ends with the run's metrics (TTFT, total, tokens per second, input, output and cache-read tokens, the ledger's cost and the stop reason). `?run=` reopens a run, live while it runs. Options the model does not take are disabled; one the user set that conflicts stays editable and flagged, and the server refuses the run, so nothing is sent and nothing is downgraded. The service tier is offered only where `RunSpec` sends it. The shared modals are `_ModelPickerModal`, `_ViewCodeModal` (C#, cURL, JSON and the provider request, rendered on the server with keys redacted), `_ToolEditorModal` and `_ErrorDetailsModal`. The tool-call loop adds a tool result (typed, or from a mock) and continues.

**Compare (R2).** `/compare` runs one prompt on 2 to 4 models. `POST /api/compare/run` reserves the columns as one Spend Guard group, all or nothing, and records one `runs.db` row per column under one group id; a refused group answers 200 `{posted: false}` with the confirm modal and is sent again under the same group id only with the user's choice. Shared options adapt per column and say so with chips (a thinking level clamped, max tokens capped, temperature not sent while a model thinks); an explicit override the model does not take refuses the run with a 400 that names the column. `compare_groups` (webagent.db migration 500) keeps the shared request, the columns and Mark best, pruned with their runs, so `?group=` reopens a comparison. Columns stream as text and are swapped for the server's `_CompareColumn` (sanitized Markdown) when they end; the Metrics tab compares them. Re-run sends one column again into its group, and Stop all cancels the running columns.

**History and the run inspector (R3).** `/history` lists `runs.db` with its filters in the query string (search, dates, source, Provider → Model, status), saved filters (settings section `history-filters`; a new data folder starts with three), totals, bulk delete and export, pin, re-run, pagination and Clear history; an agent compare run is one row that expands into its models. `/runs/{id}` shows the header, the metrics and the Request, Response, Raw SSE, Normalized events, Timing and Usage tabs, View code, and HAR and run JSON downloads; without raw payloads it says they were not stored. History › Spend links every non-chat row to the inspector, and `/history` is no longer the later-milestone page.

**Agent compare (R4, R5, R6).** Each model works in its own workspace, `<data>\workspaces\<run>\<slot>` (`WorkspaceManager`, R4): a detached git worktree from the base commit when the project is in git, else a copy that skips the excluded folders and what `.gitignore` names. The project's uncommitted changes are listed and left out, and diffs are against the base. Apply writes a model's changes into the project as uncommitted changes and is refused when the project has uncommitted changes in the same files; Keep branch makes one commit on `pisharp/compare/<run>-<slot>` without switching the user's branch; nothing is committed to an existing branch and nothing is pushed. Workspaces are kept 7 days, and leftovers are cleaned at start and daily; git runs with argument lists, and every path is checked to stay inside its root. The runner (R5, `/api/compare/agent`) gives each model a durable session on the app's device with the same instructions, tools and limits, started in a shuffled order and bound to its model's account. `AgentCompareGate` gives each model its own Spend Guard run key (`<run>-<slot>`) and an equal share of the run cap among the metered ones; turn, time and budget limits stop only that model; the check command runs in each workspace with a timeout. The run's approval mode overrides Settings › Tools for its sessions only, and approvals are answered per call, for every column at once, or as a run grant for one command. `agent_compare_runs` and `agent_compare_turns` (migration 580) keep the runs and their turns, keyed by op, so a recovered request is the same turn; `runs.db` has one parent row per run and one child row per model, with each call under its model. A restart resumes every model. The pages (R6) map compare.html's agent states (setup, dirty, running, approval, done and kept), the workspace, diff and keep modals, and Settings › Tools' agent compare defaults (`_AgentCompareDefaults`, `/api/settings/agent-compare`, settings section `agentCompare`). The "not a sandbox" warning shows wherever tools can run without asking (Allow-list, Auto, a command grant for every column). Ownership, as R6 asked: the agent compare lines of `Settings/SettingsEndpoints.cs` (the `/api/settings/agent-compare` routes, `CheckAgentCompare` and `AgentCompareBody`) and the agent compare section of `Views/Settings/Tools.cshtml` (the `_AgentCompareDefaults` host that replaced its later-milestone chip), `Views/Settings/_AgentCompareDefaults.cshtml` and `wwwroot/css/compare-agent.css` (only `.ac-*` rules, loaded only by the agent compare views) belong to agent compare's pages; the rest of both shared files stays the Settings area's, and `compare.css` stays Compare's.

**Tool Bench (R7).** `/bench` and `/api/bench`: a bench session (`bench_sessions`, migration 540) holds a setup (model, system prompt, tools with mocks, tool choice, parallel and strict, auto-respond rules, latency) and a conversation. Each turn is one guarded run (source `bench`, one group per conversation). A tool call pauses the run for a manual result or an auto-respond rule (a mock, a validation error, or skip); Pi's argument check validates the arguments, and the server checks tool definitions. The bench never runs a tool. The call log exports as JSON.

**Presets (R8).** `presets` (migration 400) holds a model, parameters, prompts and tools for the Playground, Compare or the Tool Bench, never a key or a token (a header or provider option that looks like one is refused; an account is kept by id only). `/presets` lists, filters, edits, duplicates, deletes, imports (checked whole: invalid JSON or one invalid preset saves nothing) and exports them. The Playground, Compare and the Tool Bench host the shared `_SavePresetModal` and `_LoadPresetModal` (`presets-host.js`); a preset loaded into another page is converted, with notes for what it leaves out. Every page loads a preset in place, and its account goes with its model: the Playground selects it in Model & auth's account choice ("Run on", shown when the provider has two accounts or more, or the draft names one), a Compare column in its overrides (with a chip naming it), the Tool Bench in its setup; Compare applies the preset through `compare-request.js`'s `applyDraft`, and new columns start a fresh comparison while the one shown stays in History.

**Data & storage (R9).** `/settings/data` shows the data folder and what is in it with sizes, the Data Protection key ring, chats and the 30-day archive of deleted chats (`ChatArchiveJanitor`), run-history retention and raw payload storage (off by default; a save applies the retention at once), the kept compare workspaces with View run, Open folder (on the machine running the app), Remove and Clean up, export and import (settings, presets and custom providers, reviewed item by item before anything is applied), and the danger zone (credentials, history, chats and settings, each after DELETE is typed; Reset settings writes a backup first). The export never holds a credential, not even encrypted for this machine (which the brief allowed), and says so.

**W3 leftovers (L3).** `Agent.WaitIdleAsync` waits for the stored answer in the Markdown export, and `EscapeModalAsync` presses Escape only after `shown.bs.modal`, so the two flaky W3 browser cases are steady. The spend CSV names the reservation's tokens `assumed_input_tokens` and `assumed_output_tokens`, with `reported_input_tokens`, `reported_output_tokens`, `reported_cache_read_tokens` and `reported_cache_write_tokens` beside them (empty when the ledger has none). Chat create, send and continue answer a Spend Guard refusal with 200 `{posted: false}`. A keyless custom provider counts as connected only on loopback, and Settings › Providers shows each custom provider's key source. Setup's "Add server" opens the custom provider editor through `?add=`. Admitted chat sends survive a restart in `spend_chat_sends`: migration 1400, in the chat part of the spend range, pruned after the guard's 30 days, rather than a 1200–1299 migration (the spend pages' part) pruned after a day as the brief said, so a send is remembered as long as the approval it stored. ## Model Arena, test suites and Drift Watch (W5, E0–E7 and L4)

**Contracts (E0).** `Evals/Contracts` holds the types every W5 unit codes against: ids (`ab`, `tc`, `su` or `sr` and 32 hex digits), `EvalRandom` (SplitMix64 from a stored seed, Fisher–Yates), tags, `ModelIdentity` (provider, model, thinking, temperature and service tier: a leaderboard row never names an account), `ArenaBattle` and `ArenaVote`, `TestCase` (the request as a `RunSpec` without account, endpoint or source, the reference output, the checks and where it was pinned from), `Check` and `CheckResult`, `Suite` and `SuiteTarget` (up to 6 targets, k from 1 to 10, default 3, a suite-run cap), `SuiteSchedule` (every few hours, daily or weekly, in a time zone; a slot at or before `EnabledAt` never runs, missed slots collapse into the latest, a time in a spring-forward gap moves to the first minute after it and a repeated hour runs once), `SuiteRun`, `SuiteResult`, `ScheduleSlot`, `Baseline`, `DriftSignal` with the plan's rule table (`DriftRules`), and price snapshots and changes. webagent.db migrations 2000–2004 add the tables, and the evals range is split by unit (see the table above). Settings section `evals` holds the defaults (answers held until all are in, provisional below 10 comparisons, k = 3); no page edits it. `EvalsModule` is a static partial class with one hook per unit, so the units registered without touching each other's files.

**Rater (E1).** `BradleyTerryRater` fits one leaderboard (a mode and a tag) by MAP with a Gaussian prior, so sparse votes stay finite: a tie counts half, a pick's pairs weigh 1 and a ranking's, tie's or all bad's 2/n, and an optional position parameter measures the user's left-position bias. 500 bootstrap samples, seeded from the mode and tag, give 95% intervals and rank ranges, and nothing depends on the order of the votes. `Leaderboards` builds the tag menu and the rows from voted battles only, and `ArenaMetrics` reads median cost, time to first token and tokens per second (and an agent run's cost, time, turns, files and check) from `runs.db` and agent compare's store.

**Checks and the judge (E2).** Contains; a regex with a 100 ms limit (a timeout fails the check); a JSON schema through `InputSchema`'s subset (the first `json` code block, else the first object); a tool call with argument rules by dotted path; max cost and latency; and an opt-in rubric judge. The judge's rubric is validated with `JudgmentPolicy.Parse`, the target's provider and model are hidden from it, a judge of the target's own family is warned about, its confidence is routed as `JudgmentService.Route` does (never through `JudgeAsync`, whose 24-hour cache would hide drift), and each judgement is one guarded, recorded, uncached call (source `drift`, the suite run's group as its spend run). `/api/evals/checks` validates and tries a check and previews a judge's cost without sending anything to a model.

**Drift and Price Watch (E3).** `DriftAnalyzer` applies the plan's table to one target's run against its accepted baseline. A broken case (passed all k, fails all k, with k of 3 or more), a pass-rate or judge-score drop (an exact one-sided sign test over cases, p < 0.05, with a minimum effect of 0.10 or 0.5 points), cost ±25% (split into price change and verbosity) and an answer fingerprint (SimHash) outside the baseline's own spread are suspect, and become drift only when the next run raises the same rule again; latency and tokens per second ±50% and outside the baseline's 10th–90th percentiles are info; a response model the baseline never saw is drift at once. Drift stays open until a new baseline clears it. Price Watch snapshots each provider's catalog prices when their hash changes (at start and every 10 minutes), lists the last 30 days' changes, answers what a model cost at a given time, and names the schedules a change stops fitting their cap.

**Suites, the runner and the scheduler (E4).** `EvalStore` keeps suites, cases, runs, results, schedule slots, baselines and signals, and inserts a scheduled run with its slot's decision in one transaction (both unique per suite and slot). `SuiteRunner` asks cases × targets × k through `RunEngine` (source `drift`), four at a time, under one Spend Guard group reservation of holds (`hold-<run>-<n>`), releasing each hold as its call is sent; it checks and judges each answer and, when the run completes, analyses each target against its baseline. A run can be cancelled; at the next start after a crash, a run that was going is marked interrupted: its finished answers stay, the rest are cancelled, the holds of calls never sent are released and nothing is asked again (the run engine has already marked the cut-off calls interrupted, and never retries them). `EvalScheduler` (at start and every 30 seconds) runs only a schedule's latest slot, skips it while the previous run goes, never decides a slot twice, and pauses a schedule that a price change or an edit stops fitting. A schedule needs a cap and is refused when its worst case does not fit. `/api/evals/suites`, `/cases`, `/runs` and `/drift` are idempotent JSON APIs, and a run record has `responseModel` now (`runs.db` migration 2).

**Arena (E5).** Compare's Blind switch (on the request and agent setups, remembered in this browser) sends Run all to `POST /api/evals/arena`: the server shuffles 2 to 4 models into columns A to D with a stored seed, runs a request battle as one group (source `arena`) and holds its answers until all are in (Stream anyway shows them as they come), and runs an agent battle through agent compare's runner. Before the vote, nothing `/compare/arena/{id}` sends (the page, its body and diff fragments, the battle's JSON and its event stream) names a contestant. A vote is A to D, Tie, All bad or a ranking (with 3 answers or more), under a tag (the last one used, `general` at first; `agent` for agent battles, kept apart); a stopped or failed battle is void, revealed and never counted. The reveal offers Pin as test case (request battles) or Keep (agent battles, on the run's own page). Migration 2500 adds `eval_arena_rounds`.

**Evals pages (E6).** `/evals/leaderboard` (per mode and tag, with provisional rows, the position-bias line and the votes as CSV), `/evals/suites`, `/evals/suites/{id}`, `/evals/runs/{id}` (polled while it runs) and `/evals/drift` (with the catalog's price changes), and the check editor, schedule and baseline dialogs, filled from server fragments; an unknown suite or run gets a 404 page. The Evals placeholder route is gone, and Evals is the active sidebar item on all five pages.

**Pin as test case (E7).** `_TestCaseModal` is hosted on a chat answer's footer, the Playground's output, a Compare column, the Arena's reveal, History's row menu and the inspector's More menu. The server rebuilds the draft from `runs.db` or the chat every time and stores the request as `TestCase` keeps it (never an account, a base URL or a credential; a run whose options carry one is refused without echoing it), the reference output, the suggested checks, and an existing suite or a new one (the over-cap pane says when a scheduled suite would pause). A run still going, a failed or interrupted run, an agent run and a blind answer before its vote are refused.

**W4 leftovers (L4).** The Playground's cache retention, retries, retry delay, thinking budgets and Azure API version are live controls; the options a run refuses by design say so and where they are set; Sampling shows the catalog's `samplingParams` read-only; presets keep every option the run engine carries; and `W4BenchResetCases` covers the Tool Bench's Reset, removing a message and Export as JSON.

**The shell.** E6 removed the Evals placeholder route and `LaterFeature`'s last entry, so no sidebar link opens "Coming in a later milestone" any more; the placeholder's parts are still in the source, reached by nothing (see Not done).
