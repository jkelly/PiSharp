# Pi v1.5.0 sync

Status: approved by the project owner on 2026-11-02. On the path, the owner chose "Straight to 1.5.0". On scope, the owner chose every area offered and wrote "PORT EVERYTHING!!". The owner approved the phase plan and its release cut the same day ("1.5.0 = phases 0-4, 8"), and gave the release go-ahead on 2026-11-05 ("Release when ready"): PiSharp 1.5.0 releases phases 0 to 4 and the close-out (see [Releases](#releases)). The standing rule applies: PiSharp follows what current Pi does.

The largest changes:
- **pi-schema** (`@earendil-works/pi-schema`, new). Tool arguments are validated as JSON Schema (drafts 2020-12 and 7, compiled to closures, with coercion), not by TypeBox. pi-ai no longer re-exports TypeBox.
- **The model catalog** is generated from models.dev's v2 catalog, by per-provider rules under `packages/ai/catalog/`.
- **Client identity** (1.4.0). A `pi/<version> (<platform>; <runtime>; <arch>)` user agent, and provider attribution headers from pi-ai's `ClientIdentity`.
- **Streaming**:
  - `StreamingJsonParser` parses each tool-call delta once;
  - the TUI's Markdown and highlighting reuse their last render.
- **Telemetry** (1.4.0). Spans, links, metrics and propagation in pi-telemetry, with opt-in `pi.ai.request` and `pi.ai.poll` tracing in pi-ai.
- **Durable**: the 34 breaking changes of 1.5.0 and 1.4.0's six.

## Scope

Everything in the range is in scope. This supersedes the exclusions of [decision 0006](0006-pi-1.2.0-sync.md) ("Excluded scope") and the deferrals of [architecture.md](../architecture.md) "Scope for native version 1" where they cover upstream packages. In this sync's areas:
- **pi-schema**, ported, replacing PiSharp's TypeBox validation of tool arguments. `PiSharp.Agent.TypeBoxJsonSchema` stays where 1.5.0 still uses TypeBox: the theme schema is still compiled with TypeBox.
- **The durable re-sync**: the experimental durable port ([decision 0005](0005-pi-durable-experimental.md)) moves from pi-durable v1.2.0 to v1.5.0 in this sync. It is no longer synced separately afterwards.
- **pi-telemetry**, and pi-ai's request tracing.
- **The update UX**: `pi update`'s custom self-update command (`PI_SELF_UPDATE_COMMAND`, `selfUpdateCommand`) and extension package changelogs after an update.
- **pi-env**, the remote execution daemon and its `ExecutionEnv` client. Earlier syncs excluded it.
- **Chord**, the typed host runtime. Earlier syncs excluded it.
- **pi-evals**, upstream's private evaluation package. Earlier syncs excluded it.

Some parts of the repository are not code PiSharp runs, so there is nothing to port:
- the Nix flake;
- npm packaging;
- the managed installer;
- the release scripts.

Where one of these changes behaviour that users see, the behaviour is ported, for example `pi update` and the pinned dependency versions. The applicability table records each such row.

## Standing rules

The owner's project rules hold for every area of this sync:
- no Anthropic subscription OAuth;
- secrets never reach the browser, logs or command lines;
- servers bind to 127.0.0.1;
- nothing switches model or account silently;
- automated tests stay faux and offline;
- new APIs carry experimental attributes;
- never claim Pi parity without evidence.

New public C# APIs that this sync adds carry `[Experimental]` with a diagnostic id per area. Changed defaults, such as the default OpenAI model moving from `gpt-5.5` to `gpt-6.1-sol`, apply only where no model is selected. They never replace a selection the user made.

## Notes: known design points

Each of these is settled in its area. The area records the outcome here.
- **Tool argument validation.** 1.5.0 validates tool arguments with pi-schema. TypeBox features outside JSON Schema no longer apply: refinements, `BigInt`, `Undefined` and `Void`, codecs and `Format.Set()` formats. Neither do regular-expression property names. Error texts follow pi-schema's (`- t: unresolved reference #/definitions/Missing`). Native C# tools keep their JSON Schema parameters. The Node bridge loads pi-schema with the 1.5.0 packages.
- **Identity.** PiSharp identifies as the Pi version it tracks wherever upstream reads its package version (decision 0006). In 1.4.0 the user agent becomes `pi/<version> (<platform>; <runtime>; <arch>)` and attribution headers come from `ClientIdentity`. The startup header still shows PiSharp's own version.
- **The owner's safe defaults (2026-11-05).** The four rows below that waited for the owner were decided together ("Use safe defaults"):
  - `mcp.oauth-client-registration-auto`: PiSharp is treated as a rebranded build, so under `auto` it never presents a Client ID Metadata Document and registers dynamically;
  - `core.client-identity-attribution` and `core.agent-identity`: no attribution. PiSharp sends neither `PI_ATTRIBUTION` nor its own attribution, and keeps only `x-opencode-client: pisharp`;
  - `bridge.undici-gondolin-advisories`: the extension Node runtime stays on the Pi 1.2.0 packages, because pi-agent-core 1.5.0 attributes requests to Pi by default, and an npm override pins undici to 8.12.3;
  - `cli.pinned-internal-dependencies`: PiSharp's NuGet packages pin their PiSharp siblings exactly (`[<version>]`).
- **MCP Client ID Metadata Documents** (decided 2026-11-05, see above; row `mcp.oauth-client-registration-auto`).
  - **What upstream does.** 1.5.0 makes `oauth.clientRegistration: "auto"` the default. A server that supports Client ID Metadata Documents gets `https://pi.dev/oauth/client.json` or `https://pi.dev/oauth/<id>/client.json` as the client.
  - **Why it applies to PiSharp.** Upstream's rebrand guard switches to dynamic registration when `APP_NAME` is not `pi`. PiSharp's `APP_NAME` is `pi`, so the guard never fires, and used as is PiSharp would present Pi's own OAuth client.
  - **The options:**
    - treat PiSharp as a rebranded build, which keeps dynamic registration under `auto`;
    - host PiSharp's own metadata documents;
    - follow upstream.
  - Dynamic client registration already works. The owner chose the first option.
- **Attribution** (decided 2026-11-05, see above; rows `core.client-identity-attribution` and `core.agent-identity`).
  - **What upstream does.** In 1.4.0, upstream sends `PI_ATTRIBUTION` (pi, `https://pi.dev`) on OpenRouter, NVIDIA NIM and OpenCode requests while install telemetry is on.
  - **What PiSharp does today.** It sends only `x-opencode-client: pisharp`. Decision 0004 says PiSharp must not report as Pi.
  - **The options:** a PiSharp attribution, or none. The user agent follows the Identity point above. The owner chose none.
- **Durable's PiSharp-only surfaces.** pi-durable 1.5.0 removes `watchEvents` (`durable.watch-events-removed`). The device protocol, the web hub and the web agent stream them (decisions 0008, 0010 and 0011). Phase 4 keeps a PiSharp-only event projection (see Durable below), rather than moving them to view state plus the conversation transcript. The durable rows record the other collisions with PiSharp-only code:
  - the required `checkpointWhen`;
  - `sleepUntil`;
  - batch commits in the SQL Server storage;
  - the `ConversationTranscript` and `readOnly` names;
  - which projects `PiSharp.Durable` may reference for pi-schema and telemetry (decision 0005 §4).
- **No rollback across durable formats.** These format versions mean PiSharp 1.2.0.x cannot open sessions that 1.5.0 writes:
  - SQLite schema v2;
  - `pi.live` v2/v3;
  - `pi.tool` v3;
  - `pi.generation` v2.

  The 1.5.0 release notes say so. SQL Server storage gets its own migration for the sleeping status.
- **Chord v2 is still moving upstream.** Upstream builds it slice by slice, and v1.5.0 has slices 1 to 8, 7a to 7c and 10. Phase 4 ports the store, documents state, contract data and registries that pi-durable needs at v1.5.0, under `[Experimental]`. Phase 6 ports the rest.
- **Targets .NET cannot run.** Some upstream backends and drivers run only in Cloudflare Workers (`durable.cloudflare-adapters`, `chord.sqlite-cloudflare`) or in browsers (`durable.indexeddb-storage`). They are `no-op`: the portable interfaces they implement are ported.
- **Self-update.** PiSharp's update check asks NuGet and never pi.dev (see the website's parity page). The custom self-update command runs when NuGet reports a newer PiSharp.Cli. This is recorded as an intentional difference.
- **The model catalog.** The shards are refreshed from `@earendil-works/pi-ai@1.5.0` with `refresh-model-catalogs.mjs`. Upstream now drops realtime and image-only models from the chat catalog, and PiSharp follows it.
- **Telemetry** (phase 3). `PiSharp.Telemetry` ports pi-telemetry v1.5.0 as an experimental package (`PISHARP_TELEMETRY001`). Like upstream, it has no dependencies and ships only the no-op and in-memory adapters, so nothing exports or sends telemetry.
  - **Typed schemas.** C# has no literal or mapped types. A schema is therefore a serializable record (`TelemetrySchemaDefinition`) that serializes to upstream's JSON shape. `TelemetrySchema.Define`, `CreateTypedSpanStarter` and `CreateTypedMetrics` enforce it at run time. Where TypeScript fails to compile, PiSharp throws `ArgumentException` before anything is recorded, for:
    - a span or instrument name the schema doesn't declare, or the wrong instrument kind;
    - a missing required attribute or an undeclared one;
    - a value of the wrong type or outside a closed set.

    Only upstream's check on union-valued names has no C# counterpart.
  - **Opt-in tracing.** `ChatRun` records `pi.ai.request` only when `ChatRequest.Telemetry` is set. The CLI and the coding agent set none, as upstream's coding agent passes none. Transports that a host calls directly, without a `ChatRun`, are not traced.
  - **Redaction beyond upstream.** Error messages have credential-shaped text redacted before the 500-character cap, under the standing rule that secrets never reach logs. `response.id`, which upstream records raw, is redacted and capped the same way.
  - **`pi.ai.poll`** is built and tested. PiSharp's deferred polls live in PiSharp.Durable, so phase 4's `durable.telemetry` row wired it in: `NativeDurableModels` records it for a deferred poll. Decision 0005 §4 allows PiSharp.Durable to reference only Contracts and AI. Durable already reaches PiSharp.Telemetry through PiSharp.AI, so phase 4 uses that and adds no reference.
  - **The renamed option.** `CompletionsSimpleOptions.TelemetryContext` (opaque JSON) becomes the typed `Telemetry` span, with no alias, as upstream renamed `telemetryContext`. Callers that set it must change.
- **Durable** (phase 4).
  - **The work list.** [`durable-sync-1.5.0-worklist.json`](../../compatibility/durable-sync-1.5.0-worklist.json) splits the re-sync into 48 areas in 27 waves. The areas in a wave run in parallel and touch disjoint files. [`check-worklist.mjs`](../../tools/DurablePortMap/check-worklist.mjs) checks:
    - that every changed upstream file and every phase 4 row is placed once;
    - that each wave's areas are disjoint.

    The port map follows v1.5.0 (`DurableUpstream.Commit`). The close-out area moved the Durable suite's report label to v1.5.0. Its compat captures stay v1.2.0's, as the Fixtures point says.
  - **`watchEvents`.** PiSharp.Durable drops `watchEvents`, as upstream does. PiSharp.Durable.Hosting keeps a PiSharp-only event projection built on the v1.5.0 view and observers. The device wire (decision 0008) therefore stays at v1, and the web hub (0010), the web agent (0011) and `pisharp durable attach` keep their frames. Moving them to view state and `ConversationTranscript` instead would rewrite all four. A batch of events is one publication, that is one commit as memory adopts it, and batches are never folded together. Past 100 undelivered batches, one snapshot of the newest view replaces them (decision 0008, Streams).
  - **Chord v2.** Phase 4 ports the parts durable needs, as the phase table says.
    - They go in a new `src/PiSharp.Chord` (`PISHARP_CHORD001`). It references PiSharp.Contracts and PiSharp.Telemetry, as upstream's chord depends on pi-telemetry, and no durable project.
    - PiSharp.Chord has its own copies of what Chord v1 types and PiSharp.Durable share:
      - `ChordContext`, beside Durable's `DurableContext`;
      - Chord v2's port of `watch.ts`, beside Durable's. Durable's depends on Durable types;
      - the subset of Chord's delta module that `watch.ts` and `derive.ts` import (ops, pending folds and `diffRevisions`), on `JsonNode`. A `JsonNode` cannot share subtrees between revisions, so these diffs are structural;
      - Chord's SQLite migration runner, beside PiSharp.Durable.Sqlite's. PiSharp.Chord declares the database surface its store uses. Its tests implement that surface over Microsoft.Data.Sqlite, and the adapter implements it over PiSharp.Durable.Sqlite.

      The adapter converts between them. Phase 6 decides whether the copies merge, which would need PiSharp.Durable to reference PiSharp.Chord.
    - PiSharp.Contracts makes its pi-schema internals visible to PiSharp.Chord, so Chord v2 can validate byte values. A public experimental API replaces that before PiSharp.Chord ships as a package.
    - The parts of `StoreStorage` and `registryReader` that need Chord v2 types go in a new adapter, `src/PiSharp.Durable.Store`, so PiSharp.Durable keeps decision 0005 §4. PiSharp ports `registryReader` against hand-built registry values: Chord v2's own registry records and writable sources, wired as the host's load does. Registries that a host builds wait for phase 6 (`createHost`), with upstream example 37.
    - Neither project is packed in 1.5.0. PiSharp.Chord reads PiSharp.Contracts' pi-schema internals, which need a public experimental API first, and the rest of Chord is phase 6. No packed project references either of them.
    - Upstream v2 tests that build objects through `createHost` (phase 6) run against hand-built values or wait for phase 6, and their evidence says which.
  - **Formats.** Upstream migrates v1.2.0 records when it opens them:
    - SQLite schema v1 to v2, rebuilding the tasks table for `sleeping`;
    - `pi.live` v1 to v2 to v3;
    - `pi.tool` v1 and v2 to v3;
    - `pi.generation` v1 to v2. A Harness older than 1.5.0 leaves a v2 task blocked.

    PiSharp follows. The SQL Server storage gets its own migration, which widens its tasks status check. See the no-rollback point above.
  - **Fixtures** are not recaptured.
    - The v1.2.0 corpus becomes migration input that v1.5.0 code must still open, with an `upgrade-from-v1.2.0` group beside `upgrade-from-v1.1.0`.
    - Records whose format changed are checked against expectations taken from upstream's v1.5.0 tests, labelled authored rather than captured.
    - Where formats changed (SQLite, telemetry, restarts, tool tasks, live turns, model requests and the store storage), PiSharp cannot show byte equality with upstream without a recapture. Those areas' evidence says so.
  - **Smaller points:**
    - PiSharp.Durable.Client keeps its own `Transcript.cs`; `ConversationTranscript` is ported in PiSharp.Durable for hosts.
    - Chord's `ProgressClock` (row `chord.output-progress-clock`, phase 6) lands early with Chord's output, because durable's host timers need it.
    - `DurableWire.DurableVersion` moves to 1.5.0 at close-out only if the device wire still matches durable-pi's. It stays "1.2.0": the device wire stays version 1 and keeps durable-pi v1.2.0's shapes (the `watchEvents` point), so a move belongs with a device wire version 2.
- **A requirement whose source upstream removed.** `surfaces.json` requirement `stream.indexed-events` named `assistant-message-frame.ts`, which v1.3.0 removed (upstream commit `b39979799`, "remove unused assistant-message frame API"). It now names `packages/ai/src/types.ts`, where v1.5.0 defines the indexed events. Its status stays `Deferred`.
