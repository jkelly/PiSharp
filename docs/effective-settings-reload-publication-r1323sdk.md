# Typed effective settings at acknowledged reload publication

This CLI bridge consumes the actual immutable `StartupSettingsSnapshot` supplied by the existing merge engine. It does not read files, inspect `NativeHostReloadPayload.State`, project a retry-only subset, or fabricate settings. Task7 owns callers/read facets; this leaf alone defines `ConfigureEffectiveSettings(StartupSettingsSnapshot?)`, `CaptureStartupEffectiveSettings()`, and `CaptureEffectiveSettings(AgentSessionAttachment)`.

The existing payload constructor remains supported. The additive constructor accepts an explicit typed snapshot. During real profile runtime staging the bridge preallocates an attachment-keyed settings slot and captures the exact candidate view, predecessor, generation and supplied snapshot. During the existing session publication transaction it validates the staged slot and single-use commit before invoking the original registry commit once. If that callback throws there is no candidate settings publication. If it returns the only subsequent action is a nonthrowing volatile state write. The actual owner then switches its current attachment. Before that switch readers of the old attachment still see the old snapshot; afterward stale or equal-generation foreign attachments are refused.

Every navigation attachment receives its own slot and inherits its snapshot from the weak exact-view acknowledged capture. That capture survives retirement of a predecessor attachment, which occurs before actual navigation binds its successor; it cannot confer access on the removed attachment. It is allocated during staging and acknowledged by the same nonthrowing commit state write. Retiring that attachment removes only its exact slot. A subsequent lifecycle or cleanup error does not undo a registry commit that already published. Pre-publication failure after engine invalidation does not revive the old view.

When the host omits `Settings` from the reload payload, the new generation inherits the prior acknowledged snapshot. Its slot records `SuppliedByReload=false`. That path makes no claim that files were reloaded or that newly merged settings were supplied. A null startup capture similarly means no typed settings admission; Task7's original no-layer behavior must use the actual merge engine before calling this bridge.

Six source-authored controls run the actual profile/session/reload path: held preparation and held start visibility, failed registry commit, failed staging, post-commit start failure, omitted typed payload plus foreign same-generation refusal, and actual same-file NavigateTreeAsync selection plus actual owner new-session replacement after successful reload. The latter verifies the old runtime native resource original was joined (counter exactly one) before the post-binding read and old attachment remains refused. NavigateTreeAsync itself preserves the attachment and does not perform resource retirement; it is not relabeled as that replacement route. The controls export cached actual Task/aggregate/direct references and join actual reload/profile close in finally. They are unexecuted and are not added to shared Program. Independent source/API review, source composition with Task7 getters, and separately admitted runtime qualification remain required. No Core, Agent, session, terminal or shared runner source is changed.
