The generation algorithm is authored input construction, not source output. It converts positive finite binary64 bit patterns to exact integer fractions, writes exact decimal expansions with `BigInt`, and independently finds nearest/even decimal-power centers by exact rational comparison and bounded bit-pattern binary search. Midpoints are exact rational averages; the below/above inputs differ by a smaller exact rational increment. It uses no floating parser/formatter or `JSON.parse` to author numeric values. Packaging the authored fixture with `JSON.stringify` does not compute any expected projected string. Outputs come solely from separately executed built-in parse/stringify calls.

Case IDs `previous`/`next` refer to the positive bit-pattern center; the negative cases are sign mirrors, rather than a renamed ascending order of negative values. The decimal power that rounds to positive zero uses negative minimum subnormal as its previous mathematical neighbor. Duplicate raw values are deliberately retained when they arise under different boundaries/families; no random sample or de-duplication substitutes for the declared coverage. This covers every exponent in the two declared power ranges, not every possible binary64 bit pattern or every valid/malformed JSON grammar input.

Input schema is `cases: [{ caseId, json }]`, where `json` is the original **raw JSON text as a string**. Expected schema is `cases: [{ caseId, json, serialized }]`, where `serialized` is exactly `JSON.stringify(JSON.parse(json))`. Compare the complete serialized strings ordinally; never reparse projected outputs for deep/numeric equality or reorder keys. Raw input lexemes, duplicate keys, escapes, whitespace and opaque/native-looking fields remain present in `json`. Lone-surrogate inputs use escaped inner JSON so the outer fixture stays well-formed UTF-8 and can be read by the ordinary native fixture loader. Genuine source serialization can still return a lone-surrogate escape, literal U+2028/U+2029 or supplementary text.

Top-level `numericSemantics: [{ caseId, binary64Hex, negativeZero, nonFinite }]` are observed using `DataView` on each parsed scalar number before serialization. They retain the actual binary64 bits, runtime negative-zero state and `Infinity`/`-Infinity` spelling; ordinary JSON serialization alone turns those into `0`/`null`. These sidecars are genuine runtime observations, not expected bits inferred by the authoring algorithm. A `__proto__` duplicate-key control confirms an own inert data property without prototype mutation. No JSON data restores a CLR type, delegate, extension or authority.
