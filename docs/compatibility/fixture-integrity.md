The frozen corpus through `c42b1e7efd32cd24846edba4eebd67298ca549f9` has ten manifests and sixteen fixture groups. These are integrity units: several groups contain multiple internal cases. The standalone `responses-sdk/manifest.json` contributes one group under its existing schema; the checker does not rewrite it as a grouped manifest.

The checker retains the existing immutable baseline, inventory/parity reconciliation, exact development Node pin, 99 canonical Git blob/checkout byte checks, clean checkout/tag/tree checks and canonical source archive reproduction. Recursive discovery adds fixture-group validation without executing reference captures or native scenarios. A successful report still says `fullNativeParity: blocked`, `phase1Gate: open`, and reports all 45 mandatory Deferred requirements.

## Raw value handling and confinement

The accepted `canonicalRawJson` parser validates payload JSON and preserves numeric lexemes, array order, missing versus null, exact strings and escaped lone surrogate code units. Expected corpus values remain raw JSON slices and are not round-tripped through JavaScript numbers or `JSON.stringify`. Selected identities, categories, counts, headers and provenance/lock metadata use the restricted `parseJsonSupported` runtime parser. SDK request-body strings are decoded only to hash their UTF-8 bytes and compare their embedded JSON through the raw parser. Object-key order is the sole raw JSON comparison normalization; raw body strings and retained capture bytes stay exact.

Evidence references are checked both lexically and through `realpath` before reads. Recursive fixture discovery rejects symbolic links rather than following them into external trees or cycles. The integration suite requires no privileged symlink setup; adversarial Windows symlink creation was not tested. This is validation of trusted, stable repository evidence, not an OS sandbox or protection against hostile concurrent repository rewrites.

SHA-256 binds bytes to the declared manifest digest. A reviewed capture/golden remains a separate trust input: editing payload bytes and their declared digest can satisfy integrity checks, while reference comparison or review may reject the changed behavior. The checker does not claim that a valid self-declared checksum proves an upstream execution occurred.

```powershell

node --test tools/CompatibilityReport/check.integration.test.mjs tools/CompatibilityReport/comparator.test.mjs tools/CompatibilityReport/integration.test.mjs

The separately qualified continuation baseline at `1ea8c03` passed 546 checks across seven manifests/thirteen groups and twenty tooling tests. This extension defines 67 checker integration cases (64 negative mutations and three positive controls), alongside the five existing comparator/CLI tests. Every mutation uses a fresh task-local repository copy. The original byte/digest/path/identity/normalizer/requirement/kind/duplicate-property/numeric-lexeme controls remain. New controls cover finish-decision lock/harness/raw evidence; tool provenance, source/runtime/runner pins, retained pairs, cross-hashes, schema and derived counts; and SDK lock/source/dependency/module/harness identities, retained golden history, raw bodies/headers and zero/negative observations. Several controls refresh all related declared hashes so schema and cross-field checks are exercised independently of simple byte tampering. Positive cases retain legacy root-only compatibility and wide numeric/lone-surrogate handling.

Temporary copies are removed with native Node filesystem calls only after checking their resolved target remains within the dedicated task temporary root. Actual manifests, expected files, capture locks, native source and the baseline/parity classifications are unchanged. None of these checks replaces reference re-execution, native differential tests, required platform coverage or a phase exit gate.
