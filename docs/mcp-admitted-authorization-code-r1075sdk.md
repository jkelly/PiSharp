# Admitted authorization-code and PKCE flow, source-only

This additive leaf on aceb232 preserves reviewed discovery/refresh6994. It implements the pinned Pi0.99.1 `packages/mcp/src/oauth/flow.ts` **startAuthorization** and **exchangeAuthorizationCode** with an already admitted client and discovery metadata. It is not a complete `authorizeMcp`, new credential authority or default application integration.

`McpAdmittedAuthorizationCodeFlow` requires exactly one explicit callback for each 32-byte entropy source, verifier save/read, redirect delivery, HTTP code exchange and token save. No callback has a default; no random, browser, network, client registration, storage, process or credential acquisition occurs in this leaf. Requests are proposals to the admitted exchange owner, who must independently admit every endpoint. State verification, redirect receipt/code admission, and provider/client lifetime remain the caller's responsibility. Synthetic fixture values are not real credentials.

Begin derives 43-character base64url verifier from32 supplied bytes and S256 challenge, constructs original code/client/redirect/state/scope/resource query values and offline_access consent, rejects unsupported code/S256 before effects, joins verifier-save before redirect, and fences late cancellation/close before each new effect. Complete joins verifier-read, sends original authorization_code form with Basic/Post/none selection, checks OAuth error body before HTTP status, applies original finite Number coercion and nonempty optional strings, then joins token-save. All dependency ValueTasks are captured/materialized once through existing `McpOAuthAdmittedWork`; full Task.Exception and direct references remain in its original carriers, including Faulted-OCE versus actual canceled identity. There is no refresh-grant fallback in this code exchange.

The native bounded profile admits HTTP(S) server/redirect/endpoints, requires HTTPS or loopback for token exchange, permits finite UTF8 profile/request/response limits, and serializes one operation per owner. Start is scheduled as one owned Task with both logical and physical ancestry captured before scheduling; actual dependency invocation uses a synchronous physical frame, while a shared active logical frame survives awaits and is deactivated on settlement. Close captures both ancestors, retires admission before scheduling, owns the actual cancellation Task, joins the active operation even if cancellation faults, and retains cancellation/active/cleanup original evidence. A genuinely canceled active original can make close Canceled with an explicit original carrier; other failures preserve full graph in a Faulted wrapper/aggregate. Close never replaces a returned operation with timeout/detached work. Verifier/token writes already committed by the admitted callback are not rolled back by later cancellation.

Dependency owners that cancel sources after awaits and may synchronously invoke normal Register callbacks must route that cancellation through its Cancel/CancelAsync methods and directly join the returned actual Task before the dependency returns. It grants no source/client ownership, and canceled callback siblings/faulted OCE are not normalized or dropped. Direct synchronous callback entry is also physically guarded. Own/nested ancestor joins are refused before effects; completed captured frames are inactive.
