The root must compile and execute each corrected candidate in its fresh isolated evidence directory before claiming that correction passed. The four groups exercise actual `WindowsConsoleTerminal` and `VtRenderer` calls in a private hidden ConPTY child, with independent Win32 screen/cursor inspection and actual ConPTY output capture. They do not replace physical output with a virtual sink or infer a write, resize, exit or cleanup from elapsed time.

The root's first focused execution, preserved in `artifacts/renderer-conpty-focused-first.json` and `.log`, compiled with zero warnings/errors and reported three groups passed and `parent-abort` failed with `Owned renderer process termination failed.` The abort's actual parent witness nevertheless recorded native wait result zero, child exit code 3, actual nonce output observed, and joined ConPTY close/output drain. Partial-launch children not yet assigned to that job still receive direct termination; a failed job request remains a failure even if fallback process termination settles. Every route retains the owned process handle and awaits actual native exit, ConPTY close and physical drain. This correction has not been executed by the source author and requires a fresh root-owned run.

The source fixtures are read-only references: `WindowsConPtyFixture.cs` provides the already qualified private-console acquisition, native launch/containment pattern, exact mode/codepage/cursor restoration and physical process-handle ownership; `VtRenderer.cs` and the renderer contract specify awaited cache commits, changed-row output and explicit host invalidation. Their private helpers cannot be reused without editing frozen files. The new fixture therefore owns a separate bounded launcher/worker and native bindings; it does not use reflection to access the older fixture or modify shared production code.

The parent creates a 24-column × 6-row ConPTY, owns both transport pipe ends and its kill-on-close containment job, and launches the explicit host/DLL with `CreateProcessW`. The process starts suspended, is assigned to the owned job, then resumes. Startup uses `STARTF_USESHOWWINDOW` and `SW_HIDE`, no inherited handles, and the ConPTY process attribute. It introduces no visible window, standard-handle replacement, console attachment/detachment, global Console input/output route, codepage change or system-setting change.

The child opens `CONIN$` and `CONOUT$` for that attached private console and requires actual character-device APIs. It independently reads its native viewport, modes, code pages and cursor, stamps cursor size/visibility/position, and acquires the production borrowed-handle lease. The parent sends an unpredictable eight-character ASCII nonce only after acquisition readiness; the worker completely consumes it through real terminal input. Every rendered viewport retains `LINK:<nonce>` at row zero. The parent must independently observe that nonce in actual ConPTY output. A handle to an unrelated console cannot satisfy both input and output witnesses. Inherited standard aliases are observed and required unchanged, but this fixture does not qualify genuine standard-handle `OpenAsync` or redirected-output behavior.

After each awaited real renderer operation, the child checks its native viewport through `GetConsoleScreenBufferInfo`, reads complete cells with `ReadConsoleOutputW`, and checks cursor position/visibility through `GetConsoleScreenBufferInfo` and `GetConsoleCursorInfo`. Expected ASCII rows are authored separately from renderer frame rows. A clipped native read, unavailable API, different geometry, altered cursor or incorrect cells fails the witness with its actual failure. The scope requires a native viewport at origin; buffer geometry is recorded without claiming general scrollback behavior. There is no synthetic screen fallback.

The resize command is acknowledged over the separate control pipe only after the parent native call returns success. The child then requires the exact requested native viewport; a different observation fails, without sleeps, retries, Task.Yield or timeout-as-success. This qualifies explicit host-driven resize notification only. The current `IConsoleTerminal` has no geometry or automatic resize-event contract; a production interactive host remains mandatory work.

The real console host reserializes its screen into ConPTY VT output. Captured bytes therefore are retained as evidence, with actual nonce/CSI checks, and are not compared to the renderer's encoded full/diff byte goldens. Native cells/cursor are the screen witness. This does not establish pixel rendering, a general VT emulator, synchronized-update capability, Unicode glyph presentation or real output-backpressure cancellation.

All fixture width decisions are explicit ASCII one-cell decisions. Layout handles the authored control/newline/tab input through its normal sanitizer. The maximum native witness is 32 × 8 cells (256), with normal scenarios 24 × 6 or 16 × 4. Control reads allocate at most 8,192 characters per receipt; the parent receives at most ten scenario packets after readiness. Actual output retention is capped at 65,536 bytes while the dedicated physical drain continues. Exceeding that retention cap fails qualification rather than pretending the retained prefix is complete. Normal and final failure reporting are bounded. The root owns fresh report paths and artifact persistence; the fixture itself creates no evidence files.

Normal completion requires independent original-versus-restored native state equality, zero active native reads/writes, matched started/settled worker counts, unchanged standard aliases, reacquisition through surviving original explicit handles and actual process exit code zero. A renderer owns no borrowed lease. Parent cancellation, failure and deliberate abort close admission by leaving the scenario, request termination through owned job/process handles, and join the actual process wait before releasing the handles. Partial-launch failure also joins any created child and retains its cleanup evidence. The owned ConPTY close operation and synchronous output-drain worker are awaited to actual completion; no timeout wrapper invents physical cleanup. If a native termination/close cannot settle, work remains retained and the root's contained process watchdog is required. Such a run cannot qualify cleanup.
