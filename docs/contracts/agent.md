# Native Agent and tool scheduling

Status: an in-memory native `Agent` composes the bounded loop, single-turn provider lifecycle, tool scheduler and pending-input queue. The scheduler remains independently usable with an already finalized `AssistantMessage`. This document describes implementation boundaries, not Phase 3 gate closure or full high-level Pi qualification.

The reference is Pi v0.99.1 at immutable commit `d86654abb8862e201933517d6f1fce9f88dd117f`. The pinned [agent README](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/README.md) documents awaited assistant processing, sequential preflight, execution modes, independent completion events and source-ordered transcript results. The implementation is in [agent-loop.ts](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts#L508-L738). The high-level barrier is described by the README; the low-level observational stream has a different completion contract.

## Native boundary

`ToolBatchScheduler.RunAsync(message, sink, cancellationToken)` rejects pending/deferred messages and uninitialized content. Error/aborted assistants then emit and await `AssistantMessageEnded` and return an empty tool batch. Their owned partial calls are nonexecutable history and may retain blank or duplicate provisional identities. Other finalized assistants retain unique, nonempty call ID/name and nonnull argument admission before this event. The caller can commit the assistant through this sink. The scheduler has no authoritative session store of its own. Before hooks and executors cannot begin until this barrier settles. The remaining native events are `ToolExecutionStarted`, `ToolExecutionEnded`, `ToolResultMessageStarted` and `ToolResultMessageEnded`.

The scheduler awaits every sink call. One run never overlaps sink calls, including parallel tool completion observations. Completion of `RunAsync` includes the last transcript-message sink call. A sink is an asynchronous barrier. The standalone scheduler supplies no subscriber registry or run-end API; the high-level `Agent` below owns ordered subscriptions and exclusive run settlement. Independent standalone scheduler runs sharing a sink need caller coordination.

Tools and hooks run without a coordinator lock. Definitions are copied into an immutable registry at construction. Inputs use owned immutable JSON and immutable assistant content from `PiSharp.Contracts`; results use immutable arrays and JSON. `ToolInvocation.SourceIndex` retains the original assistant content index, including preceding text/thinking blocks. Native types are deliberately separate from Pi wire serialization.

## Scheduling behavior

| Phase | Parallel default | Sequential batch |
| --- | --- | --- |
| Admission | Reject unfinished envelopes; reject malformed executable identity before events or tool effects; preserve failed/aborted provisional history | Same |
| Assistant barrier | Await `AssistantMessageEnded` | Same |
| Per-call preflight | In assistant order; all allowed calls are prepared before execution | Preflight immediately before that call executes |
| Immediate errors/blocks | Emit completion during preflight | Emit completion before moving to next call |
| Allowed execution | Run concurrently; finalize result hooks independently | Finish each call and its transcript events before the next |
| Completion observations | Emit in observed finalization order | Source order |
| Transcript messages/outcomes | Source order after all admitted executions settle | Source order, interleaved with execution |

An explicit global sequential mode or any targeted definition with sequential mode serializes the entire batch, even if that tool is later blocked. The reference branches at [agent-loop.ts:508-649](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts#L508-L649). Finalization order means executor completion plus awaited result-hook completion; a slow result hook delays that call's final observation. The internal completion queue receives at most one item per prepared call. There is no configured maximum batch size or overall memory/resource cap in this prototype.

`ToolBatchResult.Terminate` is true only for a nonempty batch whose every finalized outcome requests termination. `ShouldContinue` is true only for a nonempty, noncanceled batch that does not unanimously terminate. This is a scheduling hint; this slice does not make another provider request. The reference unanimity rule is [agent-loop.ts:679-681](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts#L679-L681).

## Cancellation and failure

Cancellation is checked before preflight and again before admitting an executor. Cancellation during parallel preflight ends further admission; previously prepared calls receive canceled outcomes without execution, while untouched later calls have no outcome. The batch is source ordered over admitted calls. Cancellation before admission returns a canceled empty batch after the assistant barrier if the sink accepts that event. Cancellation is propagated to hooks and executors; already started tools are awaited to settlement and successful completed outcomes remain successful. `IsCanceled` prevents automatic continuation.

Sink exceptions are authoritative delivery failures, not tool errors. A sink may honor its cancellation token by throwing; in that case the task faults/cancels instead of returning the batch cancellation envelope. During parallel execution a sink failure cancels the local executor lifetime and awaits all admitted executions before surfacing the failure. A cancellation-callback failure is retained alongside the sink error. No retry occurs. A noncooperative tool can indefinitely delay this cleanup; this slice has no hard timeout, process kill, rollback, or side-effect recovery. Cancellation does not prove a completed action was undone.

Tools are not executed from error or aborted assistants. These assistants pass the usual awaited commit barrier without tool preparation, argument schema validation, authorization, hooks or execution. Their owned body reaches the sink unchanged, including incomplete identities; settlement grants no executable tool authority. A sink failure still propagates as an authoritative delivery failure, and a sink that honors an already canceled delivery token can still cancel the task. If delivery succeeds, an aborted assistant or canceled token returns an empty canceled batch; an ordinary error returns an empty noncanceled batch. Wire and durable-session body admission remain their own boundaries.

Output-length-truncated assistants retain the existing identity/argument admission and produce one synthetic truncated error per admitted tool call without execution. Pending/deferred native messages are rejected. These guards follow [agent-loop.ts:245-270](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts#L245-L270) and the truncated-error path around lines 470-502. Unique/nonnull executable call identity validation remains native admission hardening; wider provider interoperability remains deferred. Failed-terminal settlement implements the existing [turn contract](turn-runner.md) that partial calls in a failed snapshot remain history and execute no tools. This native lifecycle rule does not claim a qualified source-error trace comparison.

## Stateful native Agent

`Agent` owns an in-memory canonical transcript, two pending queues and at most one active generation. Its constructor borrows an explicit `AgentConfiguration`, clock and primary `IAgentEventSink`. Configuration supplies a model, injected `IChatTransport`, immutable tool definitions, scheduler hooks/execution mode and loop preparation/finish callbacks. A generation uses a captured configuration and calls `AgentLoopRunner.RunWithContextAsync` over the complete prior history plus newly selected input. Historical finalized assistants and text tool results are retained exactly and are never scheduled as new actions.

`PromptAsync` admits a typed system/user entry or immutable array; it appends to the existing conversation. Busy prompt/continue calls throw synchronously and do not silently enqueue their arguments. `Configure` and `ReplaceMessages` also reject while busy. Idle replacement preserves the supplied owned raw bodies; the loop applies its stronger finalized-assistant/tool-result grammar before running. This native API does not expose Pi's mutable `state` object or its string/image prompt overloads. A model/tool configuration change affects the next generation; it cannot modify the active one. Tool declarations, system prompt synthesis, transformed contexts and turn-local model/loadout updates still need their own qualified integration.

`ContinueAsync` rejects empty or system-only history. A user/tool-result tail continues directly without replaying old input events. An assistant tail requires queued input: steering wins over follow-up, and the chosen queue's mode selects one entry or its entire ordered prefix. Selecting steering suppresses the loop's first steering poll so one-at-a-time continuation does not drain a second entry before the first request. If no eligible input exists, admission fails without consuming queues. `Steer`, `FollowUp` and queue-mode changes are safe during a run; the accepted loop polls their separate FIFOs at its documented boundaries. `PeekQueuedMessages` uses the steering-first selected prefix, and `ClearQueues` explicitly clears queued entries only.

The baseline for these source-linked rules is the pinned [high-level agent](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent.ts), including `PendingMessageQueue`, prompt/continue admission, `processEvents` and `finishRun`. Native tests exercise these choices; this slice does not compare a complete high-level trace against an unchanged upstream Agent.

## Snapshots, commits and recovery

`Snapshot` is an immutable point-in-time value. It reports generation, configured model/tools, canonical messages, normalized latest stream observation, completed tool outcomes, uncommitted selected inputs, separate queue counts, running/disposed flags and a fixed failure classification. Owned `JsonData`, content and arrays retain their values after later generations. Borrowed transports, executors and delegate implementations remain trusted references; immutable configuration does not make their internal code immutable or confined.

An input, assistant or tool-result message is committed when its respective ended event reaches the Agent. The Agent updates state before forwarding that event to awaited sinks. Completed tool outcomes are likewise retained before delivering their completion observation. A later listener or finish callback failure cannot erase those commits. A failed run throws its original exception, while the snapshot uses `RunFault`, `Canceled` or `ChatFailure`; it does not copy arbitrary exception messages into a state diagnostic. Callback failures can leave a canonical prefix containing an assistant or some successful tool results. This is an honest record of received commits, not automatic reconciliation, retry or side-effect rollback.

Selected input belongs to the active run until its input-ended commit. Initial prompt inputs, drained queue entries and prepared next-turn inputs that never commit remain in `PendingInputs` after cancellation, fault or a loop limit. This retained recovery list is separate from still-queued input. Another prompt/continue is rejected while that list is nonempty; idle `TakePendingInputs` transfers it explicitly to the caller, who can inspect or re-admit it. `ClearQueues` and history replacement do not silently discard this recovery list. Persisted session settlement and recovery policy remain separate work.

Default limits are 16 turns, 1,024 canonical entries, 128 tool definitions, 128 subscription leases and stream capacity 32, plus the pending queue's separately documented character/depth/count limits. These bound logical entries and queue admission. They are not a total heap cap; prompt/history raw bodies and trusted callback allocations have no new global byte budget in this slice.

## Awaited subscriptions and settlement

The primary sink runs first. `Subscribe(IAgentEventSink)` adds an independent ordered awaited subscription and returns an idempotent `IDisposable` lease. Each event takes an immutable snapshot of the current registrations after reducing Agent state. Listeners run serially outside the state lock. A lease disposed during delivery removes later events, while delivery already captured for this event finishes. Registrations added during an event begin with the next event. These explicit concurrent native semantics do not claim equivalence with every mutation case of JavaScript's live `Set` iterator. Duplicate subscriptions are independent leases.

The default SettleAborted profile gives authoritative listeners an uncanceled settlement token so durable commits complete after work cancellation; providers, tools and finish callbacks retain the actual work token. Explicit Propagate keeps the prior active-token listener contract. Awaited end listeners belong to run completion and WaitForIdleAsync. Listener faults propagate after owned cleanup. Canceling an idle waiter's token affects only that wait.

`Abort` requests cooperative cancellation of the currently active generation and is harmless when idle. Cancellation requested and cleanup completed remain distinct: `IsRunning` stays true during provider/tool disposal and awaited listeners. Cancellation callbacks run outside the state lock; callback exceptions set `CancellationCallbackFailed` and do not skip owned cleanup. Concurrent abort calls cannot dispose a cancellation source still in use by another cancellation call. `DisposeAsync` closes admission, requests abort, awaits the same run settlement and releases subscription registrations. Concurrent disposals share one task. The Agent does not dispose borrowed transports, sinks or tool executors.

Callbacks in the active execution context cannot call `WaitForIdleAsync` or `DisposeAsync` to await their own run; those calls throw synchronously. Snapshot reads, queue operations and abort remain reentrant. The guard also covers work inheriting that execution context and synchronous cancellation callbacks. It cannot turn arbitrary trusted code into a sandbox or stop a tool/listener that ignores cancellation indefinitely. No state lock is held while invoking the clock, providers, hooks, tools, listeners or cancellation callbacks.

## High-level evidence and remaining qualification

`AgentTests.Cases()` supplies nine offline gate-controlled groups: actual tool continuation followed by another prompt with exact history; busy/configuration admission; three-turn steering/follow-up delivery; eligible continuation with one-at-a-time steering; cancellation and shared delayed cleanup with throwing cancellation callbacks; commits surviving listener/finish faults; recovery of polled input after a limit; end-listener settlement/self-wait rejection; and subscription order/removal with tool execution blocked behind every assistant listener. The suite uses injected deterministic providers and fake executors, with no network or tool I/O. Registration and successful execution must be reported by the native test receipt for the immutable candidate; source existence alone is not a passing result.

The separate [abort-settlement profile](abort-settlement.md) connects actual canceled work with committed aborted assistant/turn/end delivery. Its genuine case-seven comparison uses no thinking-level or signal exemption and includes partial-stream cleanup controls. Normally delivered cancellation returns ChatFailure and Canceled state instead of throwing solely due to work cancellation; CancellationRequested retains the token fact. Low-level defaults stay unchanged. Complete fault fallback and other phase-specific abort traces remain open. Wider content/custom messages, mutable Pi state, tool-loadout/context transformation, provider options, correlation, persistence and platform qualification remain required scope.
