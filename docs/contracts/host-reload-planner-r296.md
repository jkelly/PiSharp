# Host reload payload planner R296

Source-only leaf from native commit `6170379555cc9d817cdf3a360857a319ab8ba31b`, tree `8405c976f4ded93746e6ff88532e26d6a4ce0cfc`. Oracle: original Pi v0.99.1 commit `d86654abb8862e201933517d6f1fce9f88dd117f`, `packages/coding-agent/src/core/agent-session.ts`.

`HostReloadPlanner<TPayload>` composes the existing `ResourceReloadWorkflow<HostReloadGeneration<TPayload>>`. It adds concrete candidate payload preparation, runtime metadata capture, flag and tool planning, exact generation acknowledgement checks and lifecycle callback composition. It does not register a second workflow or publish a separate registry.

Original reload lines 3575–3604 capture previous flag values, emit `session_shutdown` with reason `reload`, invalidate the old runner, reload settings, sync queue modes, reset API providers, reload resources and build runtime using previous active tools and `includeAllExtensionTools: true`. When bindings exist, beforeSessionStart precedes `session_start` with reason `reload`, unhandled MCP reporting and extension resource additions.

The adapter deliberately prepares an unexposed candidate before shutdown/invalidation, preserving the existing native workflow's old authority on stage failure. This differs from upstream's in-place sequence after invalidation. Its preparation callbacks run settings → queue modes → provider reset → resource reload → metadata capture → runtime build. Those effects must stay within the candidate payload; `ResetApiProvidersAsync` must never reset the currently published global provider state during staging. The admitted host operations may close over the exact `ResourceReloadPlan` passed to the planner; this leaf does not rediscover its approved catalogs or load resources itself.

Flags overlay all old boolean/string values on new defaults, including false, empty strings and values whose declarations disappeared (`_buildRuntime` lines 3546–3549). Runtime metadata represents direct/model-only/hidden/codemode/deferred exposure and defaultActive. Previous active names survive only while registered, declarable and permitted. Without an allowlist, declarable default-active extension tools are added. With an explicit allowlist (including an empty one), named declarable registry tools activate even when defaultActive is false. Exclusions win in both cases. Newly registered base tools do not activate by default during reload. Selection follows `_refreshToolRegistry` lines 3410–3438 and 3484–3507, `_isDeclarable`/`_isActivatedOnRegistration` lines 3510–3518, and `setActiveToolsByName` lines 1473–1480. The host must supply final deduplicated registry metadata after applying extension overrides, SDK custom tools and namespace policy; this planner does not reconstruct those registries.

Shutdown receives the old generation and reason `reload`. The host's invalidation/drain operation runs before publication. A publication acknowledgement must name the exact expected and candidate IDs. A mismatched or malformed receipt makes authority unknown, preserves the candidate for host recovery and cannot restart the old context. A valid rejection names both IDs, authority None and the original error. Old retirement completes before startup. Startup runs only for a captured host with bindings and only after failure-free New publication and retirement. Staging cleanup joins before returning failure; stage and cleanup faults retain both original exception objects. Other authority, joined-operation, cleanup and failure rules remain those of `ResourceReloadWorkflow`.

The host owns mandatory seams: session/reload reservation through the returned original task; old runner invalidation and drain of actual admitted callbacks/reporters; discovery/admission and candidate preparation; one atomic registry/session publication with a compare on expected generation; old resource retirement; and concrete startup hooks. Numeric receipt checks do not implement atomic publication or stale-context rejection. Candidate payload references are opaque; their immutability and confinement require the host implementation.

Ten meaningful source test cases in `HostReloadPlannerTests.Cases()` cover captured metadata, tool rules, lifecycle order, absent bindings, held stage rollback, original stage/cleanup faults, held publication and cancellation, stale receipt authority, held retirement failure, startup short-circuiting, explicit publication rejection and candidate identity validation. Shared `Program.cs` remains coordinator-owned: the cases must be registered there before any future approved test execution. No native build, tests, Node, process activation, network, credentials or trust changes were performed. This artifact establishes source implementation only; host integration and exact-producer runtime qualification remain open.
