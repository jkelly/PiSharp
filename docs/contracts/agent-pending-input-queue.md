# Pending steering and follow-up inputs

`AgentPendingInputQueue` is a standalone bounded store for canonical immutable `TranscriptEntry` input values. It owns independent steering and follow-up FIFOs with independent mutable drain modes. Both default to `OneAtATime`; `All` selects the entire current queue in source order. Changing a mode changes the next peek/drain, without rewriting or consuming entries.

The source-linked behavior comes from public Pi v0.99.1 [PendingMessageQueue and Agent queue methods](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent.ts) and [QueueMode](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/types.ts). Upstream pushes entries, peeks the first entry or a copied array, drains exactly that selected prefix, and clears a queue. Its high-level combined peek chooses steering before follow-up. These facts define this small native primitive; no unchanged upstream queue execution or high-level Agent parity is claimed.

`EnqueueSteering` and `EnqueueFollowUp` admit one entry or throw. `PeekSteering`/`PeekFollowUp` return immutable, non-consuming selected prefixes. `DrainSteering`/`DrainFollowUp` remove exactly the returned prefix. `PeekQueuedMessages` prioritizes the selected steering prefix when steering is nonempty, otherwise the follow-up prefix. Counts and `HasQueuedMessages` are observations at their individual lock boundaries. A sequence of separate property reads is not a combined atomic snapshot. `ClearSteering`, `ClearFollowUp`, and `ClearAll` explicitly discard pending inputs; clearing both stores is atomic.

Internal storage uses immutable FIFOs. A single private lock serializes short state transitions and observations, including mode changes. Validation runs outside that lock and checks cancellation again inside it before admission. Selection builds its immutable result before committing removal, with cancellation checks while selecting and immediately before consumption. No user callback, provider I/O, cancellation callback, or await runs while holding the lock. Concurrent producers are ordered by admitted lock operations; independently sequential entries from one producer retain order. No scheduling order between simultaneous producers is promised.

Accepted values are owned system/user bodies whose wire `role` matches `TranscriptEntry.Role`, matching the accepted low-level loop's input profile. The queue preserves the actual immutable entry/body values, including unknown fields, whitespace, exact numeric tokens, explicit null, arrays, and opaque strings. The immutable `JsonData` contract already severs a caller's `JsonDocument` lifetime. The queue does not convert provider messages, validate full user/system content schemas, execute tools, or reinterpret metadata. Other roles and custom inputs remain unsupported in this slice although upstream's queue accepts the broader `AgentMessage` type.

Native hardening limits apply separately to each store: maximum entry count and accumulated serialized wire-body UTF-16 characters. Per-message limits cover serialized wire-body characters and JSON container depth; the root object has depth one. Defaults are 256 entries per queue, 65,536 characters per message, 1,048,576 characters per queue, and depth 32. Logical body charging includes serialization whitespace and escapes. It does not count CLR headers, FIFO nodes, temporary raw-text strings, or duplicate immutable snapshots, and is not a total heap cap. Draining and clearing release queue character/count budgets. Neither store consumes the other's budget.

Invalid input or capacity/depth overflow produces a fixed sanitized `AgentPendingInputException` with `InvalidInput` or `ResourceLimit`. Invalid options or enum modes throw an argument exception containing fixed configuration text. Failed admission never changes either store, and the caller retains its rejected value. There is no automatic drop, overwrite, eviction, or hidden queueing on failure.

All explicit enqueue/peek/drain/clear operations accept cancellation. A token already cancelled at the admission/selection boundary raises `OperationCanceledException` and preserves pending state. Cancellation racing after the final check may follow a successful operation; it does not roll back that operation. A successful drain transfers responsibility for its returned inputs to the caller. There is no acknowledgment/lease protocol or automatic restoration if a consumer fails after receiving them.

`GetSteeringMessagesAsync(CancellationToken)` and `GetFollowUpMessagesAsync(CancellationToken)` return completed `ValueTask<ImmutableArray<TranscriptEntry>>` values and can be assigned directly to the corresponding `AgentLoopCallbacks`. They perform the same atomic drains and may throw synchronously on cancellation. The accepted loop decides when to poll and append inputs. In particular, cancellation after a callback has successfully drained messages is a caller/loop handoff concern, not a reservation that this queue can recover. This slice does not supply a high-level Agent, busy-prompt rejection, continue selection, active-run cancellation, run/session settlement, or lifecycle disposal.

Seven authored offline test groups cover one/all mode switching and immutable peeks, exact count/character/depth boundaries and budget reuse, invalid inputs/options with retained canonical bytes, concurrent source-ordered producers and exactly-once consumers, concurrent capacity rejection, gate-controlled cancellation, and direct callback composition with the accepted loop. The integration holds the first finished turn behind a task gate, queues two steering inputs and a follow-up, then verifies four requests and steering-before-follow-up transcript order. Tests use task gates and bounded harness timeouts, with no scheduling sleeps, provider/network effects, or golden rewrites. This is source-linked native behavior evidence and intentional hardening, not full P3 closure.
