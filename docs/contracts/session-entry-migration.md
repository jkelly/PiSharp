# Explicit pure legacy session migration

PiSharp.Sessions.Serialization.SessionEntryMigration implements the two known transforms in public Pi v0.99.1 at d86654abb8862e201933517d6f1fce9f88dd117f. It is a bounded, explicit conversion of owned JSON records, with source retention, per-field transformation receipts and sanitized blockers. It owns no filesystem, clock, random generator, callback, source rewrite, repair, import destination or extension authority. It is a portion of [P4-05](../plans/04-sessions.md); import/export workflows and G4 remain open.

The canonical implementation is [session-manager.ts](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/session-manager.ts), functions migrateV1ToV2, migrateV2ToV3 and migrateToCurrentVersion. The pinned [migration tests](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/test/session-manager/migration.test.ts) cover v1 tree identity and preservation of existing v2 identities. No unchanged upstream execution comparison is claimed by the authored native tests.

The public calls are:

    new SessionEntryMigration(options)
    Migrate(ImmutableArray<JsonData> records, ImmutableArray<string> v1EntryIds = default)
    MigrateArray(JsonData array, ImmutableArray<string> v1EntryIds = default)

The record sequence must begin with exactly one session header. A missing or explicit-null header version means v1, matching upstream's nullish default; integer-token versions 1, 2 and 3 are supported. Other Int64 versions produce UnsupportedVersion or FutureVersion blockers. Fractional/exponential integer spellings, nonnumbers and values outside Int64 produce InvalidVersion. This is the declared native integer-token profile, narrower than JavaScript number/coercion behavior. A future header is retained for inspection and receives no current-version records.

For v1, upstream assigns a new ID and previous-entry parent to every nonheader record in physical order, overwriting existing identity fields. This implementation performs that same assignment using one caller-supplied ID per nonheader record. Roots get explicit-null parentId; subsequent entries point to the immediately preceding new ID. Existing timestamps remain unchanged. IDs may be compatible nonempty strings rather than only eight hexadecimal characters. The plan requires ordinal uniqueness, valid paired Unicode and configured character bounds. No ID generator runs inside migration. Upstream's preferred generator uses the first eight hexadecimal characters of a random UUID and a full-UUID fallback; the native caller can allocate those outside this pure operation. The pinned v1 loop creates a collision-check set but does not add generated IDs to it. Rejecting collisions in an explicit native plan is declared hardening.

V1 compaction firstKeptEntryIndex addresses the complete file-entry array, including the header at index zero. A numeric index pointing to an earlier or current nonheader record becomes that record's assigned firstKeptEntryId, and firstKeptEntryIndex is deleted. The current-entry case follows upstream's assignment order. A header, negative, out-of-range, forward, fractional or non-Int64 numeric reference blocks the whole conversion. Upstream deletes numeric legacy indexes even when no valid target exists and can observe a forward entry's old ID before overwriting it later. This native profile refuses those ambiguous/lossy cases rather than guessing a boundary or silently deleting its only reference. A nonnumeric index is retained as opaque JSON, matching upstream; the record still must have a valid current firstKeptEntryId to complete. Other legacy references are not inferred or rewritten.

For v2, and after the v1 identity step, only message records with message.role exactly hookMessage change that role to custom. Header version becomes 3. Existing v2/v3 identity, parents, timestamps, content, usage, metadata and unrelated roles are retained. No customType, display, usage total/cost or other currently required fields are synthesized. A historical hook or assistant message missing fields required by the [current codec](session-entry-codec.md) produces CurrentRecordInvalid, with the original records retained and no partial successful result. This declares a limited strict-v3 migration profile rather than support for every permissively accepted historical Pi record.

Completed results contain:

- SourceVersion, VersionDefaulted, TargetVersion and WasMigrated.
- Owned SourceRecords and strict current Records, including the separate header.
- Receipts naming the record index, known JSON field path, transform, before/after presence and owned before/after JSON values.
- Nonblocking UnknownEntryRetained diagnostics for unknown entry types.

The final header-version receipt records the source value/presence and final v3 value; the internal v1-to-v2-to-v3 sequence is folded into one final version assignment. Identity overwrites, compaction reference replacement/index removal and nested hook-role replacement are individually receipted. Receipt JSON is caller data intended for explicit inspection. Diagnostics carry only fixed codes, record indexes, optional codec failure codes and fixed messages; they do not echo content, identifiers, paths or exception details.

Blocked results contain no current Records or successful Receipts. SourceRecords remain available, and MigrateArray retains its already-owned SourceArray even if its count/byte guard prevents materializing records. A result does not return a partial migrated prefix as a usable session. Source input JSON objects are immutable JsonData values, and strict reparsing severs document lifetime and rejects permissive caller comments/trailing commas. Unknown fields, nested opaque values, absent versus null and unmodified numeric/string value tokens survive conversion. Changed object property-name escaping/whitespace is not a byte-identical export guarantee. Original file bytes are outside this API; an importer must retain them and their hash separately.

Options default to 100,000 records, 16 MiB input and 16 MiB output, plus the codec's per-record character/UTF-8/depth limits. Migrate charges the sum of record JSON bytes; MigrateArray additionally charges its complete array syntax before splitting. Output charges the sum of current record JSON bytes, excluding any eventual JSONL newline or outer array framing. Exact limits are inclusive. Generic JSON validation rejects duplicate names and unsupported Unicode before known transforms, and every output record passes the strict current codec. Bounds do not represent a total heap cap; callers already own the input JSON and any source-array text.

V3 inputs pass through validation without migration receipts. Repeating migration over completed current records with no ID plan is stable. V2/v3 calls reject a supplied nonempty v1 plan to avoid silently ignoring authoring input. Header identity remains separate from tree IDs. Migration does not certify graph validity, known compaction semantic boundaries, finalized assistant state, writer admission, model-context projection or extension-state compatibility; those require their respective APIs and checks. Unknown records and CLR-looking strings remain inert data.

Eight authored groups cover missing/null/explicit-v1 versions and identity overwrite receipts; full-array compaction indexes and opaque preservation; v2 hook-role-only conversion; current idempotence/document ownership; future/invalid versions and unknown retention; invalid ID plans and missing known fields; unsafe compaction blockers; strict permissive-source rejection, decoded lone surrogates, actual non-ASCII UTF-8, depth, count and exact byte limits. Root owns registration, isolated execution and review. Filesystem source/destination collision, interrupted imports, reference-reader interoperability, complete historical corpora and phase acceptance remain separate open work.
