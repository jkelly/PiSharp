# Prepared final-action tool invocation

`ToolInvoker` implements the existing `IToolExecutor` seam for one bounded invocation. It resolves a fixed immutable registry of `IPreparedToolAdapter` implementations, prepares/normalizes arguments through the selected trusted adapter, validates the initial action, awaits action transforms in registration order, revalidates the final action, awaits policy authorization, executes, then awaits result transforms before returning. It supplies no filesystem, process, network, schema package, or built-in effect.

`PreparedToolAction` is an immutable envelope containing tool name, operation, path/command kind, exact target, owned final JSON arguments, immutable command argument vector, optional working directory, and immutable environment mapping. A command requires an explicit working directory. A path action has an empty command argument vector. Names, required fields, enum kinds, UTF-16, NUL exclusion, initialized arrays/maps, argument object/depth and logical budgets are checked structurally. The trusted adapter must resolve concrete targets, validate tool-specific arguments and final-action semantics, and execute exactly that resolved action. The primitive does not resolve paths, shell quoting, symlinks, executable search, environment inheritance, or platform-specific target semantics.

Policy and execution receive the identical final action instance after all action transforms and final validation. Policy therefore sees the operation, resolved target/program, argv, cwd, environment and arguments that execution receives. Transforms cannot substitute another registered tool name. There is no second action derivation after authorization inside the invoker. A deny result becomes fixed `Blocked` output and can retain an explicit termination hint; the executor and post-execution result transforms do not run.

The mandatory `IToolActionPolicy` returns an explicit allow/deny decision. There is no default allow policy. Adapters, policies and transforms are trusted in-process code: they can perform effects themselves, ignore cancellation, lie during validation, or execute something other than the supplied action. This primitive is a host mediation contract, not a sandbox for arbitrary native code or a claim of complete JSON Schema, extension, MCP, or upstream permission parity.

Direct calls enforce their own admission instead of relying on scheduler preflight. The assistant must be finalized with `ToolUse`; `Length` produces `Truncated`. Other stop reasons, invalid/default/null content, invalid indices, non-canonical call references, malformed identities, duplicate call IDs, missing tools and non-object/oversized/unsupported arguments cannot authorize execution. The invocation must reference the actual `ToolCallContent` instance at its source content index. Arguments are already immutable complete `JsonData`; incomplete raw JSON cannot enter that contract. No streaming-preview repair is involved. Argument numbers preserve their raw JSON tokens; tool-specific numeric/schema validation belongs to the adapter.

Owned argument JSON string values may contain escaped NUL, including recursively nested values. Initial admission and final revalidation retain the identical owned data and raw character charging; they do not rewrite, strip or replace NUL. This corrects the prior blanket argument-data rejection exposed by a published extension's echo result before its schema validator or final policy was reached. Executable strings remain separately checked: tool/call identities, operation, target, cwd, argv, and environment keys/values reject NUL, as do the existing JSON property-name checks. Allowing an inert value does not authorize an executable field or bypass adapter schema validation or final-action policy. Result-extra-property admission retains its existing separate profile. Wider JSON-key and other source-profile work remain separate requirements rather than a claim of full argument parity.

The accepted scheduler can register `new ToolDefinition(name, invoker)` for each exposed adapter name. It retains its existing assistant-message barrier, batch scheduling, event and transcript-result ordering. The invoker's action preparation/transforms/policy run inside each scheduled executor call; they do not become the scheduler's sequential batch preflight. No changed scheduler/contract source or high-level loop API is part of this slice. Result transforms replace complete immutable `ToolResult` values rather than implementing upstream partial result-merge semantics.

Unknown, invalid, truncated, blocked, preparation/hook/policy, execution and cancellation outcomes use structured `ToolResult` failures. Own failure messages contain no input target, command, credential/environment value or caught exception text. Trusted tool results are returned as tool output, subject to normalization/bounds; they are not automatically secret-redacted. A thrown preparation/validation error is `InvalidArguments`; transform/policy/finalization faults are `HookError`; execution faults are `ExecutionError`. Post-execution transforms may explicitly override an execution-error result. A non-null failure forces `IsError:true`.

Cancellation is checked before admission and across awaited stages. After both initial and final adapter validation return, the token is checked before branching on the validation result. A validator that cancels the invocation and returns false therefore yields `Canceled`; an uncancelled false result remains `InvalidArguments`. All injected asynchronous operations are awaited, including adapter execution, which must settle its owned cleanup before returning or throwing. The invoker owns no streams/processes and cannot clean up a resource hidden by an adapter. An adapter that ignores cancellation can delay settlement indefinitely; there is no background detachment, hidden timeout, retry, or rollback.

Successfully returned executor results are validated with bounded synchronous checks before observing cancellation, so known completed output/details remain available. If cancellation or finalization failure follows completed execution, the last validated output/details are preserved, a fixed diagnostic is appended, and the result carries an error/failure. An executor that throws after an effect without returning its result cannot supply those details; cancellation/failure does not prove that an admitted effect was absent or reversed. Result hooks stop at cancellation or a result-hook failure. No guarantee is made for resources/effects created during preparation or transforms by trusted code.

Default bounds cover 128 registered tools, 16 action transforms and 16 result transforms, 1,024 assistant content slots, 65,536 raw argument characters, 65,536 logical final-action characters, 128 combined argv/environment entries, 65,536 logical result characters, 128 result content slots, and JSON container depth 32. Names are also bounded by the action character cap. Action charging includes tool/operation/target/cwd strings, raw arguments, argv strings and environment keys/values. Result charging includes raw details, text, raw extra-property values/names and failure text. Own fixed diagnostics have bounded overhead outside admitted-result limits. These logical caps do not include CLR headers, immutable collection capacity, JSON serialization overhead for decoded text, or all temporary allocations and are not a total heap cap.

Nested invocations, parent operation identity, recursion depth, shared execution capacity, cancellation propagation for nested work, and deadlock-free permit handling remain unimplemented. A trusted adapter can call other code, but that does not establish nested policy mediation. Filesystem conflict checks and real read/edit/write/shell tools remain separate prerequisites.

## Source and evidence

The source-linked ordering boundary is public Pi v0.99.1 [agent-loop.ts](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts): argument preparation/validation, before-tool hook, execution, and after-tool finalization. Upstream `runToolCall` returns structured failures, and its source result hook can override execution output/errors. Native immutable action transforms, final-action revalidation/policy, authoritative direct admission, sanitized diagnostics and resource bounds are deliberate hardening. No unchanged upstream invocation oracle or full hook/schema parity is claimed.

Nine authored offline test groups cover pipeline order, an allowed-to-denied final target transform with zero executions, invalid final actions/tool substitution, identical command/argv/cwd/environment/opaque-argument handoff, direct admission, exact and exceeded bounds, result override and sanitized failures, gated cancellation/cleanup with completed-output preservation, and assistant/final-result scheduler barriers. The cancellation group includes deterministic false-plus-cancel regressions for both validation stages with uncancelled false controls, asserting zero authorization/execution. Tests inject trusted doubles only, use task gates rather than sleeps, and make no real tool/provider effects or golden changes.

Three `ToolArgumentDataNulTests.Cases()` groups add initial/transformed-final ownership through schema/policy/execution, initial and transformed executable-string denial, and inclusive raw/action budgets plus malformed Unicode, depth, decoded duplicates, nonfinite output and cancellation controls. Two exact previously negative literals from `StructuredToolResultTests` move into positive complete-pipeline regressions: `{"input":"bad\u0000argument"}` and the final argument transform `{"command":"a\u0000b"}`. The latter retains the original fixed safe Path action (`lookup`, `read`, `/synthetic/file`, empty argv/environment, null cwd) and proves final schema/policy/execution receive the identical transformed action and owned data. A JSON member named `command` does not itself become executable argv. Only these obsolete inert-data expectations are replaced; NUL tool-ID/name and all five original target/cwd/argv/environment negatives remain. The three published persistent-extension integration expectations and their NUL corpus remain unchanged. Root's prior corrected gate passed all three new NUL groups but stopped at the second obsolete negative expectation before the extension suite. The followup full gate and independent acceptance remain pending.
