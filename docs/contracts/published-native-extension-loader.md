# Experimental published fixture loader

This is a P6-04/P6-05 **unfrozen experimental slice**, profile `experimental-published-fixture-0`. It executes explicitly approved task-local published fixtures against the current descriptor registry. It does not freeze a native ABI, discover/install/build third-party projects, integrate Agent/session/UI/provider capabilities, qualify arbitrary in-process code as safe, or complete the broader native extension inventory.

The unchanged metadata admission remains non-authorizing: `ExtensionManifestAdmission.IsLoadAuthorized` is always false. A loader requires a separate explicit `PluginExecutionDecision` with disposition `ApprovePublishedFixtureExecution`. Its identity binds the canonical root with exact casing, retained root-value manifest SHA, complete ordered artifact paths/digests, source scope, effective scope ID, policy revision and host generation. The host must obtain and supply this authority from its authoritative context. Matching hashes or an affirmative metadata inspection never creates execution trust. Denial, malformed metadata and mismatched decisions reject before snapshot directories, PE inspection, ALC creation, module initializers or constructors.

## Ownership and execution sequence

`PluginAssemblyLoader.LoadAsync(metadata, root, sourceScope, effectiveScopeId, inspectionDecision, executionDecision, registry, token)` reserves one owner and a bounded snapshot allowance, then performs real metadata/path/integrity inspection. It reads every artifact again into exact owned bytes and rechecks its SHA. All source streams, cancellation and rollback cleanup are awaited. The approved bytes are copied into a new private, versioned `pisharp-package-<guid>` directory under an existing host-selected canonical local parent. Files are created with `CreateNew`; Windows read locks retain resolver bytes. The caller/source package is never loaded by path.

After explicit fixture execution trust, `PublishedPackageValidator` reads the owned PE/dependency/runtime metadata. Microsoft explicitly warns that `PEReader` is not designed for untrusted PE images; this reader is used for approved fixture metadata and is not a hostile-file safety boundary. [PEReader documentation](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.portableexecutable.pereader?view=net-10.0)

This first published profile requires a Windows x64 host configured for `win-x64`, managed IL-only DLLs without a required 32-bit execution flag, a top-level public nonabstract nongeneric entry type directly implementing `IPiSharpExtension`, a public parameterless constructor, an included `.deps.json`, and an included `.runtimeconfig.json` declaring only `Microsoft.NETCore.App` 10.0 and `net10.0`. Extra framework/self-contained/native/satellite requirements, unsupported assets, missing private closure, duplicate assembly names and invalid images reject explicitly. Package-free `project`/`reference` dependency libraries are supported; generalized NuGet assets, prerelease versions and satellite/RID asset profiles remain qualification work.

One collectible `PluginLoadContext` and `AssemblyDependencyResolver` are created per admitted package. The resolver sees only the owned versioned directory. Managed private resolution must return the exact approved snapshot path and assembly identity; execution uses `LoadFromStream` on the exact owned bytes. Private resolution does not fall through to host-private assemblies. Only the names of assemblies in the host's actual core-framework directory are permitted to use normal Default framework binding, rather than a broad `System.*` or all-TPA allowlist.

Both `PiSharp.Extensions.Abstractions` and `PiSharp.Contracts` are shared as the exact host Assembly objects. Referenced name/version/culture/public-key-token identities must match; a private runtime copy or incompatible ABI reference rejects before loading. The official plugin guidance describes `.deps.json` resolution and excluding runtime copies of shared interface assemblies. [Microsoft plugin tutorial](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support)

Native dependency sections and native images reject. The ALC native resolver throws an explicit unsupported-native diagnostic; it never returns zero to permit a default OS search. This describes the loader's resolution behavior: trusted in-process code can independently use other runtime/OS APIs, so this is not a capability sandbox or proof that arbitrary plugin code cannot load native code.

Construction and awaited initialization then use the real existing transactional registry. Published tools/observations remain mock descriptor callbacks rather than Agent tools or general event reducers. The owner generation and registration lifetime are owned by the registry; the host-generation execution binding is separately caller-owned. The loader does not compute scoped enablement, consent or reload generations itself.

## Settlement and limitations

An exactly-once owned-plugin wrapper handles both failure before registry adoption and initialization failure after adoption. Failed/canceled activation disposes actual plugin resources and removes snapshots before ordinary failure/cancellation settles. Loader close stops admission, cancels owned loading operations, awaits their completed rollback/activation, then joins every admitted lease. Throwing cancellation listeners do not skip these joins. Concurrent disposal shares actual settlement.

`LoadedExtension.DisposeAsync` stops future registry admission, joins already admitted callbacks and actual shutdown, then drops loader roots, requests ALC unload, closes snapshot streams and removes only known owned files/directories. Cleanup never recursively deletes production directories; unexpected children prevent removal and produce a failure. Disposal invoked from a callback that depends on that disposal rejects synchronously, preserving the existing registry's no-self-wait behavior.

Cleanup failure retains the owner and worst-case resource reservation, blocks replacement and reports `CleanupFailed`/`RestartMayBeRequired`. Snapshot creation rollback failure also transfers its retained ownership to the loader. Successful `UnloadRequested` means an unload was requested, not that an ALC has been collected. Captured external snapshots/delegates, plugin statics, untracked threads and outstanding enumerators can still root a context. Construction failure can leave arbitrary already-authorized side effects and reports a possible restart requirement. Cancellation is cooperative and cannot interrupt synchronous module/constructor/runtime loading or terminate arbitrary in-process code. [Microsoft cooperative unloadability guidance](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)

Defaults reserve at most 16 MiB of raw snapshot bytes per package, with 8 MiB per artifact, at most eight owned packages and at most 64 MiB cumulatively reserved. A package reserves its full per-package allowance before allocation, so the default cumulative limit admits four concurrent full reservations. Retired/failed owners remain charged until successful cleanup. Callers may lower these ceilings. Existing manifest count/character/depth limits remain unchanged; published JSON is additionally bounded to 1 MiB and depth 32. These are owned byte/count bounds, not a whole-process CLR/JIT heap limit.

The current underlying path preflight only supports Windows fixed local drives. Before/after ancestor/reparse checks and retained read locks do not establish atomic no-follow/open-handle origin identity. Source reads may still have transient link races, and private directory ancestor replacement is not fully qualified. Managed execution stays tied to hashed owned images rather than a later source path, but origin link/platform policy remains mandatory before general package loading. Non-Windows regular-file/FIFO/device support, native and full RID matrices, archive extraction, physical deduplication, managed dependency generality and stable ABI approval remain open.

The parent restores/locks/publishes these projects as framework-dependent `net10.0` libraries without a RID or self-contained output, then registers `PublishedLoaderTests.Cases()`. Fixtures enable dynamic loading and runtime-config generation, exclude shared host runtime copies, and reference only local framework/source libraries. `PrivateOne` and `PrivateTwo` both emit `Fixture.Private.dll` with different compiled assembly versions. `FutureAbi` is an approved negative assembly with the experimental interface name and version 2; it is excluded from the future plugin runtime output. Module-initializer analyzer suppression is confined to intentional fixture witnesses.

The harness finds the publish root above its own binary or uses `PISHARP_PUBLISHED_EXTENSION_FIXTURES`. It copies public fixture bytes into checked owned temporary directories. Real compiled module initializers/constructors write markers into an isolated fixture directory. Framework-only `AppContext` task gates and an explicit host action coordinate actual published initialization, observation, reentrant disposal denial and shutdown; these are fixture instrumentation, not plugin ABI or production hook dispatch. Gate deadlines guard test failure, rather than asserting elapsed-time behavior, and failure paths release gates before awaited host cleanup. The harness restores its marker environment/context slots and checks owned targets before recursive fixture cleanup. The six groups refuse non-Windows/non-x64 execution instead of silently qualifying unsupported platforms.

Six authored groups cover: denied/mismatched trust and pre-load marker absence; actual conflicting private versions, shared DTO/interface identities, raw JSON echo, source mutation independence and self-wait denial; private ABI copies and a compiled future reference; missing managed/framework/native/corrupted/strict-JSON package admission; failure before registry adoption, failed/canceled published initialization and loader-close rollback; and callback/disposal joins, retained file locks, cooperative weak-reference release and actual unexpected-child cleanup failure retaining its owner/quota. GC is forced only by the test harness after dropping host roots, never by normal loader execution. No build/publish/load/test was run by the author. The parent reported successful offline publishing of all four approved projects in `artifacts/published-extension-fixtures-first-build.log`; source-only inspection of those generated dependency/runtime JSON files confirms the intended package-free forms. Compilation of the loader and execution of the six groups still require the parent's evidence.
