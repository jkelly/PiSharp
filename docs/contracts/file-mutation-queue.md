# Bounded keyed file mutation queue

`PiSharp.Agent.Tools.FileMutationQueue` supplies a functional P3-05 prerequisite: instance-scoped serialization around a trusted host operation. `RunAsync<T>(path, operation, cancellationToken)` returns the operation's result, or propagates its exception after it settles. The queue itself performs no filesystem reads or writes, path transformation, process/provider/network action, authorization or rollback.

The constructor requires an asynchronous `FileMutationKeyResolver`. The host returns the exact key for the action it intends to perform. Key equality is ordinal and case-sensitive; the queue does not trim, lowercase, resolve relative paths or infer filesystem identity from strings. A composition root must share one queue instance across mutations it intends to coordinate. Separate queue instances are independent.

Admission is synchronized by a short state lock. The order in which concurrent callers acquire that admission lock determines registration order. Registration includes awaiting the host key resolver, so a later resolver cannot overtake or overlap an earlier resolver. After resolution, the queue reserves a position behind the previous reservation for that key and releases the registration chain. Its operation starts only after its same-key predecessor settles. Operations for different keys can overlap even while later key resolution is blocked. No host callback or asynchronous wait runs under the state lock.

Every reservation has an independent completion signal that is released in `finally`. An operation failure cannot fault the completion chain or poison a later operation. The queue awaits the operation's actual return or throw before releasing its reservation, including any asynchronous `finally` cleanup inside the trusted callback. The callback must await all of its admitted effectful work and owned cleanup. Detached writes or resources hidden by a callback cannot be observed or settled by this queue.

Cancellation is checked before admission, after waiting for earlier registration, after the awaited resolver, during atomic key admission and immediately before starting the operation. The exact supplied token is passed to both resolver and operation. A canceled registration waits until its predecessor's resolution has settled before it skips resolution and releases its registration position. A canceled same-key waiter retains its reservation until its predecessor settles; it then skips its operation and releases the successor. Its returned task and admission budget therefore remain pending during that wait. The queue does not use a canceled wait to detach a reservation or let a successor overtake still-active work.

For example, with active A, waiting B and waiting C on one key, canceling B does not allow C to run during A's delayed cleanup. B completes as canceled only after A settles, then C can start. A canceled resolver similarly retains the global registration position until its awaited cleanup finishes. An operation that cooperates with cancellation may throw after cleanup; one that ignores cancellation can delay settlement indefinitely. The queue supplies no forced background timeout, retry or process termination. If an operation returns a result successfully despite cancellation, that known returned result is preserved; there is no post-execution cancellation check that replaces it with a cancellation exception. Cancellation never proves that an already admitted effect was absent or undone.

Default immutable options are 128 registered operations, 128 registered keys and 4,096 UTF-16 characters per input path and resolved key. Each option must be positive. Input paths and resolved keys must be nonempty, contain valid UTF-16 and exclude NUL. Whitespace is preserved and can form a key. These structural constraints and logical limits are native hardening rather than upstream path semantics.

| Limit | Charged state and rejection |
| --- | --- |
| `MaximumRegisteredOperations` | Every admitted call awaiting registration, resolving a key, awaiting its key predecessor, executing or cleaning up; checked atomically before any resolver/operation callback |
| `MaximumKeys` | Distinct keys with an active or queued reservation; checked atomically after key resolution and before operation admission; existing-key waiters consume no new key |
| `MaximumKeyCharacters` | Each immutable input path and each returned key, measured in UTF-16 code units; an oversized input is rejected before resolution and an oversized resolved key before reserving a key |

`FileMutationQueueLimitException.Limit` identifies the exceeded operation, key or character cap without embedding the path. Invalid native inputs/options throw argument exceptions. A resolver or operation exception propagates unchanged; this queue does not sanitize arbitrary trusted callback diagnostics or translate them into `ToolResult`. Input/operation validation and initial capacity errors can throw synchronously from `RunAsync`; resolution and execution errors complete its returned task exceptionally. The immutable `Snapshot` exposes instantaneous registered-operation and registered-key counts. Counts include canceled but unsettled reservations, return to zero after settlement and can be used to assess budget reuse. These logical caps exclude delegate-captured data, callback-created resources, Task/CLR headers and temporary allocations; they are not a total memory cap.

The trusted resolver must not await work enqueued into the same instance, which would be behind its own serialized registration. An operation must not await another operation queued on its own reserved key. Such self-dependent nesting cannot progress under FIFO serialization. Nested-operation orchestration and deadlock-free permit handling are separate work.

## Relationship to the pinned source

The selected source is Pi v0.99.1, commit `d86654abb8862e201933517d6f1fce9f88dd117f`, `packages/coding-agent/src/core/tools/file-mutation-queue.ts`, SHA-256 `33cb06ac9bcdf32c8b84d9d12e33be44c503a7670f668e003a3262cd34294d11`. The upstream MIT notice is retained in [THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md). Its dependency closure is that module plus the Node built-in `node:fs/promises` `realpath` function and `node:path` `resolve` function; source inspection required no package installation.

The upstream implementation first applies `resolve(filePath)`, then awaits `realpath`. Only `ENOENT` or `ENOTDIR` causes fallback to the resolved lexical path; other resolver errors propagate. Its module-global registration promise serializes resolution and registration, a map of per-key promise tails serializes operations, and the callback's awaited `finally` releases the next reservation and removes an unused tail. The native queue carries those registration/FIFO/failure-cleanup relationships through an explicitly injected resolver. Native per-instance ownership, cooperative cancellation and logical bounds are additional design choices; upstream has no cancellation parameter or equivalent admission caps.

No native `realpath`, symlink, hard-link, case, cwd, missing-destination or OS identity implementation is supplied here. The authored resolver test maps two chosen strings to the same key; that proves use of the injected key, not actual alias resolution or filesystem parity. The upstream missing-path fallback also does not establish a universal file-identity equivalence. A real host resolver, filesystem identity fixtures, outside-writer conflict checks and path-change race handling remain future prerequisites.

## Evidence and remaining work

Ten authored offline test groups cover same-key FIFO and operation failure recovery; overlap for distinct ordinal keys; serialized asynchronous resolution with synthetic alias keys; awaited failing-resolver cleanup; cancellation before admission, during registration waiting and during resolver cleanup; canceled key waiters retaining predecessors; execution cancellation and delayed cleanup; successful results returned despite cancellation; atomic operation/key/character bounds and budget reuse; concurrent exact-cap admission; and native option/UTF-16 input validation. Tests use Tasks and explicit gates, without sleeps or real filesystem effects. Source and tests are supplied for the root owner's isolated build and execution; this document does not claim an unexecuted test pass or an unchanged upstream differential oracle.

This queue is not connected to real read/write/edit/shell tools, the policy invoker, session generation or a filesystem adapter. It coordinates only supported operations sharing the host queue and keys. External processes/writers and hidden trusted-code effects remain outside its authority. P3-05, built-in tool behavior and all phase gates remain open.
