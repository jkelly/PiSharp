# Explicit session copy CLI contract

`SessionCopyCommand` is a PiSharp-specific, one-shot adapter over the native [copy service](session-copy-service.md). It adds no upstream CLI spelling/parity claim. The public compatibility target remains Pi v0.99.1 at `d86654abb8862e201933517d6f1fce9f88dd117f`; [Phase 4](../plans/04-sessions.md) P4-05 and [Phase 5](../plans/05-headless-rpc-terminal-ui.md) remain open. The pinned [session manager](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/session-manager.ts) and [session format](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/docs/session-format.md) ground the existing migration/record semantics; the new command grammar and stricter admission are native choices.

```text
session copy-inspect --source <absolute JSONL> [--id-plan <absolute JSON file>]
session copy --source <absolute JSONL> --destination <new absolute JSONL>
             --format native-exact|current-jsonl|native-archive-exact [--id-plan <absolute JSON file>]
session migrate --source <absolute JSONL> --destination <new absolute JSONL>
                [--id-plan <absolute JSON file>]
```

All paths are explicit bounded local absolute file paths. Options are case sensitive, may occur once, and require a value. Unknown flags, positional text, duplicate flags and incompatible options fail before acquisition. `copy` requires an explicit format. `migrate` explicitly chooses `CompatibleCurrentJsonl`; a current v3 input can pass through that format without receiving fictitious legacy transformation receipts. There is no default Pi/PiSharp home, inferred destination, implicit credential, provider request, extension authority, generated entry ID, in-place migration, transcript path dereference, image loading or repair.

The command rejects control characters (including NUL), unpaired UTF-16 surrogates, paths longer than 4,096 UTF-16 code units, UNC/device paths, Windows alternate-data-stream paths, empty filenames and lexically non-normalized aliases such as `..` segments. Comparison follows Windows case-insensitive path spelling on Windows and ordinal spelling elsewhere. Explicit trusted paths are a host boundary: this command is not a sandbox or a replacement for filesystem authorization. The service rejects an existing destination (including the source itself), uses exclusive same-directory temporary creation, and publishes without overwrite. Sources and ID plans are opened read-only. The service holds the source open through validation and publication; the command adds no source write.

`native-exact` requires a complete valid current v3 file and publishes the captured original bytes, including numeric/string tokens, spacing, LF/CRLF, blank lines and a valid final unterminated record. `current-jsonl` emits strict current JSON records with LF framing after existing pure v1/v2 migration. Every opaque/native-looking record and field remains data. The whole forest must validate and parents must precede children for runnable store admission; a valid selected prefix alone cannot authorize publication. Future, damaged, empty, invalid UTF-8 and invalid-graph sources return a bounded inspection/blocked report. The additive native-archive-exact format publishes a complete capture as inert data, including future/damaged/invalid UTF-8 files. It reports a null targetVersion, ArchiveNotRunnable, exact byte retention and zero exclusions. Partial source captures never publish. This format supplies an archival route while runnable current-format admission stays blocked.

An ID plan is a strict UTF-8 JSON file whose entire root is a string array, for example `["legacy-user", "legacy-compaction"]`. Each item explicitly assigns one non-header v1 record in physical order. Missing/null legacy version defaults and compaction index references follow the existing [pure migration](session-entry-migration.md). V2 hook roles become current custom roles. No v1 plan is invented; a missing/wrong plan remains a migration blocker, and nonempty plans supplied for v2/v3 are rejected by the migration service. An empty plan is useful only when the source needs no v1 entry identities. Identifiers are strings, never filenames: traversal-like text such as `../../entry` is retained as an ID and cannot choose an output path.

The default command profile bounds source input and output to 8 MiB, physical lines and records to 10,000 (including the header), lines to 4 MiB and each record to the codec's 1,048,576 UTF-16 characters/4 MiB UTF-8/32 nesting levels. The ID plan is at most 1 MiB, 10,000 items, and 4,096 UTF-16 characters per unique nonempty ID. The ID limit is a deliberate stricter CLI authoring profile: the underlying migration accepts identities up to its configured codec character limit. Plan IDs reject control characters and unpaired surrogates; Unicode/supplementary/combining characters are accepted. Duplicate decoded IDs, numeric/null/object/array items, comments, trailing commas, BOM, invalid UTF-8 and nesting beyond two levels fail. Byte limits apply before unbounded capture; count/length limits apply before admission to the service. Full receipts remain bounded by these finite input/record/plan limits and are not silently truncated. Trusted injected service options can choose a different service profile; serialized arguments cannot select those seams.

Each completed inspection/publication writes one LF-terminated JSON object to stdout with `schemaVersion:1`, `type:"session_copy_command_result"`, explicit source/destination/plan paths, the selected format, captured bytes/hash, full-source hash only when EOF was observed, source/current versions, validated prefix counts/ranges, graph/reader/migration diagnostics, and all migration transformation receipts. Receipt `BeforePresent`/`AfterPresent` flags distinguish missing fields from explicit null; `before`/`after` hold only the transformed fields. Arbitrary transcript/opaque bodies are not echoed. Field names inherited from typed receipts retain their PascalCase spelling (for example `RecordIndex`, `Field`, `WasMigrated`, `VersionDefaulted`); command envelope fields use the spelling in the implementation.

Statuses are `inspected`, `blocked`, `published` and `published_with_cleanup_failure`. Exit 0 means a complete inspectable/runnable current projection or clean known publication. Exit 1 accompanies a blocked source, a known publication with cleanup failure, cancellation, I/O failure or failed output delivery. Exit 2 is invalid grammar/path/ID-plan admission or plan resource limits. Fixed sanitized stderr records name the error code and `publication` (`not_attempted`, `uncertain`, `published`), `temporaryMayRemain`, sanitized cleanup codes and any ID-plan cleanup failure; they omit exception messages, source bodies and failed path values. Failed diagnostic delivery still returns failure. Blocked inspection/copy is reported on stdout, because it contains the requested inspection result.

Successful published reports have actual zero unsupported export exclusions in `dataRetention.omittedRecords`/`omittedFields`. This is a data-retention assertion, not semantic support for opaque state. Documented legacy transformations (including removal of `firstKeptEntryIndex`) are separately receipted. `piReaderInteroperabilityVerified:false`, `upstreamCliParity:false`, and `opaqueDataSemanticsVerified:false` stay explicit. Compatible exports require a genuine pinned Pi reader round trip before interoperability acceptance. Neither format claims platform-wide atomicity, disk/power-loss durability, filesystem locking equivalence or completion of Phase 4.

Cancellation is checked before acquisition and through owned reads/validation/temp writes. Source/plan/temp disposal and temporary deletion are awaited before returning. An unrelated stream `OperationCanceledException` is classified as a fixed I/O failure, rather than caller cancellation. Primary failures retain sanitized cleanup information. Once the service confirms publication, late caller cancellation returns the known published receipt; output delivery is awaited without the caller token. If output delivery fails after publication, the error retains `publication:"published"` and returns failure instead of claiming cancellation/no effects. A trusted publish callback that moves then throws remains `uncertain`. Cleanup failure after a known publish returns `published_with_cleanup_failure`; no automatic retry, overwrite or deletion of the destination follows.

The public native seam is `SessionCopyCommand.RunAsync(args, stdout, stderr, cancellationToken, service, idPlanFiles)`. The optional native `SessionCopyService` and `ISessionCopyFileSystem` instances are trusted test/host dependencies. Only the plan seam's `OpenReadAsync` is used; the command owns the returned stream and joins disposal. The normal CLI path uses the bounded real local filesystem service. These seams are not encoded or selected through JSON/CLR type names.

The authored `SessionCopyCommandTests.Cases(dotnetHost, cliDll)` supplies eight groups. Separate compiled CLI processes create a session, execute a permitted owned write, exact-copy it, reopen it, and resume its actual offline request with history checks while proving the completed write is not replayed. Other groups retain raw unknown numeric/null fields and branches, test v1/v2 receipts, inspect future/damaged/invalid forests, reject aliases/collisions/grammar/ID-plan limits, and use real temporary files plus awaited fault seams for cancellation, cleanup, partial writes, publication uncertainty, late cancellation and output delivery failure. Synthetic provider DTOs are labeled authored offline data; no test invokes a live provider or establishes a genuine upstream differential. Authorship and static review do not establish passed counts.

Root-owned registration is required: dispatch `session copy-inspect|copy|migrate` from `Program.RunSessionAsync` to this class, include `SessionCopyCommand.Usage` in help, and concatenate `SessionCopyCommandTests.Cases(dotnetHost, cliDll)` in the CodingAgent test runner. This slice owns no existing Program, command, project, registration or status file. Root performs build/execution/review and records the immutable candidate evidence.
