# Standalone native SSE decoder contract

This dependency-ready P2-04 slice implements byte-stream SSE framing in `PiSharp.AI.Transports.SseDecoder`. It is separate from the accepted normalized assistant-stream reducer. It does not issue HTTP requests, parse provider JSON, interpret `[DONE]`, enforce assistant terminal events, reconnect, authenticate or implement a provider adapter. Those responsibilities remain deferred.

The normative framing source is the [WHATWG SSE parsing and interpretation specification](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream), with [WHATWG UTF-8 decoding](https://encoding.spec.whatwg.org/#utf-8-decode). Source review uses public Pi v0.99.1 commit `d86654abb8862e201933517d6f1fce9f88dd117f`. No complete provider parity is asserted.

Create one decoder and consume `DecodeAsync(Stream input, bool leaveOpen = false, CancellationToken cancellationToken = default)`. One decoder admits exactly one input enumeration. It exposes immutable `SseEvent(EventType, Data, LastEventId, RetryMilliseconds)` values and a separate immutable `State` snapshot. The state makes control-only ID/retry blocks observable without inventing a data event. No mutable input buffer is exposed to consumers.

The incremental decoder keeps UTF-8 state across reads, including fragmented multibyte code points. It strips exactly one leading BOM and retains later U+FEFF characters. CRLF, CR and LF end lines; a CR at the end of one byte chunk and LF in the next form one line ending. Unicode U+2028/U+2029 remain ordinary data characters.

Fields are case-sensitive. Comments start with a colon. The first colon separates a field name and value; only one leading ASCII space after it is removed. A line without a colon has an empty value. Unknown fields are ignored. Each `data` field appends its value and one LF; a blank line dispatches accumulated data with only the final LF removed. An empty `data` field still creates a data event. A block with no `data` fields does not dispatch. Event names default to `message` and reset after every blank-line boundary, including control-only blocks.

An `id` field updates the pending ID unless it contains NUL; a blank line commits that ID to `State.LastEventId`, even when no data event is emitted. IDs persist between events, and an empty `id` clears the ID. A `retry` field containing one or more ASCII digits updates state immediately. Its exact integer is represented by framework `BigInteger`; overflow is not rounded, wrapped or silently ignored. Signed values, fractions, empty values and non-ASCII digits are ignored. This decoder does not turn retry values into timers or scheduling authority.

Default EOF behavior is `DiscardPendingEvent`: completed events survive; unterminated data is discarded and no terminal event is invented. A trailing partial line is unparsed. This decoder policy includes pending control fields on that partial line. Already terminated retry fields apply immediately, while an ID without a following blank-line boundary remains uncommitted.

`DispatchPendingEvent` is an explicit alternate EOF policy: process the final unterminated line, then dispatch pending data if present. Pinned upstream direct parsers flush residual data at EOF, so future adapters can select this policy deliberately. It does not reproduce all parser-specific behavior:

Default malformed UTF-8 handling replaces invalid sequences with U+FFFD. `RejectInvalidUtf8` is optional native hardening and raises a sanitized `SseDecodeException` with `InvalidUtf8`. Strict mode delivers every complete event in the valid prefix before rejecting the first malformed sequence, including an incomplete sequence at EOF. This boundary is independent of read chunks and buffer sizes. In strict mode decoding advances byte by byte, so early iterator disposal after an event need not inspect later bytes even if they arrived in the same read. Default replacement decoding retains the bulk path. Strict rejection differs from upstream's default nonfatal `TextDecoder` behavior and is not an upstream parity defect.

Default bounds are a 4,096-byte read buffer, 65,536 UTF-16 code units per line, and 1,048,576 code units of logical event/connection fields. The read-buffer option is capped at 65,536 bytes. Line limits include comments and unknown fields. `MaximumEventCharacters` charges buffered data with LF separators, event type, pending ID, retry digit count and any distinct committed `State.LastEventId` string. Committed and pending IDs sharing the same string reference are charged once. When a new ID is pending, both retained strings are charged until the blank line commits the new ID; equal values in separate string instances are also charged separately. Replacing pending fields releases their previous charge, but does not release the still-committed ID. Data/type clear after dispatch; IDs and retry state persist.

Limits are native hardening and report `LineLimit` or `EventLimit` without including rejected payload contents. The logical event charge excludes the separately bounded line/read/character buffers, retained `StringBuilder` capacity, transient parser strings and consumer-held events/state snapshots. It is not a total heap cap, a limit on total connection bytes, provider JSON depth or assistant response size.

Cancellation is checked before and after reads and while consuming buffered characters; it reaches the input stream's asynchronous read. Cooperative cancellation interrupts enumeration with `OperationCanceledException`. The admitted input is asynchronously disposed on EOF, cancellation, parse failure, I/O failure or early iterator disposal unless `leaveOpen` is true. Enumerator disposal awaits input cleanup. Consumers must not concurrently call `MoveNextAsync` and `DisposeAsync`; this follows the async iterator's normal single-consumer contract. An unenumerated input remains the caller's responsibility. Arbitrary uncooperative stream reads cannot be forcibly stopped here. Source I/O and disposal failures propagate to the caller for later provider-layer normalization.
