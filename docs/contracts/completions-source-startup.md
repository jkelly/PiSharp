# Completions source startup handoff

The public `CompletionsHttpSseTransport.StartAsync` operation supplies one invocation-owned awaiting continuation before an already admitted first body read resumes decoding. C# completed awaits otherwise let a synchronous handler and reader finish the producer before the caller receives the run. This changes the actual live message seen by the source event consumer; immutable publication snapshots alone cannot repair that observation.

`CompletionsStartupHandoff` implements the existing `ValueTask<CompletionsRun>` return contract. Await the operation once. Its continuation receives the fully constructed run on the caller's registration context. After that continuation yields or returns, the handoff releases the producer's first body-read completion. The handoff holds no event-reader admission and requires no `NextAsync` acknowledgement. Result-only callers therefore continue production, and returned consumers retain the existing bounded discard drain. Task conversion is supported; a deliberately late consumer still sees the actual current live alias.

The actual first read is admitted before this completion handoff. Acquisition faults can therefore update the source message before the caller drains Start, as in the unchanged source capture. Preparation faults still publish no Start. The same leased `CompletionsBodyReader` supplies the real result and decoder bytes. Cancellation releases the handoff and then awaits that admitted read, retaining its closed result or failure; it never abandons the read task. There is no sleep, thread-pool scheduling hint, prefetch queue, synthetic read, frozen live event or reconstructed future snapshot.

Only public source startup supplies this handoff. Canonical startup/progress acknowledgements, final-batch physical cleanup, `SourceResult`, `CleanupCompletion`, `CanonicalCompletion`, strict single-reader ownership and failure sanitization retain their existing authority. No `PiSharp.Contracts` change is required.
