# Bounded session log recovery reader

`PiSharp.Sessions.Storage.SessionLogReader` reads one UTF-8 JSONL source without changing it. `ReadAsync(Stream, leaveOpen: true, CancellationToken)` starts at the caller stream's current position. `ReadFileAsync(path, CancellationToken)` opens an existing file with read access and owns its asynchronous cleanup. This is the recovery-reader portion of P4-02 in [the sessions plan](../plans/04-sessions.md), using the accepted [entry codec](session-entry-codec.md). Writers, locks, durable flush acknowledgements, repair/copy operations, migrations, branch graphs and context projection remain separate work.

The inspected public Pi v0.99.1 source is pinned to `d86654abb8862e201933517d6f1fce9f88dd117f`. Its [session-manager.ts](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/session-manager.ts) `loadEntriesFromFile` reads chunks through `StringDecoder("utf8")`, splits on LF, skips blank/malformed lines, accepts the final line without LF, checks that the first parsed record is a session header with a string ID, and appends LF when a successfully loaded file has nonempty pending text. Header discovery has a separate bounded optimization. The [format documentation](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/docs/session-format.md) describes the v3 entry tree and legacy migrations. This reader's strict UTF-8, damaged-prefix stopping, resource limits, nonempty current header ID and non-mutating recovery policy are native hardening decisions; no unchanged upstream reader comparison is claimed.

The result owns immutable `OriginalBytes`, `ValidatedPrefix`, `Diagnostics` and `ValidatedPrefixByteLength`, plus `SourceComplete`, `Status`, `Header`, `OpaqueHeader` and `DetectedVersion`. Original bytes preserve encoding, all framing/whitespace, unknown data and damaged descendants within the bounded observed input. Parsed records also own their complete immutable codec bodies. Mutating the original input byte array, a copied output array or an independently changed immutable snapshot cannot alter the result. `OriginalBytes` can contain secrets; diagnostic text never copies it.

`ValidatedPrefix` includes the accepted header followed by accepted nonblank records in physical order. Every record supplies one-based `LineNumber`, zero-based `ByteOffset`, `ContentByteLength`, `PhysicalByteLength` and `HasLineTerminator`. Offsets are relative to the read starting position, not an assumed absolute file position. Content ranges include JSON formatting whitespace, exclude LF and exclude its immediately preceding CR; physical ranges include the complete LF/CRLF delimiter. `ValidatedPrefixByteLength` is the exclusive end of the usable byte prefix, including accepted surrounding blank lines. It never advances through the first rejected line or an incomplete bounded-capture fragment. These values support later explicit admission/recovery decisions; they do not validate parent links, duplicates IDs or graph ancestry.

The first nonblank record must be a current-v3 header. Empty input reports `EmptyLog`; whitespace-only input and a valid non-header first record report `MissingHeader`. A malformed or schema-invalid first record reports `InvalidHeader`, subject to the more precise UTF-8, incomplete-tail and resource diagnostics below. A current header with an empty string ID reports `EmptyHeader`. A second header reports `UnexpectedHeader`. No malformed first line is skipped to find a later header.

Physical lines use LF, with optional CR immediately before it. A standalone CR is JSON whitespace, not a line separator. ASCII space/tab/CR-only lines are allowed before, between and after records; their bytes are retained and they count toward the physical line limit. A terminal LF does not create an extra empty line. Other Unicode whitespace is subject to the strict codec rather than JavaScript `trim()` semantics. UTF-8 must be well-formed, and a UTF-8 BOM at the start of a nonblank record is rejected. A BOM after formatting whitespace also fails strict JSON validation. A U+FEFF character inside a JSON string remains ordinary data.

| Situation | Result behavior |
| --- | --- |
| Valid final record with no LF | Accepted; nonblocking `FinalLineWithoutNewline`; source remains untouched |
| EOF inside a final UTF-8 sequence, without LF | Prefix retained; `IncompleteFinalUtf8` |
| Final strict JSON failure that the non-final JSON tokenizer can continue, without LF | Prefix retained; `IncompleteFinalJson` |
| Invalid UTF-8 or incomplete UTF-8 before a recorded LF | Prefix retained; `InvalidUtf8` |
| Malformed/schema-invalid middle line | Prefix stops before it; `InvalidRecord` or a more precise codec/resource diagnostic; later bytes retained without interpreted records |
| Complete malformed final JSON, or a malformed line with LF | Prefix stops before it; `InvalidRecord`/`InvalidHeader`, rather than assuming an interrupted write |
| Source exceeds configured input cap | Bounded observed bytes and completed prefix retained; `InputByteLimit`; `SourceComplete == false` |

Incomplete JSON classification uses `Utf8JsonReader` with `isFinalBlock: false`, after strict parsing failed. It checks unclosed containers or an unconsumed incomplete token and excludes tokenizer-detected errors. It is a syntax/recovery diagnostic, not proof that the writer crashed or that a particular repair will restore a valid record. A fragment stopped by the byte cap has no EOF claim and is never admitted as a valid final record.

Unsupported headers remain inspectable within current syntax/resource bounds. When the codec reports `UnsupportedVersion`, its whole-body strict JSON, duplicate-property, Unicode and depth checks have already run. The reader retains that body as `OpaqueHeader`. An integer declared version greater than 3 reports `FutureHeaderVersion`; other unsupported/missing version declarations report `UnsupportedHeaderVersion`. `DetectedVersion` is present only for the native Int64 integer profile. Neither case supplies a current `Header` or validated records, and neither interprets following future entries. Full future/legacy bytes remain in `OriginalBytes`. This route does not certify future schema meaning, authorize writes or perform a migration. Future headers outside the codec's current basic string/syntax/resource profile still fail safely with retained bytes.

`Status` is `Complete`, `RecoveryRequired`, `UnsupportedVersion` or `ResourceLimit`. A valid nonterminated final record is `Complete` with an informational diagnostic. `SourceComplete` means the stream returned EOF, independently of whether the content was valid. For a later append store, a complete supported source requires both `Status == Complete` and `SourceComplete`; the missing LF information then remains relevant to append framing. This reader itself grants no writer lease or durable checkpoint and supplies no repair action.

Defaults are 16,777,216 input bytes, 4,194,304 content bytes per physical line, 100,000 physical lines, 100,000 parsed records including the header, and an 8,192-byte read buffer. The buffer can be configured from 1 through 65,536 bytes. Positive input limits below `Int32.MaxValue` reserve space for one overflow probe. Codec options carry their separate UTF-16/UTF-8/depth limits. The reader bounds capture growth before every read and retains at most `MaximumInputBytes + 1` bytes, including a consumed overflow probe. On overflow, the probe is retained for honest observed-byte accounting but excluded from record admission. `SourceComplete` remains false; unread source bytes are not claimed preserved. An exact-sized source is EOF-probed and remains accepted.

Capture finishes within the total byte cap before parsing lines. Line size/count and record count are checked before decoding/parsing each admitted line or growing the record collection. Inspection stops at the first semantic/line/record failure, while the captured raw remainder stays available. This design bounds input growth even for a source with no LF and avoids splitting multibyte sequences across decode calls. The bounded capture, copies, immutable byte owner, cloned JSON documents and records consume additional memory; limits are not a total CLR heap cap or a throughput guarantee. A resource-limited result may contain an earlier content diagnostic plus the input-limit diagnostic; `ResourceLimit` has status precedence.

Diagnostics supply typed `Code`, physical line, byte range, an optional codec failure category, fixed `Message` and `IsBlocking`. Line zero is reserved for the input overflow probe. All ranges refer to retained observed bytes. There is no rejected payload, property name, filesystem path or inner parser exception in diagnostic messages. Opening/reading failures throw sanitized `SessionLogReadException(ReadFailed)`; owned disposal failures after otherwise successful reading throw `CleanupFailed`. A stream's `OperationCanceledException` is propagated as caller cancellation only when the supplied caller token is actually cancelled; an unrelated cancellation is sanitized as `ReadFailed`. An original read failure or caller cancellation retains precedence if cleanup also fails. I/O failure/cancellation returns no purported complete recovery result.

The default `leaveOpen: true` preserves caller ownership on success, read failure and cancellation. With `leaveOpen: false`, `DisposeAsync` is awaited before returning or propagating an error, including precancellation. File reads always use this owned path. Cancellation is checked before reads, after awaited reads, between scanned lines and before returning after cleanup. The underlying stream must honor its asynchronous read token for prompt cancellation; synchronous codec work is bounded but does not itself accept cancellation. Cleanup has no cancellation token and is allowed to finish. A cancellation racing after the last check may follow successful completion. No provider callback or source mutation runs during reading.

File reads open with `FileMode.Open`, `FileAccess.Read`, `FileShare.Read`, asynchronous/sequential options, and no existence/create/repair fallback. They neither append LF nor change file attributes. File sharing is not a portable cross-process writer lease and observed bytes are not a transactional snapshot of arbitrary external writes. A later store must acquire its own supported-platform writer lease and define durability before accepting commits.

Eight authored native test groups cover one-byte fragmented LF/CRLF/Unicode reads, blank lines, offsets and final-line admission; immutable bytes and nonzero caller stream starting position; incomplete versus malformed JSON/UTF-8 tails; damaged-middle stopping with retained descendants and repeatable diagnostics; empty/missing/invalid/empty-ID/duplicate/future/legacy headers and BOM; inclusive input/line/record/line-count/codec limits and overflow probes; gated asynchronous cleanup, read/disposal fault precedence, precancellation, cancellation during a read and cancellation during cleanup; and actual read-only temporary-file reads with unchanged SHA-256 bytes and attributes plus missing-file failure. Root registration/build execution is recorded separately. These are synthetic regression evidence, not full P4-02 acceptance, crash durability, cross-platform qualification or session interoperability closure.
