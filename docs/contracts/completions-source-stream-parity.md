## Source numbers and native values

Pinned `models.ts` evaluates input, output and cacheRead as `(binary64 rate / 1000000) * count`, cacheWrite as a multiply before division for these captures, and total as left-associated additions. CLR decimal arithmetic previously produced `0.000040` for the text total. The mapper now performs the measured binary64 operations in the source order and uses the already accepted opt-in ECMAScript JSON projection kernel to obtain exact source number spelling. It does not treat a CLR roundtrip formatter as the source formatter.

`UsageCost` retains its existing decimal fields and adds an immutable `SourceBinary64Cost` JSON sidecar. `PiWireJson` emits the five numeric fields from that sidecar after validating exact field count, numeric types, finite nonnegative values and coherence with all five typed decimal values. A record copy that changes a typed cost while retaining a stale sidecar raises JsonException instead of silently emitting the old number. Coherence compares numeric decimal values; unchanged source lexemes and numerically equal decimal scale changes retain the original raw spelling. The cost test keeps unchanged roundtrip/native-decimal positives and rejects an independent change to each typed field. Other directly constructed provider costs keep their decimal serialization. Reading wire costs retains their raw five-field numeric representation for roundtrip ownership. Source costs are charged as retained metadata; opaque argument/signature numbers are not globally cost-normalized.

Only the captured authored rates and bounded integer count profile have complete-source comparisons here. General fractional/exponent/negative/string/unsafe counts, unsafe aggregate totals, tiers, negative zero, underflow/overflow and the full rate domain remain required numeric work. Counts still use the prior nonnegative safe-integer token admission and reasoning-subset rule. Values outside decimal-accessor capacity can fail the native profile even when a source engine could represent them; this is not a waiver or a full-number-profile claim.

## Provisional identity and strict finals

`ToolCallProvisionalStarted` explicitly represents a real wire slot with an empty ID and/or name and an empty native argument object. It starts immediately at the original content position. Wire index and later nonempty ID correlate that slot. `ToolCallHeaderUpdated` fills only fields that were empty; it cannot overwrite an established identity or create a duplicate ID. Earlier compact frames remain immutable. No generated ID, delayed start or reordered text/tool stream is substituted.

Header update is an explicit native state operation for an in-place source field assignment; the public source does not push a separate event for it. The source-facing projection therefore identifies this one typed operation as non-emitting. Every other frame in a successful explicitly captured reference case must carry both source push and drain snapshots; the differential test rejects missing snapshots. Default compact frames carry neither source snapshot. Compact native event serialization remains a separate contract, including explicit provisional/header event names. It is not asserted identical to the source's mutable partial frames.

The mapper validates every final tool's nonblank ID/name, unique ID and strict complete object arguments before exposing any successful tool end. The reducer independently enforces provisional fill rules, empty initial provisional arguments, stable end identity, unique final IDs and strict argument admission. Never-filled identity, repaired/truncated/scalar/duplicate/nonfinite finals, correlation conflicts and cancellation cannot produce successful Done/tool permission. The display parser's repaired value is never executable final input. All existing tool-effect schema, selected final policy and Agent admission remain required; a provider progress frame is no permission to execute a tool.

Two old `StrictAndUnsupported` assertions were explicitly migrated because the qualified source disproved those temporary exclusions: an indexed blank identity can later complete, and a valid encrypted reasoning detail is replay data. They now have positive default behavior plus retained never-filled/strict-final negatives. Adjacent unsupported feature, malformed argument, alias, resource, ownership and cancellation controls remain assertions. No default legacy exclusion was introduced.

## Owned source snapshots and alias timing

`StreamEvent.SourceEmissionSnapshot` and `SourceDrainSnapshot` are immutable owned JSON, separate from compact Pi wire event serialization. `OpenAICompletionsWireOptions.CaptureSourceEmissionSnapshots` defaults to false. Ordinary provider progress emits compact native frames, preserves every source cost/provisional identity/reasoning/final correction and performs no full-message source copy or repeated whole-prefix display parse. Native tool fragments accumulate in the reducer's bounded buffer for final strict parsing.

`CompletionsSourceEventProjection.CaptureOwnedSnapshots(options)` explicitly selects full source push capture. In that mode the mapper builds a whole message snapshot at each source push position, with current response ID/model, usage, raw finish reason and content. The source-facing tool view retains the original partialArgs, actual streamIndex, bounded display-preview arguments and own-undefined customInput presence. It removes scratch properties at that tool's end while other active tools retain theirs. Native tool arguments remain empty until strict finalization. Full historical capture has cumulative export limits; selecting it does not change successful compact frames or finals within those limits. This keeps default streaming aligned with architecture section 4's requirement to avoid cloning a whole transcript on each token.

The accepted preview helper and ECMAScript projection are selected only for captured display. Default progress does not require that display conversion; native strict final arguments retain raw tokens in both modes. The display helper's unsupported numeric/Unicode profiles remain explicit. General preview/final numeric equivalence and source repair of executable finals remain mandatory follow-up. The three fixed captures do not contain a wide/fractional raw tool argument that would prove those profiles closed.

The genuine driver's `for await` drains concurrently with the unchanged source. Its async SDK iteration and awaited onProviderStreamEvent callback create observation boundaries between chunks. Pushes within one synchronous chunk share a mutable source partial until that boundary; for example, text_start can drain with that chunk's subsequent text, and a text update can drain with a tool block added later in the same chunk. Start drains before the first chunk, so it remains pending and empty. Finalization pushes share the fully finalized partial, including removal of every tool scratch field. These are the measured boundaries for this three-case driver, not an after-completion drain schedule.

Selected capture stores each push view at Emit and each drain view when its Process batch finishes; it separately captures start and the synchronous finalization batch. This is state-based producer instrumentation without golden reads, case IDs or index substitutions. `ReadEmission` and `ReadDrain` expose those independent owned views. `ReadCapturedDrainObservations` requires a successful captured terminal and every non-header push/drain view, bounds their total admitted JSON and returns them unchanged. It never replaces partials with final messages or clears undefined paths. The full golden compares both arrays and their ownUndefinedPaths independently. Arbitrary slow/concurrent consumers, different SDK scheduling, failed/canceled histories and universal mutable-alias behavior remain unqualified; native immutable delivery timing is a separate contract.

## Reasoning details and bounds

The source's detail validator admits summary, text and encrypted shapes with valid common ID/format/index and signature types; invalid detail objects are ignored after strict whole-DTO admission. Consecutive summary/text entries concatenate their selected text, fill only missing/null common fields and empty optional format/signature fields, and preserve the first entry's opaque properties and insertion order. Encrypted entries remain discrete opaque records. No unknown field is loaded as a CLR type or executable authority.

Details remain replay metadata until thinking_end; they do not invent visible thinking deltas. The final thinkingSignature is an exact source JSON string, produced through the accepted projection kernel with retained property order. Incoming chunks, raw fragments, selected identity and metadata, owned costs, retained detail arrays and final signature values consume the mapper's existing raw/content limits. Explicit source capture additionally charges every exported push and drain snapshot cumulatively alongside retained logical content; drain export separately bounds both admitted views. No enlarged default cap or unbounded replay buffer is added.

The generic reducer admits both current incoming sidecars together with the response data it actually retains, checks resulting state under one shared character cap, then releases their charge. It holds no earlier progress snapshots and removes both sidecars from its private terminal record while leaving the caller's immutable frame intact. Historical snapshots that a selected capture consumer retains belong to that bounded capture path. The reducer therefore rejects an oversized individual snapshot or oversized combined snapshots/state without treating already delivered progress as a retained transcript. Tests cover repeated discarded pairs, separate oversized push/drain views, combined-pair overflow, post-apply retained-state growth and a terminal with two owned current snapshots.

A source-view cap failure settles with the existing sanitized ResourceLimit terminal. If no budget remains for a source-facing error copy, it does not manufacture that snapshot or substitute successful Done. Complete failed/provisional history and error/cancellation projection remain required follow-up outside this success corpus. Resource and strict-input failures must retain denial of tool authority. Bounds describe admitted logical strings/JSON copies, not total CLR heap or process RSS.
