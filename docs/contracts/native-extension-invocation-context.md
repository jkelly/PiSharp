# Optional native tool invocation context

This additive native prerequisite supplies a real provider tool-call identity and joined progress to an existing registered extension callback. It does not implement or execute another Node extension, change the corpus inventory, admit a new schema, or claim whole source scheduling parity. All eleven unchanged extensions and 42 corpus scenario IDs remain required.

`IExtensionToolInvocationContext : IExtensionToolContext` adds `ToolCallId` and `ReportUpdateAsync(JsonData, CancellationToken)`. The registry advertises `tool-invocation-context`. No member changes on `IExtensionContext`, `IExtensionToolContext`, `IPiSharpExtension` or `ExtensionToolDescriptor`; the original `ExtensionToolCallback` delegate remains unchanged. A compiled legacy extension receives the same callback ABI. The original `ExtensionRegistry.InvokeToolAsync` overload keeps its original context and supplies no invocation-aware interface or invented ID.

The new registry overload requires an explicit actual ID and one host-owned `ExtensionToolUpdateCallback`. IDs retain exact scalar text, including the Responses composite `call_id|item_id`; there is no ASCII-name filtering, trimming, normalization or generated fallback. Empty/whitespace-only, NUL, unpaired-surrogate and oversized identities reject before admission. The ID length is bounded by the registry's existing `MaximumJsonCharacters`. A multicast update sink rejects because its delegate return would not join earlier sinks.

`IInvocationPreparedToolAdapter` supplements the existing prepared adapter interface. `ToolInvoker` calls it only after the existing preparation, schema validation, hooks/transforms, final validation and final authorization succeed. It receives the original immutable `ToolInvocation` and the identical authorized `PreparedToolAction`; invocation identity is not derived from mutable arguments or placed inside the action. Legacy prepared adapters continue through their original execution overload.

`ExtensionToolAdapter` forwards `invocation.Call.Id` and `action.Arguments` to the new registry overload. This preserves the original provider identity while executing the final transformed arguments. A denied or invalid final action enters neither the registered tool callback nor its progress sink. Argument validation and final native policy remain authoritative.

The derived context remains the exact object passed through `ExtensionUiContextLease`; the lease does not wrap away its optional interface. Registry admission still validates the captured registry identity, registration, owner generation and active scope before creating a callback lease. Removed registrations and replaced/closed owners reject later invocations. An admitted invocation retains its lease through callback settlement, update delivery and UI disposal.

Progress uses **native awaited producer semantics**. One update may be active per invocation. The context retains one actual delivery receipt, rejects overlapping reports, validates strict object JSON using existing registry character/depth/scalar/finite/duplicate-field bounds, and fences operation/session/extension cancellation before admission. Data and concurrency faults remain sticky even when trusted callback code ignores or catches the returned failure. A closed context rejects later reports instead of accepting detached updates.

The Agent adapter additionally parses every partial result through the configured `ToolResultValueCodec` limits and passes the exact framework callback to existing `ToolProgressDelivery.ReportAndWaitAsync`. This recovers the owned delivery receipt and preserves configured parent source-compatible update/pending/retained-character/block quotas. No quota increases, new unbounded history or double-charging path are introduced. The context itself retains no progress history; direct registry callers receive registry JSON bounds and native pacing, while their supplied sink owns any additional result/event quotas.

The existing outer Agent delivery mode remains explicit. In native mode, a report awaits the actual native sink. In source-compatible mode, ordinary source callback invocation can remain immediate under the existing Agent contract, but this optional native context intentionally awaits its owned receipt. This stronger native producer pacing does not establish unchanged JavaScript `onUpdate` scheduling or Node progress support. A future source adapter must implement and qualify that boundary separately.

After the actual callback returns or throws, the registry closes update admission and joins the last admitted delivery before releasing the callback lease. This join also applies to a trusted callback that failed to await `ReportUpdateAsync`. Registry/owner disposal therefore waits for both callback `finally` and admitted sink completion. Cancellation does not abandon admitted delivery that ignores cancellation. Callback and delivery faults are both retained when distinct; combined cancellation retains both causes inside a cancellation exception. Joined closure releases the sink/validator references, and stale contexts cannot publish into a later invocation or generation.

`ExtensionToolInvocationTests.Cases()` has five authored ordinary native groups:

1. Actual registered tool through a two-turn Agent and authored provider transport, exact original composite ID, transformed final arguments, progress-before-tool-end and complete next-request tool result.
2. Final denial/invalid action with zero callback effects, original registry overload without the optional context and legacy prepared-adapter fallback.
3. Two concurrent invocations with distinct actual IDs, inputs, context objects and update receipts.
4. Operation cancellation and registry disposal joining a deliberately unawaited held update and callback `finally`, shared cleanup, closed context and removed-registration rejection.
5. Malformed/duplicate/nonobject/oversized partials, configured result bounds, overlapping delivery, existing source-compatible progress quotas and invalid/multicast invocation admission.

The existing compiled published-plugin and native-only regression gates must remain passing alongside these groups. No test was run by this author; root owns harness registration, builds, runtime execution, immutable commits and independent review. This slice creates no new executed/passing corpus count and grants no P6-G/P7-G completion credit.
