# Native SDK creation admission

An admitted SDK command can request a clone whose reconstructed target exceeds the callback snapshot limits. In particular, a valid 4,096-entry source ancestry plus a globally resolved label on a sibling produces a 4,097-entry clone. On candidate `65caa08b8fa2ffe71d3cb3d8b0d133b3d30ad79c`, the broker committed that attachment before the registry rejected its required returned context. Independent finding `LIFECYCLE-SDK-PREFLIGHT-1` holds that candidate despite its passing 858 native groups and original process gates.

The corrected SDK operation supplies the eventual registry snapshot validator to the actual native broker. The broker captures the actual staged target with its proposed attachment generation and invokes that validator through `ReplaceableAgentSession.CreateAsync`'s `beforeAttach` callback. Source and target reservations are both held. The registry calls the same `OwnSessionSnapshot` method used when admitting the returned context. Entry count, per-entry/aggregate character and UTF-8 bounds, depth, identifiers and explicit host opaque-number policy remain unchanged. A rejection occurs before source writer retirement or attachment publication, and the owner joins target close and deletion of the known unattached file. The old source remains current and writable.

The scope contract has an additive overload taking `Func<ExtensionSessionSnapshot, CancellationToken, ValueTask>`. The former overload is retained. An older broker that implements only the former overload fails the required SDK operation before effects through the new overload's default implementation. It must implement staged validation under its actual reservation/publication boundary to support creation returning an SDK context. The staged validator calls registry policy, not plugin code, and cancellation is checked before and after validation.

Snapshot preflight cannot predict arbitrary postcommit callbacks or a later operational failure during context admission. Once the broker returns its committed result, a failure admitting that context becomes `ExtensionSessionCreationCommittedException`. Its receipt records the actual session ID, attachment generation and selected leaf, without granting mutation authority. Context admission owns and joins the supplied scope cleanup before returning that error. Existing coordinator notification failures retain their existing committed replacement receipt. Precommit validation failures retain the ordinary registry diagnostic and do not claim commitment.

The readonly session-view capability still preserves raw opaque numeric tokens such as `1.00e400` only for an explicitly configured trusted host. Ordinary providers and executable plugin input keep the finite-number policy. No snapshot limit is raised to admit a large clone. Direct RPC output/event preflight, source/target reservations, veto handling, conservative uncertain publication, known-file rollback and physical retirement remain required regression boundaries.

The immutable independent V2 reproduction, its successful adjacent control and its original failed assertion are preserved. The correction also adds registry policy/cancellation/older-broker/committed-error controls and actual production SDK storage tests. Full exact-candidate gates and separate independent successor acceptance are required. All 79 original work packages and all eight complete phase gates remain open. The separate catalog/resume draft is frozen, unbuilt and untested until this correction is accepted.
