# Experimental native extension Agent binding

`PiSharp.Extensions.Agent.ExtensionAgentBinding` captures the current immutable `ExtensionRegistrySnapshot` and creates executable `ToolDefinition` values for the real Agent pipeline. The registry remains caller-owned. Creating a binding neither loads code nor grants trust, starts an Agent, discovers credentials, or changes a session.

The existing experimental extension abstractions remain unchanged. In this binding, a registered tool callback returns a **complete JSON result object**, admitted by `ToolResultValueCodec`. An arbitrary JSON value accepted by registration-only dispatch is not necessarily an Agent tool result. Absent, explicit null and empty content retain their distinct owned properties; the typed content view and canonical model message normalize absent/null content to an empty array. Details and usage retain presence and original numeric/null tokens in canonical history. Structured content and arbitrary result properties remain on the execution result; provider requests use their existing source-defined message projection. Runtime failure/outcome error stays separate from the result object's own fields.

Snapshot `Tools` exposes owner ID/generation, registration ID/name, description and owned parameters. It exposes no callback. The binding invokes callbacks only through `ExtensionRegistry.InvokeToolAsync`, preserving registry identity, registration removal, owner generation, dispatch quotas and callback leases. A captured binding cannot execute a removed registration or a replacement generation. Already admitted callbacks retain their lease and are joined before extension shutdown. A later registry snapshot requires an explicit host idle transaction to publish matching executable tools and declaration changes. This helper does not silently replace a running Agent's configuration or publish removals.

Every binding requires an explicit trusted `ExtensionToolArgumentValidator` and `IToolActionPolicy`. The validator receives the complete schema metadata and input before transforms and again after transforms. It must validate its entire supported schema and reject any unsupported schema/input; there is no automatic partial evaluator or no-validator fallback. The tests' validator implements its complete authored object/string/enum/required/additional-properties schema and rejects every other schema. Full canonical JSON Schema validation remains a required implementation dependency.

The prepared action has kind `Extension`, operation `invoke`, and target `ownerId/ownerGeneration/registrationId`. It has no working directory, command arguments or environment. Adapter validation rejects identity changes and any file/shell action shape. The existing ToolInvoker sends the identical immutable final action instance to policy, then invokes the callback with that action's owned arguments. Existing path and command adapters/policies explicitly require their respective kinds; an extension action does not inherit those grants. Trusted extension code can still perform arbitrary in-process effects: this action boundary and registry are not a sandbox.

`CreateDeclarationMessage(content, timestamp)` creates an explicit system input containing ordered `toolsAdded` function declarations. Description and parameters come from the same captured metadata. Schema JSON tokens are retained. Tool count and cumulative declaration character/UTF-8 byte budgets are charged before each record enters the output buffer; the complete message envelope and content are bounded too. Bindings also require valid complete result limits. Registry input/output bounds, codec bounds, Invoker final result bounds and Agent progress/result bounds all apply; raising one does not bypass another. Invalid syntax, decoded duplicate names, unpaired Unicode, excessive depth and nonfinite numbers retain their existing strict diagnostics and sanitization.

The supplied Agent operation token, optional session token and registry extension-lifetime token remain distinct in callback context. Registry dispatch links them for actual callback work. Cancellation carrying a canceled work/session/linked callback token becomes a native `Canceled` result after callback cleanup has settled. An unrelated callback exception, including an uncanceled cancellation exception, follows execution-error admission. This does not abort a whole Agent automatically when an independently supplied session token or extension lifetime ends; the host still owns Agent/coordinator cancellation. Concurrent registry disposal shares settlement, stops new admission, cancels and joins actual callbacks, then awaits extension disposal. No timeout proxy releases those ownership barriers.

`ExtensionAgentBindingTests.Cases()` contributes five native regression groups: a real two-turn Agent plus next Responses request projection; final-action/schema/policy rejection before effects; captured removal and generation replacement; actual abort/caller/session/lifetime cancellation with gated callback and extension cleanup; and result presence/termination/strict-output/declaration quotas. These are authored native controls, not an unchanged-source extension oracle or a full P6-06 acceptance claim.

Mandatory remaining work includes the complete schema evaluator and typed authoring contracts, namespace/exposure/annotations/execution metadata, progress callbacks in the extension ABI, nested execution with parent IDs/depth and normal authorization, shared file mutation scheduling, safe host action broker, automatic transactional declaration/session updates, generation-checked session contexts, event reducer integration, and the wider loader/trust/UI/provider/reload gates. The current experimental abstraction is not a frozen native v1 SDK.
