# Explicit profile resource admission composition

This source slice is based on e3bce705cfc415d788ee74d6c207ddc322bc1972. `McpProfileResourceAdmissions.WithResources(baseAdmission, resourceAdmission)` is an opt-in public bridge accepted by the existing profile/command injection signature. It introduces no transport, process, provider, credential, filesystem saver, or authority acquisition.

The base callback receives the original cwd, reserved generation, actual native registry, exact final policy, and token. Its successful response must preserve registry/policy reference identity and expose independent native/discovery owners before any wrapping. An already supplied resource registration is refused before the explicit resource callback. The resource callback receives one captured request object containing that exact base response. The successful response must return that same request object by reference, a fresh registration, and an independently closeable resource owner. Record value equality is insufficient. Successful composition uses `with` to preserve all other admission properties and the existing single activation prepares resources before discovery.

Ownership transfers on successful callback return, including when returned metadata is rejected. The bridge closes independent returned resource ownership and then discovery/native ownership on rejection. Aliases are refused and each visible owner is joined once by reference. Callback allocations not returned remain callback-owned; a callback must join them before throwing. The bridge cannot introspect a registration's private registry/scope or detect hidden aliases inside arbitrary caller owner wrappers. The explicit caller contract therefore requires each fresh owner to own its registration scope, registry, and saver lifetime independently of other acquisitions. No fresh-registration claim extends beyond this composition delegate's registration identity ledger and the existing registration's own single-attempt guard.

Acquisition/disposal ValueTasks are converted to their original Task once. Synchronous failures retain their exact evidence separately; faulted originals retain the complete Task.Exception with sibling faults. Only an original canceled Task is recorded as cancellation. Faulted and synchronously thrown OperationCanceledExceptions remain faults. Composed native/resource ownership exposes one stable close Task, joins resource ownership before native ownership, and refuses reentrant self-join.

`McpProfileResourceAdmissionTests.Cases()` contains source controls for successful native resource calls through the actual factory/lifecycle/channel/saver, resource preparation before discovery, held saver shutdown, absent opt-in behavior, multicast refusal, held rollback retaining resource/discovery/native sibling faults, base owner alias refusal before resource acquisition, acquisition cancellation provenance, rejected value-equal foreign request rollback, and repeated composed disposal sharing one Task. Its actual `OfflineSessionProfile.CreateAsync` / `CreateLifecycle` / `AttachOwnerAsync` caller control confirms actual catalog binding and final-policy denial before resource channel or saver effects.

The pinned profile's FilePolicy admits extension actions only through its explicit exact name/target authority map. Dynamic MCP/resource registration does not populate that map. Successful public profile resource execution therefore remains blocked pending an explicit caller authority admission seam; this slice preserves that boundary. The separate factory success control supplies an explicit synthetic allowing policy. Profile view binding alone cannot grant authority.

The files are included by existing SDK default globs; the test case provider is intentionally unregistered because root Program is reserved. Integrators must register `McpProfileResourceAdmissionTests.Cases()` in the existing runner. No compiler, build, tests, native runtime, HTTP, process, TypeScript, package acquisition, or credential reads were executed. Static source inspection and git whitespace checks are evidence only, not runtime acceptance, ABI closure, or transitive SDK AST/type closure.
