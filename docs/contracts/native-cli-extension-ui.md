# Published native CLI extension UI

This bounded P5-06/P6-08 integration binds explicitly approved published native packages to the existing offline durable CLI and its actual RPC connection. It reuses the accepted UI service, registry callback leases, registered input/tool hooks, runtime configuration, mandatory final-action policy and session append barriers. Package discovery does not grant execution. The separate package/hash/scope/session/workspace/snapshot approval and exact enabled tool names are unchanged; `ApprovePublishedFixtureExecution` remains an experimental trusted in-process execution disposition, not a general plugin sandbox.

`OfflineSessionProfile.CreateAsync` and `NativeExtensionActivation.LoadAsync` append an optional borrowed `IExtensionUiProvider`. RPC constructs one `RpcExtensionUiCoordinator` before activating the package and supplies that same instance to the actual registry and dispatcher. The dispatcher constructor preserves the registered-input argument position and appends `extensionUi`; both accepted test families remain registered. There is one stdin reader and one stdout JSONL writer, no UI handshake, session header, parallel connection or separate authority store. Notifications, requests, command responses and Agent events share the existing complete-record write/flush barrier.

Print/report and JSON commands supply explicit mode-specific `UnavailableExtensionUiProvider` instances. Their callbacks expose empty capabilities and `Unavailable(NoUi)`, publish no remote dialog, and never turn missing confirmation into approval. RPC offers the existing nine baseline features: select, confirm, input, editor, notification, status, text widget, title and editor text. Offered capabilities do not prove that a client renders them. Custom terminal components remain unavailable until the terminal host is implemented.

Requests retain the pinned `rpc-mode.ts` / `rpc-types.ts` field names and optional-field distinctions documented in [RPC extension UI](rpc-extension-ui.md). Replies arrive on the same stdin as commands using `extension_ui_response`. Unknown and duplicate IDs produce no ordinary response and cannot resolve another request. Matching null or missing values are `Unavailable(InvalidResponse)`; `cancelled: true` denies even when `confirmed: true` is also present. Empty strings, valid Unicode, NUL and CR/LF remain data. A retained callback UI scope becomes `Unavailable(StaleContext)` after that callback has closed, even while another callback of the same loaded owner continues. The optional timeout follows the accepted service policy; the compiled control uses a finite system timer without sleeps or a claim that publication always precedes timeout.

UI confirmation is a plugin decision only. Tool replacement/schema admission and mandatory authorization still apply to the final prepared action. The published fixture can report `ui:approved`, but a later native file action requires the existing explicit per-file permission independently. Assistant commit and public message-end precede the callback; actual tool-result append completes before the next scripted provider request. UI records themselves are absent from the durable conversation. Complete plugin result details, structured fields and explicit null remain on public tool events, while canonical tool messages retain their established model-facing fields.

EOF, abort and broken output use the dispatcher’s accepted connection shutdown: pending UI resolves before joining callbacks, entered writes/flushes and callback scopes are awaited, then the coordinator/session/profile and published loader close. No cancellation or failed publication supplies approval. Abort and EOF do not acquire a subsequent provider response or execute a later native effect. Outstanding UI, deferred ordinary input and retained bytes keep the service’s existing caps; this integration raises no quota and installs no retry. Failed stdout remains a failed host receipt after cleanup rather than a second success response.

The root publishes `tests/fixtures/extensions/native/PluginCliUi` as assembly `PublishedFixture.CliUi`, entry `PublishedCliUiFixture.Entry`, under `artifacts/extensions/published-fixtures/cli-ui`. Its single closed-schema tool is `fixture.cli.ui` with `{action:string}`. Test-owned marker IO proves module/constructor/initialize/callback-finally/dispose ordering; it is confined to an explicitly supplied test temporary directory and is absent from production activation logic. The package is ordinary trusted C# code and can execute arbitrary in-process code after approval; its marker convention is evidence instrumentation rather than a security boundary.

Root registration is `NativeCliExtensionUiTests.Cases(dotnetHost, cliDll)`: six new compiled-process groups cover all four dialogs and all source-shaped notification methods, strict whole-record structural comparison (object-key order only, exact number tokens/strings/null/missing/arrays), complete result fields, Unicode/NUL output, independently authorized write bytes, acknowledged physical history, independent reopen/selected branch, Print/Json noUI, unknown/duplicate/null/cancelled replies, stale scope, actual finite timeout, held abort/EOF, approval denial with zero module markers, and actual closed stdout. Each child has bounded output and an owned deadline/finally process-tree join. Deadlines bound failures; expected ordering uses request/response/settlement records and callback markers. No real console Ctrl+C or source timing equivalence is asserted. The author has performed static inspection only; root owns publish/build and native process execution, so there is no passing claim before that gate.

This is an authored native integration over literal offline Responses, Anthropic and Completions streams, not an unchanged source oracle of the complete CLI/plugin protocol. The accepted service’s source research and its qualified standalone scenarios remain separate evidence. Full terminal rendering, custom components, source `ui_prompt_start`/`ui_prompt_end` nesting/microtask behavior, session replacement generations, all remaining extension events, production execution approval/API qualification and the complete P5/P6 supported-platform matrix remain mandatory work. No dependencies, provider credentials, environment key discovery, package restore or live requests are introduced here.
