# Explicit-store discovery, resume and branch state

This bounded milestone continues the accepted SDK lifecycle correction `b783dfd85f7c4bbc405943b3fb9eacc520922199`. It adds one catalog/resume path for embedders, native C# plugins, RPC and cooked/terminal input. All 79 original work-package scopes and eight full phase gates remain open. Test counts are evidence for this profile, not a completion percentage or full source parity claim.

`SessionCatalog` accepts explicitly named absolute directories. It never searches a default home or recursively follows directories. Store identity, filename and the complete strict header fingerprint produce an opaque catalog key; identical header IDs and filenames in separate stores remain distinct. Known cwd and parent-session metadata are retained as data. Parent paths are never opened. Windows cwd grouping folds case and separators lexically; Unix grouping preserves case. These comparisons do not resolve foreign paths or grant workspace permissions.

Discovery reads bounded current-v3 headers, not complete message/image bodies. It may read at most a small fixed chunk beyond the header newline, but does not parse the body. Malformed headers/names and final links are skipped with counts. Directory-entry and reader bounds fail explicitly rather than truncate a successful listing. Pages sort by modification time and stable store/filename order. Opaque cursors bind the explicit store configuration, cwd query and last sorting keys. Each page rescans the live filesystem; this is not a snapshot or lease across pages. Cancellation and host shutdown join actual reader/enumerator close before completing the owned operation. Header discovery does not prove that a damaged body is resumable.

`PersistentSessionLifecycle` supplies creation, existing opens and catalog resume to `ReplaceableAgentSession.WithLifecycle`. Resume resolves the explicit key, opens the actual complete log through its exclusive writer, validates its graph, selected ancestry and runtime configuration, then compares the actual opened header against discovery. A changed header, malformed full log, unknown model, typed veto or cancellation leaves A current and joins B cleanup. An imported existing B is never deleted by rollback. Source and actual target stay reserved through all target/context/output preflight. Only publication retires A, increments the attachment generation and returns fresh B authority. Matching disk IDs cannot revive an old context. Notification failure reports the committed replacement instead of implying rollback.

An optional trusted `registryForWorkingDirectory` factory binds services from the actual fully validated opened header cwd. It borrows registries and does not widen tools, paths or credentials. Without that explicit factory the existing same-workspace policy remains enforced. Subscription rebinding uses the existing committed attachment notification. More general provider/resource setup, lazy/in-memory backends and complete import/export/read-only service parity remain open.

Native callbacks may use `IExtensionSessionCatalogContext.ListSessionsAsync`; only a command context has `ResumeSessionAsync`. Resume and switch now use additive broker overloads requiring validation of the actual staged snapshot with the same eventual `OwnSessionSnapshot` policy before retirement. Older effectful-only brokers fail closed. The accepted creation overload and its original bounds are retained. Snapshot count, per-record/depth/identity and aggregate character/UTF-8 limits remain unchanged; trusted read-only views retain opaque strict JSON numeric spelling, while executable arguments remain finite. Catalog DTOs are bounded and copied into an owned array. Postcommit fresh-context admission errors include actual ID/generation/leaf receipts after joined cleanup.

`ExtensionSessionState.ReadLatest` reads only the acknowledged selected ancestry, namespaced by callback owner and record kind. It returns the latest matching `pisharp.extension-state` record and opaque JSON payload. The extension explicitly owns schema migration: incompatible versions and malformed matching envelopes produce errors, without rewriting history. Other owners, absent extensions, unknown custom kinds and sibling-only state remain inert and intact. State-only custom records retain the existing exclusion from model input. External plugin storage is separate from branch history.

The compiled read-only CLI command is `session list --session-store name=absoluteDirectory`, with repeatable stores, `--page-size 1..128`, `--cursor` and `--cwd`. It acquires no provider, tool, plugin or session writer. RPC/interactive setup accepts repeatable explicit `--session-store` flags; its default catalog is only the explicitly attached session's directory. Native RPC commands are `pisharp_list_sessions` and `pisharp_resume_session`, with optional explicit root/leaf selection. Success response and switch-event output budgets are validated on the actual target before retirement, including ordinary switch. Existing RPC asynchronous admission/correlation remains in use.

Cooked and terminal input exposes `/sessions [cwd]`, `/sessions-next` and `/resume <number or key> [leafId or @root]`. Numbered choices belong to the complete validated latest page and current attachment generation. Late listing responses and older switch/fork observations cannot restore an old selection or draft. Listing text passes through the existing inert-control display escaping. These controls exercise the cooked frontend; the original genuine borrowed-standard-handle terminal qualification remains bounded, with `productionCliBootstrapQualified:false` retained.

Evidence includes actual local reader/writer cancellation and cleanup, two-store identity, selected siblings/root, physical stale-write rejection, independent reopen, source/target byte preservation, opaque/absent-extension state, actual SDK preflight, RPC output boundaries and cooked/compiled CLI controls. All new groups are authored native controls. Full native and unchanged original Commands/Input, genuine-terminal, SDK creation and target-reservation probes must pass for the immutable candidate, followed by independent Astra Medium review. No paid live API calls, credential setup, public push/release or permission expansion is part of this milestone.
