# Bounded JSONL RPC transport foundation

`PiSharp.Rpc` provides a framework-only JSON-object transport over caller-supplied streams. It implements the framing portion of [P5-03](../plans/05-headless-rpc-terminal-ui.md), using the pinned [RPC framing documentation](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/docs/rpc.md#framing), [jsonl.ts](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/modes/rpc/jsonl.ts) and its [framing tests](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/test/rpc-jsonl.test.ts). These are source-linked authored native tests; no unchanged-source differential capture or complete RPC qualification is claimed.

`new JsonlReader(stream, options: null, ownership: JsonlStreamOwnership.Borrowed)` returns owned immutable `JsonData` values through `ReadAllAsync(cancellationToken)`. One reader permits one enumeration. It pulls bounded chunks only when its consumer advances, splits on byte LF alone, and removes one immediately preceding CR. Bare CR, U+2028 and U+2029 are never record separators. Fragmented UTF-8 is retained as frame bytes and decoded strictly only when the frame completes, so read splits cannot change its meaning. Each returned value outlives the parsing document, input buffer and stream.

A complete final JSON object without LF is accepted, matching the pinned reader's `onEnd` and explicit source test. A malformed or incomplete final JSON value fails `PartialFinalFrame`; malformed LF-terminated JSON fails `MalformedJson`. Incomplete/invalid UTF-8 fails `InvalidUtf8`, including at EOF. Empty/whitespace-only records, comments, trailing commas and BOM prefixes are malformed. All admitted protocol records must be JSON objects; other complete JSON values fail `InvalidRecord`. This foundation returns failures to its caller and closes its own reader lifecycle. A later command dispatcher remains responsible for protocol parse responses and any recovery policy.

The native ownership policy rejects duplicate decoded property names at every object depth, including escaped-name duplicates, with `DuplicateProperty`. `JsonData` cannot represent duplicate objects. Upstream JavaScript parsing uses its own last-property behavior; this rejection is disclosed native hardening. Escaped unpaired UTF-16 surrogates fail `InvalidUnicode`; literal invalid UTF-8 is rejected earlier. Valid surrogate pairs and literal Unicode separators remain valid data. Accepted raw JSON value syntax preserves numeric token spelling, property order, nested opaque data, signatures, array order and missing/null distinctions; surrounding framing whitespace and the line terminator are not part of the owned JSON value. No numeric conversion, command inference or opaque-field normalization occurs.

`new JsonlWriter(stream, options: null, ownership: JsonlStreamOwnership.Borrowed)` exposes `WriteAsync(JsonData record, cancellationToken)`. It admits at most `MaximumPendingWrites` calls, including the active one; excess callers receive `PendingWriteLimit`. Admitted calls wait for one serialization gate and retain only their existing immutable input until their turn. The writer strictly reparses retained raw syntax before encoding, since `JsonData.FromElement` can own values obtained from a permissive parser. Comments or trailing commas retained in those values fail sanitized `MalformedJson` before any stream write; the writer remains available. It then compacts whitespace outside strings, preserves raw number/string/value tokens and property order, writes one complete UTF-8 object plus LF, and awaits the stream write and flush before releasing the gate. It has no background writer or encoded-record queue. Callers must await writes to propagate backpressure. Concurrent record bytes cannot interleave through this writer; applications sharing the underlying stream must route all protocol writes through the same writer.

Admission/encoding failures and cancellation while waiting for the gate emit no bytes and leave the writer available. A failure or cancellation after a stream write begins can leave a partial or already delivered record. The writer then closes admission, cancels queued calls, awaits their exit and shared cleanup, and rejects reuse. It never retries or appends another record to an uncertain frame. A successful write means the caller-supplied stream completed write and flush; it does not prove peer delivery or command handling. Broken pipes and other stream errors propagate to the caller.

Both wrappers implement `IAsyncDisposable`. The default `Borrowed` policy leaves the underlying stream open. `Owned` transfers cleanup responsibility after successful construction and awaits its `DisposeAsync` on reader EOF/failure/cancellation/early enumeration disposal or writer disposal/terminal write failure. Repeated concurrent disposal returns the same cleanup task, including a shared faulted cleanup result. Reader disposal cancels active reads and waits for active iterator work, including asynchronous `ReadAsync` finally work, to settle before completing or disposing an owned stream. This settlement obligation also applies to borrowed streams. Paused yielded records own independent data and do not keep an active-work lease; no new work is admitted after disposal. Iterator finalization releases its active-work lease before joining shared cleanup, preventing cleanup from waiting on itself. Reentrant asynchronous disposal from a cancellation callback joins the same cleanup task. Writer disposal closes admission, cancels active/queued operations and waits for admitted calls to leave before owned stream disposal. Cancellation callback failures still permit active-work settlement and attempted owned stream cleanup. Supplied streams must cooperate with cancellation or finish their pending I/O; these wrappers cannot make arbitrary noncooperative I/O terminate. For a shared duplex stream, own its lifetime externally and construct both wrappers as borrowed, avoiding two independent owners.

`JsonlTransportOptions` defaults to 4,096 read-buffer bytes, 1,048,576 frame bytes, JSON depth 32 and 16 pending writes. Read buffers are limited to 1–65,536 bytes, depth to 1–64, and all other limits must be positive; frame size also reserves one integer-safe byte for LF/optional CR. Frame byte limits exclude the LF and one removed terminal CR, and include all other incoming whitespace. A reader retains at most one bounded frame plus its bounded read buffer. A writer validates depth and record shape, bounds compacted output characters before UTF-8 sizing, checks the exact UTF-8 byte count, then allocates one admitted frame plus LF. Depth checks count objects/arrays, ignoring brackets inside strings. These logical bounds do not claim a total process heap cap or bound caller-owned data before submission.

`JsonlTransportException.Failure` supplies fixed diagnostics for frame/depth limits, UTF-8/Unicode, malformed/partial JSON, duplicates, non-object records and pending-write limits. Cancellation remains `OperationCanceledException`; disposed/reused wrapper misuse has standard disposal/invalid-operation diagnostics. Underlying stream and cleanup exceptions remain observable. Record contents are never included in transport-generated diagnostics.

`JsonlTransportTests.Cases()` exposes six groups for parent registration: every-byte/Unicode/CRLF/ownership and pull behavior; exact limits and malformed data; raw-token serialization and pre-effect admission, including permissively parsed owned values; bounded concurrent backpressure and queued cancellation; cancellation/read failure/broken pipe/partial-write poisoning; and borrowed/owned/idempotent awaited cleanup, gated asynchronous read-finally settlement and throwing/reentrant cancellation callbacks. The new projects reference only `PiSharp.Contracts` and framework libraries. Root integration supplies test entry points, solution/helper registration and locked restores. Native execution remains pending at this candidate freeze. This layer implements no dispatch, CLI mode, command IDs, responses/events, dialogs, handshake, session settlement or subprocess lifecycle; those P5 dependencies remain open.
