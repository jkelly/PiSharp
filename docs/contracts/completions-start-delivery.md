# Completions canonical delivery and pull pacing

This candidate corrects the actual canonical HTTP iterator's delivery boundaries. It uses the same Completions invocation owner, mapper, source semantic task, decoder, bounded event channel and cleanup tasks. The public source API and the default `IChatTransport` adapter retain their respective consumer backpressure without branching reader Cancel/Release, abort, exact DONE or EOF policy.

The previous producer could run synchronous request construction, response preparation and body reads before the canonical iterator attached. It published Start into its bounded channel, but a synchronous next advance could acquire and consume the entire body before that Start reached the actual transport consumer. The retained full lifecycle comparison therefore gained 13 canonical ordering observations in candidate `211275673f3a72c10d953a89ebcf978a8238c1f1`. These are recorded in the immutable residual census; this candidate does not rewrite that receipt or the source goldens.

Canonical construction explicitly selects an envelope-owned delivery acknowledgement. After the actual mapper has completed request preparation and the awaited response hook, the producer admits the real StreamStarted envelope to the existing bounded channel and awaits that acknowledgement using its owned cancellation token. The canonical iterator yields the actual Start. Its next advance acknowledges delivery before permitting the same producer to acquire the body. Holding the iterator at Start leaves that body unacquired. Every later immutable frame uses the same handoff: the producer cannot advance the mapper to another frame or read a later SSE event while the canonical consumer holds the current frame. A `ChatRun` consuming this transport acknowledges at its own transport advance; this change does not promise that every outer UI consumer has already consumed the separately buffered ChatRun event.

The Start-only candidate passed its eight new groups but failed the unchanged legacy `CompletionsHttpSseTransportTests.FaultsAndPullPacing` assertion in root's native transport gate: an independent producer read beyond the SSE event between already available TextStarted and TextDelta frames. This revision extends the actual handoff instead of changing that assertion, its fixture, or any comparison.

Root's `a9ed6c1282cce10593636272bcc719a50d1c4c16` gate built cleanly and passed all 660 native groups, including 121 transport groups and the unchanged 99-read pacing assertion. Its complete unchanged 14-case strict comparison still failed all fourteen differential groups, with 421 observations: 202 canonical and 219 public. Twelve of the thirteen new canonical ordering observations were removed. The remaining return-after-Start observation placed outer consumer return before acquisition because the acknowledged producer resumed through a queued continuation. These are reported gate facts, not a full parity claim.

The follow-up creates only the per-envelope acknowledgment without RunContinuationsAsynchronously. The canonical reader signals it outside every lock, and the same waiting producer can resume inline on the actual next MoveNext. For a synchronous acquisition followed by a held asynchronous read, that next operation starts acquisition before yielding back to the outer ChatRun constructor/reader. The direct first Start still has no acknowledgment and leaves the body unacquired. Each resumed producer admits at most one next envelope before awaiting its new acknowledgment, so it unwinds before another consumer advance and cannot build a recursive acknowledgment chain. User hooks continue through their real awaited operations, with the existing producer-context disposal guard. All other completion sources, channel continuation settings and cleanup operations remain unchanged.

Public `StartAsync` explicitly selects bounded enqueue acknowledgement. Healthy `SourceResult` consumption therefore does not depend on opening an event reader. Source emission retention remains a separate argument; it does not select producer I/O or cleanup policy. Public `ReturnAsync` still transfers the bounded source queue to the existing single owned discard drain and retains the provider. Canonical early close still cancels the invocation and joins its actual owner.

The handoff has at most one outstanding completion source per canonical invocation and no extra worker, callback, queue, polling loop or unbounded waiter collection. The producer settles each unacknowledged handoff as canceled when its admission/wait exits. Caller cancellation or iterator close interrupts its actual wait through the invocation token. The existing run disposal, physical cleanup, channel completion and retained discard drain remain the ownership barrier. Normal exact DONE still waits its actual reader cancellation/release; natural EOF still releases; semantic abort remains separate from joined canonical completion.

`CompletionsProductionContext.CloseSourceAsync` admits the actual disposal task before `Finish` marks the final batch. Before delivering each successful final block, the canonical reader now awaits that exact context cleanup task. The joined owner later awaits the same task after SourceResult and joins the retained drain before publishing CleanupCompletion and CanonicalCompletion. The reader does not await a forwarding physical promise whose owner depends on SourceResult: that cycle could deadlock a capacity-one queue with multiple final blocks. A cleanup fault suppresses all successful final envelopes while acknowledging their discard, allowing the producer and bounded queue to settle. The joined owner retains the failure and publishes a sanitized StreamError. Public SourceResult still represents actual semantic production rather than physical cleanup.

The existing `CompletionsSourceRunTests.DefaultToolBarrier` early-close fixture previously assumed body acquisition merely because it had received Start. Its current physical cleanup assertions and messages are retained. The fixture now requests the actual next operation, observes the held read, releases that read and receives a nonfinal ToolCallStarted before closing. It thus owns the asynchronous body whose cleanup it asserts, without changing production to acquire an otherwise unused body on close. The dedicated new immediate-return group separately verifies that close at Start acquires no body/reader and disposes the prepared response and request through their actual ownership path.

`CompletionsStartDeliveryTests.Cases()` supplies twelve actual behavior groups. Its original eight cover synchronous delivery before acquisition; held awaited factory and response hook; acquisition failure after Start and response-hook failure before Start; held actual read with exact DONE/EOF and joined physical cleanup; immediate canonical close at Start; caller cancellation at the handoff including a throwing actual token callback; public result-only consumption with shared concurrent disposal; and public return with a capacity-one owned discard drain. Three additional groups cover the six immutable text/thinking/tool progress frames from one byte-fragmented SSE event without a later read or cleanup; capacity-one delivery of three final blocks for normal/fatal held cleanup with exact DONE and natural EOF; and early close/cancellation at a held immutable frame with joined actual cleanup. The follow-up group directly verifies first Start with zero acquisition, then checks capacity-one ChatRun's actual acquisition/held-read order before outer return and its retained normal or canceled physical cleanup. The groups assert actual metadata, callbacks, reader effects, operations, retained data, terminal disposition, disposal and unchanged private-exception sanitization. No comparison, fixture golden, deadline or prior assertion is removed.
