# Native edit tool and immutable replacement plan

`PiSharp.Tools.Files.EditTool` is a functional P3-06 text-edit slice using the accepted `ToolInvoker`, `PathResolver`, `FileMutationQueue` and `IFileOperations`. It reads and overwrites real UTF-8 files using framework code. It supplies no Node runtime, provider call, process, preview UI or new filesystem implementation. Full edit-tool differential parity and P3-06/phase acceptance remain open.

The constructor is `EditTool(workingDirectory, homeDirectory, mutationQueue, operations?, options?, accessProbe?)`. The queue is required. A composition root must inject that same queue into `ReadWriteTools(..., mutationQueue: queue)` and every coordinated edit/write adapter; separate queue instances cannot coordinate effects. The resolver of that shared queue remains a trusted host responsibility. `LocalFileOperations` provides its existing-segment identity profile, with the same hard-link, missing-path alias and race limits as [read-write-tools.md](read-write-tools.md). The optional trusted `IFileAccessProbe` defaults to `LocalFileAccessProbe`; it is separate from `IFileOperations` so existing read/write hosts retain their interface.

The tool implements `IPreparedToolAdapter`, exposes its owned `Declaration` and read-only mutation snapshot, and supplies `CreateInvoker(requiredPolicy, actionTransforms?, resultTransforms?)` and `CreateDefinition(invoker)`. A host may register this adapter alongside the read/write adapters in one invoker. It must supply argument/action/result bounds that accommodate each supported tool; the generic invoker's default 65,536-character result cap can be smaller than a supported edit diff. The edit factory computes a result cap for bounded escaped display/patch metadata. Direct adapter execution validates structure but is not an authorization boundary; effectful product calls must use the mandatory policy invoker.

## Arguments and final action

The public declaration requires a string `path` and an `edits` array of objects with string `oldText` and `newText`. Legacy fields are absent from that declaration. Source-ordered argument preparation also accepts a single edit object, a JSON string containing an array/object, and a top-level legacy pair. A valid top-level pair is appended after prepared array edits; invalid/missing legacy pairs are ignored when a valid array already supplies edits. Malformed/non-array string input with a valid legacy pair falls back to that pair, matching the source preparation relationship. An initialized empty array survives preparation and final validation; after mandatory policy, execution returns the observed `Edit tool input is invalid. edits must contain at least one replacement.` before queue admission or access/content operations. Missing/malformed structural fields retain the invoker's generic invalid-input admission error. Unknown public properties and unknown edit-object fields are rejected in this native closed-schema profile. Empty `oldText` is rejected by the plan after reading, while empty `newText` supports deletion. The pure `EditPlan.Create` empty-array boundary instead returns the observed plural no-change error, matching the separate source helper.

Preparation performs only lexical path expansion and read-only canonical metadata resolution. It does not use read-tool screenshot/NFD filename probes: the selected source edit resolves `resolveToCwd`. The prepared immutable action uses name/operation `edit`, kind `Path`, an absolute target, empty command arguments, fixed cwd and empty environment. Owned arguments bind `path` to the exact target, retain the original spelling as display-only `displayPath`, and normalize replacements into an owned array. Final validation after transforms requires this complete shape and target/path equality. Policy receives that immutable final target and all final replacement text. Execution uses exactly those fields and repeats structural validation; it does not rederive a target from the original call/display path.

No content read or mutation occurs before authorization. Metadata preparation probes and queue-key resolution are read-only host work. Authorization does not confine hostile native callbacks, external writers or path replacement races. The trusted operations seam must await all owned I/O and cleanup and must not conceal detached effects.

## Matching all edits before effects

`EditMatcher` and `EditPlan` are pure native primitives. The immutable plan contains normalized `BaseContent`/`NewContent`, final BOM/ending-restored `Content`, source offsets and fuzzy-use metadata. UTF-16 indices match JavaScript string offset units, including supplementary Unicode.

The plan strips one leading decoded U+FEFF BOM, detects the source's chosen line ending, and normalizes CRLF and lone CR to LF. Every old/new replacement is also normalized to LF. Every edit initially searches the same original normalized file with exact matching first, then fuzzy matching. Fuzzy normalization applies NFKC, ECMAScript trailing whitespace removal per LF line, smart quotes, Unicode dashes/minus and selected spaces. The explicit ECMAScript trim set avoids the different .NET default whitespace treatment of U+0085 and U+FEFF. NFKC still uses the platform/framework Unicode normalization tables; exhaustive Unicode-version equivalence remains to be qualified.

If any initial match uses fuzzy matching, all edits are matched again against one common fuzzy-normalized base. Uniqueness is counted in normalized space even for an exact match, using non-overlapping occurrences as in source `split(pattern)`. This rejects an exact spelling that also has another normalization-equivalent occurrence. The source's whitespace-only pattern quirk is retained: when fuzzy normalization yields an empty pattern, JS `split("")` counts UTF-16 units minus one. Such a pattern can insert into a one-character file or fail range/ambiguity validation; it is not silently redefined as an ordinary empty `oldText`.

Matched ranges are stably sorted by original offset. Nested/overlapping ranges fail before mutation; adjacent disjoint ranges remain valid. Replacement text created by an earlier edit cannot satisfy a later match or create a duplicate for that later edit. A no-op entry is allowed when another replacement changes the final result; only an entirely unchanged result receives the source-shaped no-change error.

In fuzzy mode, touched ranges are widened to their actual base line groups. Those groups are rewritten from the fuzzy base; untouched groups are copied from the original LF-normalized content. This preserves unrelated quotes, trailing spaces and duplicate-looking line occurrences instead of globally normalizing the file. Final line endings are restored to the source's detected choice and the original BOM is restored. Mixed line endings therefore become the chosen global ending; the source's preservation is not a promise that mixed-ending bytes remain unchanged. With first LF occurring inside a CRLF, the choice is CRLF; otherwise it is LF, including lone-CR-only files.

Not-found, ambiguity, overlap, empty-old, invalid range and no-change failures return source-shaped text with a native failure code. Every replacement is validated and final bytes/diff/result metadata are constructed before the only overwrite. A failure in a later replacement leaves the original file bytes unchanged by this adapter.

## Diff and patch profile

`DiffFormatter` uses a bounded native Myers line diff with whole LF-ending line tokens. It supplies source-shaped numbered `+`/`-`/space display lines, four context lines by default, omission markers for large unchanged gaps and a 1-based first changed line in the new file. Removed lines precede added lines within a contiguous change block. Missing final LF is a line-token difference. A deletion's first changed line may point beyond the new file's final line, as source navigation metadata does.

The unified patch has file-only `---`/`+++` headers, merged context neighborhoods, explicit start/count hunk ranges and `\ No newline at end of file` records. It describes `BaseContent` to `NewContent`, excluding BOM and before global ending restoration. Ordinary path labels retain display spelling; tabs/newlines in labels are JSON-quoted in this native profile. Tests use an independent patch consumer to verify context/removal text, hunk counts and reconstructed output.

The selected source delegates these operations to `diff` 8.0.4. Root subsequently restored a separate exact edit oracle and captured the unchanged whole public tool, including full display, patch and first-changed-line fields, in [the immutable edit corpus](../../fixtures/pi-v0.99.1/edit/core.expected.json). This candidate compares every such field in its five successful corpus cases; native execution of that comparison remains root-owned and pending at authoring. No formatter rewrite follows from an assumed mismatch. Repeated-line ties, larger hunk layouts and control-character filename quoting still need additional genuine observations; the native JSON-quoted control-label profile differs from source raw labels outside this corpus. These are pending qualifications, not permanent exclusions of mandatory edit behavior.

## Access before reading

After authorization and queue admission, execution awaits `IFileAccessProbe.CheckAsync(finalTarget, Read | Write, token)` before its first content read. Both successful and failed callback settlement are followed by cancellation checks. A typed, bounded `FileAccessProbeException.Code` produces `Could not edit file: <displayPath>. Error code: <code>.`; arbitrary callback exception text receives a fixed access-probe failure message. All access failures prevent content reads and writes. Hosts using remote/custom file operations must supply an access probe for that same backend; the default checks the local filesystem. Trusted callbacks must settle their owned work before returning/throwing; a canceled callback that is still settling retains the reservation.

The qualified runtime reports Node 24.19.0 with libuv 1.52.1. Its Windows access implementation calls `GetFileAttributesW`, admits read access when metadata succeeds, and rejects requested write access on ReadOnly regular files with `EPERM`; ReadOnly directories remain admitted. The native local probe follows that metadata profile and does not substitute a read/write open or an ACL test. Linux/macOS use libc `access(path, mode)` with real-ID semantics and bounded symbolic errno mapping, retrying interrupted calls. Unknown unmapped errors retain `UNKNOWN`; no complete platform/error-code equivalence is claimed. See [libuv Windows access](https://github.com/libuv/libuv/blob/v1.52.1/src/win/fs.c#L2356), [libuv Unix access](https://github.com/libuv/libuv/blob/v1.52.1/src/unix/fs.c#L1604) and [Node's Windows ACL caveat](https://nodejs.org/download/release/v24.19.0/docs/api/fs.html#fsaccesspath-mode-callback).

The probe acts on the immutable authorized target. This canonical-target profile can differ from source probing a lexical symbolic-link path: [GetFileAttributesW returns link attributes](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileattributesw). Real-ID permission results also depend on the actual Unix process credentials. Access does not guarantee later I/O success or prevent path changes between operations. Cross-platform, symlink/ACL, unusual-error and source preview-access qualifications remain required; no permanent exclusion or sandbox claim follows from this local probe.

## Commit conflict, cancellation and effect state

All reads, planning and the write occur within the shared same-key reservation. Before commit, the adapter performs a second bounded read and compares its exact owned bytes to the first read. A mismatch returns `OutsideChange` with `writeAttempted: false`; it preserves the outside writer's bytes. A failed second read also prevents this adapter's write. This reread is a stronger native conflict profile; upstream `edit.ts` has no equivalent second read. It detects byte changes at that instant, not identical-byte identity replacement, changes that were later reverted, or changes between the comparison and write. There is no atomic compare-and-swap, handle-based confinement, rollback or temporary-file replacement.

Cancellation is checked before admission and after awaited canonical resolution, reads, planning/diff construction and write settlement. The token reaches file I/O and bounded diff work. A queued edit waits behind its predecessor; its read sees the preceding committed content rather than a stale pre-queue plan. A canceled admitted overwrite retains its reservation through the operations callback's awaited cleanup. Same-key read/write/edit successors cannot start during that cleanup; unrelated keys may proceed. A callback that ignores cancellation can delay completion; there is no detached timeout or forced cancellation of trusted native code.

Failures/cancellation include `details.fileOperation` with a stable code, `writeAttempted` and `writeCompleted`. Attempted means the write callback was entered; completed means it returned successfully. An exception/cancellation can leave a truncated or partial file even when completed is false. If the callback returned successfully after cancellation, completed remains true. The outer invoker preserves that owned effect record when appending cancellation diagnostics. A queued/admission failure before this adapter's callback need not supply an effect record. Arbitrary host exception text is replaced by a fixed error; stable typed access errors use the source-shaped access wrapper described above. Raw arbitrary exception wording remains outside that owned error profile.

Success returns `Successfully replaced N block(s) in <displayPath>.` and owned `details.diff`, `details.patch`, `details.firstChangedLine`. Native diff/resource failures occur before writes, while upstream generates diff/patch after its write. This stronger ordering avoids a formatter error following a successful native mutation; it is not described as exact source effect-order parity.

## Bounds and evidence

Defaults are 1 MiB original input and final encoded output, 64 replacements, 524,288 argument characters and 4,096 path characters. Native option ranges permit 1..64 MiB byte caps, 1..8 Mi argument characters, 1..65,536 path characters and 1..1,024 replacements. Public and normalized owned arguments must both fit their bound. NUL/malformed UTF-16 arguments are rejected; strict UTF-8 file decoding and unsupported binary/control admission follow the read/write text profile. Printable valid UTF-8 bytes are treated as text; this is not complete binary identification. GIF/WEBP signatures and invalid UTF-8/control data are explicitly unsupported; images and other encodings remain unfinished.

Pure plan inputs/output and aggregate edit text have logical character bounds. Default diff caps are 8,192 old/new line tokens, 4,000,000 frontier/equality work steps, 1,000,000 retained trace cells and 131,072 characters each for display and patch. Context is configurable from 0 to 32. String equality/NFKC cost, callbacks, owned bytes, string/JSON copies and temporary output allocations are additional bounded work/memory; these are not exact CLR heap limits. The shared queue's caps remain host-configured.

The original twelve authored offline groups cover source argument variants; reverse/disjoint/all-original matching; unchanged bytes on invalid plans; fuzzy preservation and normalization-equivalent ambiguity; BOM/mixed endings/supplementary text; numbered/context diff and independent patch round trips; exact final policy handoff/denial; external byte changes; two queued edits reading prior commits; shared read/write/edit cancellation cleanup; cooperative awaited-boundary cancellation and known late writes; resource rejection and partial write faults/recovery. Root reported that frozen developer candidate passed 284 developer checks, including these twelve groups; that was before this access/differential candidate and is not independent acceptance.

Four new groups cover the complete twelve-case [genuine source corpus](../compatibility/edit-differential.md), actual local existence/ReadOnly-file/ReadOnly-directory behavior, settled access cancellation/failure, and empty-versus-malformed admission. Input/expected bytes are SHA-256 checked before JSON parsing. Every available pure helper field, public prepared input, success content/details, source generic failure name/message, and exact before/after file length/hash/base64/UTF-8/equality flag is compared without string/newline/diff normalization. Whole source observations and whole owned native results remain in structured evidence, and differences are collected before the corpus assertion. Filesystem effects stay within fresh owned temporary roots; ordering uses Tasks/gates. No build or tests were executed by this implementation agent; root-owned isolated execution of this candidate is pending.

The comparison maps native typed `TextContent` to source `{type:"text",text}` and native InvalidArguments/ExecutionError records to the source's generic `Error` name plus exact message. This is a declared portable result/error envelope, not a claim that a returned .NET failure record is a thrown JavaScript Error. Native failure kind, termination state and effect metadata are retained separately. Source preparation mutates some supplied arrays/objects; owned native input stays unchanged and its logical prepared fields are compared after projecting absolute target/display-path bookkeeping. Source preview observations are retained completely, but this candidate supplies no public native read-only preview orchestration API. That remains a required follow-up, not a passing or permanently excluded comparison. The corpus's twelve exact cases establish no uncaptured cancellation, permission, path, large-input, UI or cross-platform parity.
