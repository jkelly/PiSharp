# Registered extension hooks in prepared tool execution

This experimental native integration connects registered `tool_call` and `tool_result` reducers to `ExtensionAgentBinding`, the existing `ToolInvoker`, the accepted scheduler, and durable `PersistentAgentSession` event barriers. Input admission is a separate required integration. The remaining extension events, complete source qualification, and an approved SDK remain unfinished; this contract does not freeze the experimental API.

`ExtensionAgentBinding` captures tools and both hook families from one actual registry snapshot and revision. It creates one long-lived `RegisteredExtensionEventDispatcher` for that binding, retaining configured concurrent/depth accounting across invocations. `ExtensionAgentBindingOptions` exposes `ToolEventDispatch`, `MaximumToolEventHandlers` (default 256, admitted range 1–4096), and an optional awaited trusted `ReportEventDiagnostic` sink. The registry and its extensions remain borrowed. An idle host must explicitly publish a new binding and declaration message to use a new generation or revision.

## Preparation and effect authority

The existing `ToolInvoker` constructor and legacy executor methods keep their signatures. Its named `WithPreparedHooks` factory opts into the neutral `IPreparedToolHooks` seam. The actual sequence is:

1. Admit the finalized assistant and original tool call, resolve one registered adapter, prepare it, and run the adapter's mandatory initial full-schema/action validation.
2. Await the captured registered call reducers. A first `block:true` stops their chain and returns a fixed sanitized `Blocked` failure, retaining only the explicit boolean termination flag. A thrown or invalid call hook yields a sanitized `HookError`; neither path executes effects or result reducers.
3. If arguments were replaced, construct an owned preparation view whose assistant content contains the same replacement call reference. Reprepare through the **same resolved adapter**. The original committed assistant, call, registration target, and invocation context are retained unchanged.
4. Await every configured action transform, then validate the complete resulting arguments and action again. Mandatory policy receives the identical final immutable action that execution receives. A hook replacement or nonblocking decision cannot grant authorization, change the resolved tool, or bypass validation or policy.
5. Execute through the accepted progress scope and join every admitted publication before finalization. Await existing host result transforms, then registered result reducers. Final result admission still uses the configured complete strict codec and invoker limits.

The schema validator remains an explicit trusted host seam. It must validate the entire registered schema and reject unsupported schema constructs; this bridge supplies no substitute schema validator or native-code sandbox. An extension action retains its captured owner/generation/registration target and cannot acquire command/path authority through an argument patch. Host transforms, adapters, and policy remain trusted code. Policy and callbacks run outside registry and Agent locks.

## Results and scheduler disposition

Registered result callbacks receive effective final-action arguments, tool identity, the complete admitted result, and actual execution error disposition. The Runner-shaped `isError` field in their supplied event is seeded from that disposition. The tool's original owned result remains separate, including its own `isError` property, opaque fields, numeric tokens, and missing/null presence.

The existing typed reducer processes callbacks in registry owner/insertion order. Only `content`, `details`, `structuredContent`, `isError`, and `usage` reduce result state. Replacing content without a structured-content field clears stale structured output. Explicit null is retained for subsequent callbacks. Invalid patches and callback errors produce bounded sanitized diagnostics and continue to later result callbacks. If configured, the trusted diagnostic listener is awaited before final result publication; its failure becomes a sanitized finalization failure retaining known completed output.

After all callbacks, the text-only projection follows the public coding Agent session's `hook.content ?? result.content ?? []` and `hook.isError ?? executionIsError` rules. It then supplies those five fields to the existing `SourceToolAfterHook.Apply`; there is no second result-mapping implementation. Nullish details/usage preserve the original values. Aggregate non-null content with null/missing structured output clears the original structured value. Unknown hook-patch fields, including `terminate`, are not copied. Original unknown result fields stay in the execution result; the accepted canonical tool-message materializer controls what enters model and durable messages.

`IFinalizedToolExecutor` is the optional neutral transport for `FinalizedToolExecution(Result, IsError)`. `ToolBatchScheduler` uses its separate disposition without rewriting the result object's raw `isError`. Legacy `IToolExecutor` implementations retain their old behavior and compatibility methods still return `ToolResult`. Both scheduling modes share this execution path. Existing source after hooks and legacy complete-result hooks remain available; a later configured hook retains its existing semantics. No progress mode, quota, callback receipt, scheduling order, or durable serializer is changed.

## Leases, cleanup, and durability

Each family dispatch acquires all of that family's participating owner/generation callback leases before its first callback. The actual registry supplies the ordered callbacks directly; there is no mirror handler store. The registry-wide dispatch cap and retained registration charges remain active across bindings and tools. Removal preserves an already admitted family dispatch, excludes future snapshots, and prevents a stale captured binding from starting new work through a removed registration. Tool invocation obtains its own actual registry lease after mandatory policy; these phases do not hold a single invocation-wide lease that would authorize a removed tool.

Requested work/session/owner cancellation joins actual callback cleanup before returning. Owner/registry disposal retains accepted reentrant-disposal protections and joins admitted callbacks and extension cleanup. Concurrent durable coordinator disposal shares settlement. Cancellation is cooperative; a callback that never settles can hold its owned lease. A binding does not dispose borrowed registry state.

In the real session composition, the assistant end-event checkpoint is acknowledged before tool preparation and registered hooks begin. Final tool-result end-event checkpoint and awaited listeners settle before the next provider request. Append or uncertain checkpoint failure prevents continuation and preserves the coordinator's fault and acknowledged state. No automatic retry, recovery, or unacknowledged checkpoint success is introduced. Execution-only structured/opaque output continues to follow the accepted model-message projection.
