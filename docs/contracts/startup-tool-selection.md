# Explicit startup tool selection

Baseline: Pi v0.99.1, commit `d86654abb8862e201933517d6f1fce9f88dd117f`.

`session create`, `prompt`, `resume` and `rpc` accept `--tools` or `-t` with comma-separated names. Interactive and terminal commands forward their arguments to the same RPC host. Names are trimmed, empty comma fields discarded, and repeated options use the last value. An explicit empty value selects no tools. Explicit CLI selection overrides `defaultTools` loaded from explicitly admitted user/project settings paths.

The existing settings merge remains unchanged: a later modifier-only tool array appends to an earlier array, including the source's empty-array append quirk. The pure projection filters non-string entries. A present non-array resolves to an empty list; an absent property has no configured selection. Plain names establish the base; modifier-only nonempty arrays start from read, bash, edit, write. Ordered `+name` adds missing names, `-name` removes the first occurrence. Stable deduplication occurs at installation, after modifier resolution.

Source evidence:

- [CLI argument parsing](https://github.com/badlogic/pi-mono/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/cli/args.ts): `--tools`/`-t` parsing.
- [Settings projection and merge](https://github.com/badlogic/pi-mono/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/settings-manager.ts): `mergeDefaultTools`, `resolveDefaultTools`, `getDefaultTools`.
- [SDK precedence](https://github.com/badlogic/pi-mono/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/sdk.ts): configured defaults and explicit tools determine initial active names.
- [Session startup](https://github.com/badlogic/pi-mono/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/agent-session.ts): constructor restores transcript tools only if initial names are undefined; `_buildRuntime` appends default-active declarable extensions for settings and deduplicates active names.

Configured initial names now resolve before restored tools are bound. The transcript is still structurally validated and bounded; only currently admitted selected declarations form the effective runtime. A recorded declaration that remains selected must match its current binding. A restored declaration that differs from its current binding is restored by name with the binding's declaration (with or without a configured selection), and a restored tool that is now hidden is skipped and kept pending, as Pi 1.1.0 `_restoreToolsFromTranscript`/`_applyToolLoadout` do; the restored loadout is then recorded before use. Tree navigation to a branch with no system message keeps the current tools as the logical selection and records them at the next request. A restored unavailable declaration follows Pi 0.99.2 `_restoreToolsFromTranscript` (owner decision for the 1.1.0 sync): it is left out of the restored loadout, which is recorded before the session is used, and stays pending until it registers (a later catalog publication such as a connecting MCP server activates it), unless --tools/--exclude-tools keep it out; a prompt or a deactivating selection drops it. Tree navigation restores the target branch the same way. Read or explicit empty selection can replace an unavailable former binding without acquiring it. The initial durable delta removes the recorded names, then adds the effective selection through the existing owned configuration checkpoint before opening returns. Reporting and validation failures precede that checkpoint; uncertain append outcomes retain existing storage poison/fault receipts and owned cleanup.

Selection admits only already registered, declarable tools. This profile registers read, edit, write and ls, plus Bash only after its existing explicit authorization; find/grep remain unavailable here. Unknown/unavailable names are ignored, as Pi 1.1.0 `sdk.ts` (initialActiveToolNames) and `agent-session.ts` `_applyToolLoadout` drop them: they select nothing and never become pending (owner decision for the 1.1.0 sync; formerly InvalidArguments before session creation/opening). Only malformed `--tools` lists (mixed or pattern `+name`/`-name` entries, `args.ts` `getToolListError`) and a flag without its value remain argument errors. Settings selection appends already admitted default-active direct/model-only extensions. Explicit CLI selection includes only requested admitted declarable extensions. It never loads extensions from settings or changes file/process grants.

Explicit CLI selection carries task10's immutable lifetime allow/exclude policy into the runtime registry. Candidate registrations are filtered before callable metadata and loadout preparation. Invocation-owner clones retain the same policy and diagnostic-drain ownership. Capped activation of a name outside the policy is ignored like an unknown name (Pi 1.1.0 `setActiveToolsByName`; formerly UnknownTool before a durable mutation), so an unchanged effective selection appends nothing; settings-only selection remains unrestricted. Lifecycle factories carry the exact policy through new/open/fork/clone and refreshed cwd-dependent registries. A custom replacement factory must admit its target with the same policy; widening factories are rejected before source retirement. The new initial selection projection omits Hidden/Codemode/Deferred entries. Legacy explicit activation and ordinary recorded replay retain every exposure except Hidden, including Codemode and Deferred; catalog filtering and forbidden-name checks still enforce lifetime caps. Existing file/process grants, denied-package behavior and policy-mediated export write authority are unchanged. Actual reload owners must retain this same policy on each incoming catalog. Additional no-tools/exclude CLI flags remain coordinator-owned and are not advertised by this slice.

Pi 1.1.0 name selection (owner decision for the 1.1.0 sync): unregistered or capped-out names in an initial selection (`--tools`, `defaultTools`, `SessionRuntimeRegistryOptions.InitialActiveToolNames`, MCP discovery) and in explicit activation (`SetActiveToolsAsync`, `ScheduleToolActivation`, the extension `setActiveTools` facade) are ignored instead of raising `SessionRuntimeRegistryFailure.UnknownTool` or InvalidArguments, and they do not become pending. A tool a `--tools` allowlist names that registers later activates at that catalog refresh (`_refreshToolRegistry`; the registered MCP refresh uses `AllowedToolSelection.SelectReloaded`). Strict resolution that is not name selection is unchanged: resolving a transcript or an explicit system message that declares an unbound tool still fails with UnknownTool, a mismatched declaration with DeclarationMismatch, and malformed or oversized names with InvalidRegistration or ResourceLimit. Covered by the CliSync cases `selection.initial-tools-settings-and-sdk-names-ignore-unregistered`, `selection.allowlisted-mcp-tool-activates-when-it-registers` and `selection.explicit-activation-ignores-unknown-and-capped-names`.
