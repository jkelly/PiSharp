# Explicit-path session log store

`PiSharp.Sessions.Storage.SessionLogStore` is a bounded append store with one serialized writer lease, immutable committed state, and an explicit flush-to-disk checkpoint. `CreateNewAsync(path, validatedHeader, options, token)` exclusively creates an explicit new file and commits its header. `OpenAsync(path, options, token)` admits an existing supported log through the [recovery reader](session-log-reader.md). `AppendAsync(ImmutableArray<SessionEntry>, token)` commits one ordered batch of owned entries. `DisposeAsync()` shares one asynchronous cleanup operation among callers. This is a portion of [P4-02](../plans/04-sessions.md), not complete session, durability or phase acceptance.

Public Pi v0.99.1 at `d86654abb8862e201933517d6f1fce9f88dd117f` supplies the wire record shapes and append order in [session-manager.ts](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/coding-agent/src/core/session-manager.ts). Its `_appendEntry` updates memory/index/leaf before `_persist`; `_persist` delays first-file creation until a user/assistant conversation and then uses `wx` and `appendFileSync` JSONL writes. That seam does not provide an explicit fsync acknowledgement. This store creates the requested header immediately and publishes memory after its durable checkpoint. Those are declared native decisions, not demonstrated upstream durability parity.

The default backend opens `FileMode.CreateNew` or `FileMode.Open`, `FileAccess.ReadWrite`, `FileShare.Read`, asynchronous/sequential options. Existing paths are never overwritten by creation. No parent directory, default Pi/PiSharp home, import copy, replacement, migration, repair or truncation is created automatically. Missing existing paths fail. A failed creation may leave a new empty/partial file for explicit inspection; cleanup releases the stream and never removes that evidence. Header validation, limits and precancellation run before creation. Once creation begins, caller cancellation is shielded through the initial header checkpoint.

Existing logs require `Status == Complete` and `SourceComplete` from the bounded reader, then additional tree identity checks. Damaged/unsupported/future logs, duplicate tree IDs, empty tree IDs, forward/missing/self parents and known pending assistant messages cannot admit a writer. The reader remains available separately for their immutable byte inspection. Open performs no newline repair and never rewrites an imported source. Raw fields, opaque metadata and numeric tokens follow the [codec profile](session-entry-codec.md). Append does not convert provider messages or restore CLR type names/delegates.

`Snapshot` is an immutable `SessionLogStoreSnapshot` with `Header`, ordered tree `Entries`, ordinal `ById`, `LeafId`, `CommittedByteLength` and `Sequence`. Header identity is separate from tree identity. Roots use null parents; other parents must refer to earlier committed or earlier batch entries. Multiple roots and branches are allowed. `LeafId` is the last appended physical tree entry, not a context projection. Open reconstructs this state from the log and starts the local batch checkpoint sequence at zero. Each successful append increments that sequence once. The sequence is not persisted or a cross-process globally unique identifier.

Each append first awaits the writer semaphore with the caller token. Under that serialization boundary it clones/validates every body with the codec, reserves all batch IDs in a candidate immutable index, verifies parent ordering/finalized known assistant status, serializes and bounds the whole batch, and builds the candidate snapshot before any file operation. Invalid/default/empty batches are rejected. Failed preflight releases all candidate ID reservations and leaves bytes/state/lease usable. IDs are caller-supplied compatible strings; this primitive does not generate timestamps or IDs. An assistant `stopReason: pending` is rejected; other supported stop reasons and inert extension state retain their codec meaning.

Append emits compact UTF-8 JSON with one LF per new record. Existing original bytes stay unchanged. If the existing observed source ended without LF, the first append explicitly writes one separator LF before the new batch. This also handles a trailing allowed whitespace-only physical line. Entry byte offsets, length and final committed length include that separator when present. Opening alone performs no framing write.

The commit stages are accepted candidate, write, asynchronous flush, synchronous `FileStream.Flush(flushToDisk: true)`, checkpoint finalization, then one atomic snapshot publication. A successful `SessionLogAppendResult` supplies distinct `Accepted`, `Flushed`, `DurableCheckpointAcknowledged`, `Sequence`, `ByteOffset`, `ByteLength`, new `Entries` and the exact published `Snapshot`. All three stage flags are true only on successful return. There are no intermediate successful results or unflushed public snapshot updates. The byte-length check before positioning additionally detects an unexpected length change while the lease is held.

The final prewrite token check establishes the cancellation boundary. Cancellation while waiting/preflighting causes no append effects and preserves state. Once writing begins, commit I/O uses no caller token; a late caller cancellation does not turn a known successfully committed batch into a cancellation exception. A cancellation callback can request disposal without synchronously waiting for I/O under a state lock. The writer finishes its current commit, and shared cleanup then completes. Callers must await asynchronous disposal; synchronously blocking on it from a cancellation callback is not supported.

Write, flush, durable-flush or checkpoint-finalization exceptions poison the lease. The old immutable snapshot stays published, later appends fail `Poisoned`, and the caller must close and explicitly inspect/reopen. `SessionLogStoreException` exposes fixed `Failure`, `MayHaveWritten` and `DurableFlushCompleted`, with no payload/path/inner exception. `MayHaveWritten` is conservatively true once write invocation begins, including partial-write failure. `DurableFlushCompleted` becomes true only after the flush-to-disk call returned successfully. A failure during checkpoint finalization can therefore leave a complete durable record on disk without a successful caller acknowledgement or published snapshot. The store never retries that batch, reruns tools or repairs it automatically; explicit reopen can reconstruct whatever complete records the reader validates. Flush-to-disk failure does not prove that data was lost or that no storage effect occurred.

Concurrent appends are serialized across the entire I/O checkpoint by a private semaphore. The separate short lifecycle lock only creates the shared disposal task; trusted I/O runs after releasing it. No provider/extension callback or plugin hook runs under that lock. Disposal marks the store closing immediately, bars queued/new appends, waits for the active writer, and awaits owned storage disposal once. Concurrent disposers receive the same task and the same completion/failure. Cleanup errors are sanitized as `CleanupFailed`. Initial create/open failure also awaits owned cleanup while preserving the original failure/cancellation cause. Snapshot observations remain available after poison/close.

Options default to the reader's 16 MiB source/growth cap, 4 MiB line cap, 100,000 physical lines/records and codec limits, plus 256 records per batch. Appends charge the complete newly encoded bytes, including LF/separator, against the committed total. Record count includes the header; physical line counts include existing allowed blanks. Per-line/codec/batch/count/total failures happen before writes. These bounds are not a total heap cap or a bound on externally queued concurrent caller tasks.

`ISessionLogStorageFactory`/`ISessionLogStorage` is a trusted host fault/I/O seam. Its `LocalFileFlush` capability must be backed by actual file flush-to-disk behavior. Storage declaring `Unsupported`, including the test's in-memory model, is rejected before a durable acknowledgement. The native factory is available as `DefaultStorageFactory` for decorators. Deterministic faults/gates wrap that actual backend's write, asynchronous flush, durable flush, checkpoint return and cleanup. This capability declaration is not a security mechanism against a malicious trusted backend that lies about its implementation, and the interface is not an extension execution hook.

On Windows local files, `FileShare.Read` excludes another cooperating .NET writer open while permitting read-only inspection by a reader that shares the existing writer's access (for example, read-only `FileAccess.Read` with `FileShare.ReadWrite`). The reader's convenience `ReadFileAsync` uses stricter sharing and is intended after lease release; a compatible owned stream can be passed to `ReadAsync` during the lease. The authored fixture invokes a separate native child process while the first lease remains live, requires writer-open denial, then opens successfully after lease release. Root's runner dispatches `--session-store-lease-probe <path>` to `SessionLogStoreTests.RunLeaseProbeAsync` before normal test argument parsing. Unix, network shares, external native writers ignoring applicable OS sharing, atomic namespace replacement and remote storage need separate qualification. This store is not an OS security sandbox.

The acknowledged durability boundary is successful completion of the native asynchronous flush and flush-to-disk call for the appended file bytes. Directory-entry durability for first creation, every filesystem/storage controller, power-loss outcomes, network filesystem guarantees and cross-platform lease behavior remain unqualified. The checkpoint names the executed native boundary; it does not promise survival of every hardware failure. No in-memory model is counted as durability evidence.

Eight authored native test groups cover actual create/append/dispose/reopen bytes and immutable snapshots; overwrite/admission/future/damaged/ID/parent/pending/fake-durability rejection; untouched nonterminated existing prefixes; gated writer serialization and shared successful/failing cleanup; partial write/asynchronous flush/durable flush/checkpoint faults with poison/state/explicit-reopen assertions; precancellation and known commit after late cancellation with a disposal callback; inclusive batch/record/line/total limits; and an independent Windows child writer lease. Root owns registration, isolated execution and review evidence. This document makes no completed P4-02, crash-matrix, cross-platform, full durability or eight-phase gate claim.
