# Awaited native tool progress

This prerequisite supplies invocation-scoped progress through the existing tool executor, prepared-action invoker and genuine scheduler. It targets public Pi v0.99.1 at `d86654abb8862e201933517d6f1fce9f88dd117f`, with a native .NET 10 runtime and no Node dependency. It does not implement Bash, process streaming, ordinary output NUL support, partial result patches, an RPC serializer, or a complete source progress parity claim.

## Public callback seam

`ToolProgressCallback` has signature `ValueTask (ToolResult partialResult, CancellationToken cancellationToken)`. The caller awaits one complete partial result before reporting another. `IToolExecutor.ExecuteAsync(ToolInvocation, ToolProgressCallback, CancellationToken)` and `IPreparedToolAdapter.ExecuteAsync(PreparedToolAction, ToolProgressCallback, CancellationToken)` are default-interface overloads with a different arity; their defaults invoke the existing two-argument execution methods. Existing implementers need no new method. Existing constructors, positional results/options and deconstruction remain unchanged.

`ToolInvoker` implements the new overload and preserves its existing two-argument public method. Both methods use the same final-action preparation, validation, transforms and policy path. Only execution receives the callback. An explicit callback must be non-null. A caller using the old method receives no observations, while a progress-capable adapter still receives a scoped callback that validates each reported value. The callback token combines the invocation token and the reporter's token. Adapters should pass their actual execution token and await every report.

Partial values are complete immutable `ToolResult` values, independently of the final result. The invoker uses its existing `Normalize` path before publication: initialized/bounded content, ordinary details/text/failure budgets, Unicode/NUL policy, failure-to-error normalization and separately bounded structured metadata. The accepted structured admission strictly reparses retained raw syntax after charging size, validates finite numbers, Unicode and depth, and keeps the original owned value and raw tokens. Permissive `FromElement` comments or root/nested trailing commas cannot enter structured progress. Progress neither runs final result transforms nor calls scheduler afterhooks. Partial content, details, errors, termination and structured metadata do not implicitly become final fields.

## Lifetime and backpressure

Each invoker execution and scheduler execution owns a scope retaining at most one in-flight delivery and its latest delivery task. Concurrent or reentrant reports on that invocation fail with a fixed `InvalidOperationException`; the API requires awaiting reports rather than building a background event queue. Closing the scope rejects further reports and awaits the admitted delivery before result transforms, afterhooks and terminal observation. A callback failure is retained even if trusted executor code catches it, and scope closure observes the owned failed delivery. An executor that starts a report without awaiting it cannot make finalization overtake that admitted report.

The scheduler emits `ToolExecutionUpdated(ToolInvocation Invocation, ToolResult PartialResult)` from the actual callback path. Invocation correlation is the original assistant, tool-call instance and source index. Generic executors receive the scheduler's existing structural result checks; bounded final-result admission is supplied by the actual `ToolInvoker`. This change does not claim strict normalization of arbitrary trusted scheduler executors or outer afterhook replacements.

Parallel execution uses a bounded channel with one queue slot shared by progress and finalized outcomes. One consumer awaits the sink for each observation. Every update has a delivery acknowledgement; its producer waits for that acknowledgement before returning. There is one execution task per admitted tool and at most one pending update per invocation, including writers waiting for the channel slot. No list of event tasks grows with update count. These limits are relative to the already admitted batch size; the existing scheduler does not gain a new batch-size limit or total heap guarantee.

Updates and ends follow channel admission order. An invocation's end is enqueued only after its admitted progress, executor cleanup, result transforms and afterhook finish. Completion events retain observed finalized order, while final transcript results remain in assistant source order. Parallel preflight is still sequential before execution. A sequential tool still serializes the batch; its updates directly await the same sink inside its execution, followed by its existing final end/message sequence. Immediate preflight errors do not create progress callbacks.

During progress/end delivery, republishing an update to the same batch fails explicitly before waiting on its single consumer. This prevents a sink callback from enqueuing another invocation's update and waiting for itself. Each invocation also rejects same-scope recursive reporting. Arbitrary trusted callbacks that await unrelated cycles or ignore cancellation can still delay settlement; this contract does not detect all user-created task dependency cycles.

## Cancellation and failures

Reporter/invocation cancellation before update admission prevents publication. An enqueued parallel update remains owned until its delivery succeeds or fails; invocation closure cannot overtake its acknowledgement. On a sink fault, the parallel consumer closes the channel, rejects queued acknowledgements and releases blocked writers before canceling owned execution and awaiting every admitted task. Final-outcome publishers tolerate the consumer's closed channel. This ordering prevents cleanup from hanging behind an acknowledgement that no consumer will fulfill. Sequential progress faults cancel that execution, await its scope and cleanup, and propagate the sink failure before any final end.

Cancellation that faults delivery uses the same cleanup path. Cancellation callback faults remain observable alongside the original sink fault. No completed output is presented as a durable commit merely because a callback was entered. Adapters and sinks own their cleanup and must cooperate; no detached process kill, retry, rollback or forced cleanup timeout is added.

Final result transforms and scheduler hooks retain their existing whole-result replacement semantics, structured retention and error behavior. A progress failure may make execution fail, but no partial value is automatically promoted to a completed result. The prior structured-result cancellation/finalization retention contract remains intact for valid completed executor results. Ordinary output NUL admission and existing parsed-JSON boundaries outside structured results remain separate work.

## Transcript and source boundary

Progress is observational. The scheduler creates no `ToolResultMessage` for an update, and Agent canonical history/persistence consumes only finalized message events. Structured progress remains on `PartialResult`; structured final output remains on the finalized outcome. Neither becomes a new model/durable message field. The parent owns any subsequent explicit RPC event projection.

The pinned [AgentToolUpdateCallback](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/types.ts#L456) reports partial execution results. [emitToolExecutionUpdate](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts#L778) emits the tool identity, raw arguments and partial result. [executePreparedToolCall](https://github.com/earendil-works/pi/blob/d86654abb8862e201933517d6f1fce9f88dd117f/packages/agent/src/agent-loop.ts#L820) closes update acceptance when the tool settles and joins its collected update promises before finalization. The native callback instead makes backpressure explicit, bounds pending delivery, and rejects late callbacks rather than silently ignoring them. Native updates require complete `ToolResult` values; the source's optional/undefined details, images, usage, partial-patch rendering, snapshot timing and shell throttling are not certified by this slice. These are declared native lifecycle choices pending genuine captured progress comparison, not waivers of required full-product behavior.

## Authored evidence

`ToolProgressTests.Cases()` supplies eight gated groups: legacy implementer compilation, policy-before-progress and normalized awaited metadata, malformed permissive metadata/finite/Unicode/depth/size rejection, parallel slow-sink ordering/backpressure, admitted unawaited report joining before finalization with whole-result hook replacement and late-call rejection, cancellation cleanup in both modes, output faults with queued acknowledgements/blocked writers and owned cleanup, and concurrent/reentrant/same-batch self-wait rejection. No timing sleeps determine expected order. Test data is native authored evidence, not a substituted source corpus.

At handoff the tests are **NOT RUN**. The parent owns harness registration, isolated build/test execution, independent review, immutable commit and RPC projection. This slice changes only the four named Agent files and adds this document plus the focused test file.
