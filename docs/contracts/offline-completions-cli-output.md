Every previous case name, order and default provider selection remains. The existing raw-byte child capture, output gates, complete-log reader and exclusive reopen helpers are reused. Literal chunk helpers supply input only; expected output text, usage, identities, bytes and lifecycle assertions are independently stated.

Print's Completions scenario performs actual allowed read and write effects across three provider turns. It requires exact final UTF-8 bytes containing NUL, CJK, a supplementary character, U+2028/U+2029, CR/LF and tab, plus the single LF added by the final-text adapter. Actual write content contains inert NUL and is compared against exact UTF-8 file bytes. The complete canonical write argument object and successful result link must survive independent resume and selected older-leaf branching; the subsequent real projected HTTP requests must contain the saved arguments and acknowledged prior results. Prior session, script, source and sibling bytes remain unchanged. Finalized assistants retain the Completions API/model/provider, authored cached-token accounting, response ID and raw finish reason. An explicit report after print still requires durable byte acknowledgement.

Print lifecycle controls retain real denied effects and unfinished provider-stream failures. A successful final assistant after a denied tool prints its text while returning the existing nonzero command status; a failed assistant suppresses known partial stdout and returns fixed `ProviderFailed` stderr. Held write and flush faults use the actual public command with the Completions profile. The borrowed output is entered only after the coordinator closes and an exclusive durable reopen verifies the acknowledged final state. Failure preserves completed effects and durable bytes, joins the held writer, reports possible effects, and retries neither output nor execution. Pre-cancellation produces no output or session acquisition. This does not claim console signal delivery or upstream exit-code parity.

JSON's separate-process scenario checks the actual opening session header, delta-only records, finalized assistants and tool results, turn-end records, and final `agent_end`. Every authoritative `message_end` must match an identical physical durable body. The Completions tool fragments yield two starts, four argument deltas and two validated ends. Decoded text deltas concatenate to the independently authored final text; JSON contains no physical unescaped NUL. The complete final write arguments equal the canonical durable call, and actual NUL/Unicode file bytes remain exact. Full history correlation, usage/cache/response metadata, independent resume and selected branch, rejected NUL file reads, denied effects and unfinished provider-stream failures retain their assertions.

The additional JSON lifecycle group holds the actual assistant `message_end` flush before tool execution and proves that the target is absent while the assistant is already durable. A second control holds the acknowledged tool-result flush before continuation. It then checks either successful full delivery or poisoned write/flush failure: completed file bytes and durable records remain, the subsequent successful assistant is absent, no output retry occurs, and the closed log can reacquire its exclusive writer lease. Gates run through the real command and HTTP profile; no provider result or final output substitutes for the event barrier. An unacknowledged stdout record on a failed flush is not described as acknowledged delivery.

It uses scalar-boundary chunks of at most 4,096 characters and the same authored literal chunk helper, with fewer than 256 DTOs and each raw DTO below the inherited 65,530-character admission bound.
