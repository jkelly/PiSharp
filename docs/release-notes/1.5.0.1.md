**Unpublished; release preparation in progress.** The published release remains [1.5.0](1.5.0.md). No 1.5.0.1 tag, GitHub release or NuGet package has been published. Historical pins, captures and the original 1.5.0 release record remain intact.

## Providers, tools and extensions

Responses transcript tool handling, non-null assistant-content compatibility, prompt-cache-key controls, classifier provider overrides from `models.json` and Copilot System One routing are implemented. The effective per-request Responses service tier supplies usage pricing when the provider omits its tier echo. These are source-backed request and routing changes; fake transports and offline fixtures do not establish whole-provider equivalence.

Anthropic message threads add bounded process-local continuation state with compatibility checks, OAuth projection, cleanup and shared cache-warming policy. Prepared requests, optional captures and public wire round trips preserve UTF-16 values and metadata names while retaining malformed-field and resource-limit checks. Continuation state is not a durable transcript or a cross-process cache.

Large-file reads can stream selected ranges through supporting adapters; custom adapters retain a bounded fallback. Process output capture is bounded while retaining process-tree cleanup. Streamed tool arguments retain immutable snapshots without repeatedly copying the complete history. Shell authentication adds login/logout paths, API-key and no-browser modes through the existing provider flows.

The Node bridge uses the reviewed, pinned Pi 1.5.0 npm package set and [attribution policy](../../website/src/content/docs/docs/extensions/node-bridge.md). Overlay handles now coordinate lifetime, focus, visibility and resize state. Native macOS modifier queries are implemented; physical Apple Terminal key behavior still needs its own qualification.

## Durable, Chord and native hosting

Durable adds per-conversation compaction settings and transaction submission lookup, forwards thinking budgets and WebSocket handshake timeouts through prepared native and hosted requests, and carries explicit identity and provider request hooks through chat and non-chat operations and account routes. An already prepared in-flight request keeps its persisted settings. Ordered SQLite bulk execution preserves transaction, refusal and receipt semantics. SQLite telemetry is opt-in; the delta tracker reduces retained open-change work.

Chord now includes the native host, transactional reload and version adaptation, jobs, registries, versioned links and remote routes. Its **legacy protocol-4 runtime and cluster/manager remain distinct** from the current protocol. Native hosting adds trusted .NET plugins, HTTP utilities and process workers; [the plugin sample](../../samples/chord/NativePlugins) demonstrates the application boundary. This does not imply arbitrary TypeScript/npm plugin, Node IPC or browser-build compatibility.

`PiSharp.Durable.Store` provides the Chord storage and registry adapters. [Examples 35–37](../../samples/Durable.Chord.Examples/README.md) use the real Chord host. Separate independently reproduced upstream captures cover restart, compaction and the stored table/job schema-migration corpus. They extend the available evidence without relabeling historical captures or turning authored cases into captured observations.

## Remote environments and evaluations

The Env implementation includes bounded protocol framing, client lifecycle, a native daemon, remote filesystem and process adapters, watches, SSH bootstrap and a verified artifact cache. Unix PTY support uses a native shim. **Windows terminal creation returns `ENOTSUP`**; ordinary Windows filesystem and process operations remain available. Daemon executables are separate NativeAOT artifacts, supplied through an explicitly trusted hash catalogue; installing an Env package does not download or run a daemon. See [SSH and artifact handling](../env-ssh.md).

The [repository evaluation harness](../evals.md) compares paired runs with and without supplied documentation, validates incomplete or invalid observations, and reports nullable metrics and deterministic protocol identities. Its default synthetic fixture tests reporting mechanics. Explicit process/container and live-provider modes require separate inputs and execution; fixture scores are not evidence of model quality, documentation lift or live container qualification. The tool is not a NuGet package or the WebAgent Evals product.

## Release preparation corrections

Validation of the candidate exposed additional runtime and qualification defects:

- The plugin loader classifies the awaited primary exception before aggregating the remaining fault evidence, retaining the distinction between initialization and load failures without losing cleanup diagnostics.
- Responses and Codex strict-tool patching covers both initial and incremental developer `additional_tools` declarations. Malformed or ambiguous targets are refused instead of silently applying an incomplete patch.
- Unix hosting uses cancellable named-mutex ownership without unsupported multiple-handle waits, distinguishes HTTP request-target forms correctly, and uses private Unix pipe paths for native process transports. Existing authorization and origin checks remain in force.
- The Env daemon's hello version comes from the actual build, with source metadata removed. Candidate 1.5.0.1 artifacts can therefore agree with SSH's exact trusted-artifact version check; explicit version overrides and protocol version 1 remain supported.
- The Node compatibility loader preserves file-URL query and hash components when resolving disk paths, retaining the fresh module identity required by reload. The defect and correction were reproduced with real Node; that focused evidence is not whole-extension or all-platform qualification.
- CI setup resolves and propagates the actual SDK executable, provisions the integrity-pinned historical npm archive and required `fd` tool, and parses actual strict result statuses. Missing prerequisites, failures and skips remain evidence rather than being treated as passes.

These corrections do not by themselves establish successful required hosted workflows. Candidate readiness still requires the exact-source gates below.

## Packages and migration

The candidate prepares **28 libraries plus `PiSharp.Cli`: 29 packages total**. The five added experimental libraries are:

| Package | Opt-in diagnostics |
| --- | --- |
| `PiSharp.Chord` | `PISHARP_CHORD001` |
| `PiSharp.Chord.Hosting` | `PISHARP_CHORD001` |
| `PiSharp.Durable.Store` | `PISHARP_DURABLE001`, `PISHARP_CHORD001` |
| `PiSharp.Env.Protocol` | `PISHARP_ENV001` |
| `PiSharp.Env` | `PISHARP_ENV001`, `PISHARP_DURABLE001` |

All target .NET 10. Existing experimental diagnostics remain applicable. Every PiSharp sibling dependency stays pinned to the exact same package version; upgrade siblings together. Chord deliberately uses Contracts' internal schema engine through a friend assembly without exposing those internal types. Chord and Hosting depend directly on Tools and bring Agent/AI transitively. Hosting requires the `Microsoft.AspNetCore.App` shared framework; native plugins are trusted code, not a security sandbox. Details and the external-consumer gate are in [package admission](../contracts/gap-package-admission.md).

The daemon and evaluation tool are not NuGet libraries. WebAgent, Durable.Web, Durable.MSSQL, Durable.Hosting/Server/Client, ModelRuntime and Web.Common remain unpackaged; the existing CLI-internal hosting components do not become separate packages. Adding the five libraries does not add a default CLI dependency on them. `PiSharp.ExtensionHost` retains assembly identity **1.0.0.0**; other assemblies follow the candidate's SDK-derived **1.5.0.1** identity.

The Durable API and stored formats remain experimental and may change in any release. The new `ITx.GetSubmissionAsync` has a default implementation that throws `NotSupportedException`: existing external implementations can still compile, but must implement lookup before callers can use it. Back up sessions before testing upgrades. The [1.5.0 migration cautions](1.5.0.md#stored-formats-no-way-back) still apply: sessions opened or written by the 1.5.0 line cannot be continued by PiSharp 1.2.0.x. New per-conversation compaction data does not require a new SQL table schema. The existing native fail-stop policy after an uncertain session write remains in effect.
