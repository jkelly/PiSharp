# Explicit admitted MCP HTTP authentication (R946 SDK)

This leaf binds caller-supplied bearer-token and unauthorized callbacks into the actual admitted HTTP operation and CLI channel factory. It performs no client, endpoint, credential, token-store, discovery, browser, PKCE or OAuth exchange acquisition. The default factory remains unauthenticated. The optional authentication argument is explicit host admission, independent of the previously bound per-channel dynamic roots provider.

The pinned original is Pi v0.99.1 commit d86654abb8862e201933517d6f1fce9f88dd117f, packages/mcp/src/auth-provider.ts and transports/streamable-http.ts. Original authorizedFetch reads a token for each attempt; after a first 401 or 403 challenge containing insufficient_scope it awaits onUnauthorized, discards that response, and retries once with newly read credentials. Other responses and the second response are returned unchanged. Only GET/POST use this retry loop; DELETE receives token headers without challenge retry. Nonempty tokens replace Authorization; an absent/empty token preserves explicitly supplied headers. This source follows those bounded decisions and replays the identical finite buffered body to the exact admitted endpoint.

The native unauthorized context borrows the first rejected HttpResponseMessage until its original callback settles. It carries the admitted endpoint and rejected token, and deliberately grants no implicit fetch/client dependency. A caller may separately admit its own exchange dependency in its callback closure. Its diagnostic ToString excludes the token. The transport owns the returned response; the wrapper discards rejected responses and its own cloned requests. Unlike the original discard helper, which suppresses body-cancel rejection, native disposal failures remain disclosed and can prevent retry. This is a documented native ownership adaptation, not full JS OAuth or response-object parity.

Each callback ValueTask is materialized exactly once; its actual Task is directly awaited and retained in McpHttpAuthenticationOriginalException with complete unflattened Task.Exception evidence and the direct await exception. Faulted OperationCanceledException remains Faulted. A genuinely canceled callback with the requested owned token remains canceled; unrelated cancellation is disclosed as an original failure. Stop fences later physical admission, cancels the owned token, starts actual physical stops, joins held token/challenge/send/cancellation originals and disposes owned registrations. Physical stop originals are captured once and shared across retry/close. As in the admitted physical-operation contract, Send owns send failures, while Stop joins Send and reports cancellation/cleanup failures. Close never requires the caller to release or forget user work: an ignoring callback must settle before close can complete. Same-owner callback stop/send reentry rejects before effects; inherited frames deactivate on settlement.

Six authored groups in McpAdmittedHttpAuthenticationTests exercise actual McpServerRuntime initialization over a borrowed HttpClient with an in-memory handler, exact 401 body replay/token reread/discard order, ordinary versus insufficient-scope 403 behavior and the two-attempt bound, held token/challenge drain and reentry, no late send after stop, shared/multiple original faults, faulted OCE, and simultaneous challenge/discard failure. No network handler, live service, credential, browser or store is used. CapturedOriginals exposes subsidiary Task/aggregate/direct identities. Finite callback-entry gates are raced against actual work and owned timers, which are canceled and joined. Tests are authored only: the coordinator must explicitly register Cases() and compile/run them in its qualification owner. No global fixture Program, project, existing producer artifact or accepted qualification is changed.

Dependencies are the frozen dynamic-roots binding 1953cc141b20adb5c5b19bd2b52547aab3a55be5 and fixture correction 403fcad7b21d189beffebdd8dc24049e9e6ece6a. OAuth state-provider six-case evidence does not qualify this HTTP flow. This leaf has zero native execution; full OAuth authorization-server discovery, refresh coordination, protected-resource metadata, token persistence and default profile policy remain separate work.
## R971 cancellation ancestry successor

R967 identified a real late cancellation self-join: normal CancellationToken.Register captures the token invocation context; once that invocation returns, its shared frame is inactive. A later owner CancelAsync callback could obtain and synchronously join the same stop task that must await that callback. The successor performs actual synchronous CancellationTokenSource.Cancel inside an explicitly captured, owned Task under thread-local cancellation ancestry. That original cancellation Task is directly joined and its unflattened fault aggregate is retained. It is not detached cancellation work. CancelAsync cannot establish an initiating thread's thread-local guard in its queued callback execution.

Before scheduling stop, both logical and actual synchronous parent frames are captured explicitly and passed through to the cancellation worker. Normal Register execution-context restoration cannot erase the worker's ThreadStatic ancestry. Same-owner and nested ancestor stop/send entry refuses before returning an existing stop task or mutating admission. Shared frames deactivate in finally; unrelated owner retirement and later ordinary joins remain supported. No caller token callback is suppressed or abandoned.

The existing six named groups now also author ordinary Register callbacks after successful token work has completed; real nested cancellation/inner-stop joins assert both self and ancestor immediate refusal, while an unrelated third owner actually closes. Unexpectedly accepted tasks are retained and joined after callback unwind rather than hanging the control. A separate subcontrol makes normal cancellation callbacks throw a shared leaf and nested AggregateException, asserting the actual cancellation original remains faulted with both exact references. Existing held-token/challenge and retry controls remain unchanged. These controls remain source-only and unexecuted; R946 and R967 history is preserved.
